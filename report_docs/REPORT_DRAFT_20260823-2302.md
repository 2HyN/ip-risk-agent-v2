# ⟪완료 1⟫ Drive — D1 이 "결정"에서 "배포된 구조"로

이전 초안 §4.0 은 D1 을 **채택한 결정**으로 적었다. 이 판에서는 그것이 **구현·검증·배포**
됐고, 도중의 실측이 결정의 성격 자체를 바꿨다.

## 1.1 ⟪정정⟫ `drive.file` 은 "버린 대안"이 아니라 **동작하지 않는 것**이었다

이전 초안의 세 선택지 표는 `drive.file` 을 "안전하지만 파일을 하나씩 고르게 하므로 폐기"
라고 적었다. **실측이 그 서술을 뒤집었다.**

운영에서 사용자가 폴더(`patent`, 사용자 소유, 파일 5개)를 Picker 로 골랐다.

| 물음 | 답 |
|---|---|
| 폴더 메타데이터가 읽히는가 | 예 — `canListChildren=True` |
| `files.list('<폴더>' in parents)` | **0개** |
| 같은 폴더를 서비스 계정으로 | **5개** |

`drive.file` 의 `files.list` 는 **폴더 소속이 아니라 건별 승인**으로 거른다. Picker 의
폴더 선택은 **폴더 객체 자신만** 준다 — 안은 영영 못 읽는다. 반대 방향이 그것을
증명한다: 승인받은 문서 하나의 부모 폴더는 메타데이터가 **404** 인데, 그 폴더를 부모로
건 질의는 그 문서를 돌려준다.

**그래서 D1 은 개선이 아니라 전제였다.** 폴더 단위 추적(D2)은 `drive.file` 위에서
원리상 성립하지 않는다. (결함 41, `SOURCE_MEASUREMENT.md` §2.1.2)

이 실측에 이르는 과정 자체가 결함 둘을 더 냈다 — 서버가 `mimeType` 을 검사하지 않아
**Google 문서 하나가 폴더로 받아들여져** 아무것도 추적하지 않는 ACTIVE 마운트가
성공으로 보였고(결함 37), 빈 폴더와 못 읽는 폴더가 화면에서 똑같이 아무것도 아닌 것으로
보여 **사용자가 폴더를 제대로 고르고도 안 되는 줄 알았다**(결함 40).

## 1.2 지금의 Drive 연결 흐름

승인 화면도 Picker 도 없다. 세 화면이 한 문장으로 줄었다 — **"폴더를 이 주소에 공유하고,
그 주소를 붙여 넣으세요."**

| | 예전 (`drive.file` + Picker) | 지금 (D1) |
|---|---|---|
| 신원 | 사용자 OAuth | 서비스 계정 `iprisk-v2-drive` — **프로젝트 역할 0** |
| 승인 | OAuth 동의 화면 + Picker | 사용자가 폴더를 그 주소에 **뷰어로 공유** |
| 폴더 안 | 못 읽는다 | 읽는다 |
| 보관할 자격증명 | 사용자 refresh token | **없다** |
| 브라우저로 내려보내는 것 | Picker API 키 | 공유 주소 (알아도 접근이 안 생긴다) |

* **가장(impersonation)으로 매번 짧은 토큰을 받고 저장하지 않는다.** 키 파일이 없고
  Secret Manager 에도 없다. workspace 를 전부 지운 뒤 refresh token 19개가 남아 있던
  사고가 **구조적으로 재발 불가**가 됐다 — 이전 초안이 D1 의 기대 효과로 적었던 그
  문장이 이제 배포된 사실이다.
* **Drive 전용 SA 는 프로젝트 역할이 0이다.** 접근이 공유에서만 오므로 역할이 필요
  없고, 역할이 없으므로 그 신원이 새더라도 프로젝트 데이터에 닿지 않는다. 운영 신원
  둘(api·worker)에는 이 SA 하나에 대한 `serviceAccountTokenCreator` 만 붙어 있고,
  이 결속은 IAM 계약 문서와 배포 관문이 검증한다.
* **붙이기 전에 확인한다.** 폴더인지 보고 아니면 거절하며(결함 37), 훑은 파일 개수를
  응답에 실어 **0을 0이라고 말한다**(결함 40). 감시 채널은 6시간 주기 갱신을 기다리지
  않고 **붙이는 자리에서** 건다(결함 39).

## 1.3 D1 전환이 드러낸 숨은 결합 둘

전환 직후 운영에서 두 가지가 연쇄로 부러졌고, 각각 시험으로 잠갔다.

**결함 43 — OAuth 시절의 조건이 D1 마운트를 거절했다.** 마운트-연결 조회가
"자격증명이 없으면 고장"이라는 조건을 갖고 있었다. OAuth 시절엔 맞는 조건이었지만 D1
에서는 **없는 것이 정상**이라, 모든 D1 마운트가 초기 훑기에서 502로 떨어졌다. 라우터
시험이 가짜 조회를 써서 이 경로를 못 봤다 — 실제 조회를 쓰는 시험을 넣고, 옛 조건을
되살리면 실패하는 것까지 확인했다.

**결함 42 — 정체성이 계정이라 폴더 둘이 하나로 접혔다.** Drive 마운트의 정체성이
"연결된 Drive 계정"이었다. 사용자 OAuth 시절엔 실제로 마운트를 갈라 주는 값이었는데,
신원이 서비스 계정 하나가 되자 **모든 사용자·모든 폴더에 대해 같은 값**이 됐다. 폴더
둘을 붙이면 같은 마운트로 수렴해 두 번째가 첫 번째의 추적 범위를 덮어쓰고, 변경 커서를
나눠 쓰다 서로의 변경을 삼킨다. 정체성을 **폴더 id** 로 옮겼다 — GitHub 이
`owner/repo@branch` 를 쓰는 자리다. 두 키 모두 `risk_workspace_id` 를 품으므로 **서로
다른 워크스페이스가 같은 폴더를 추적해도 각자의 마운트·커서·감시 채널을 갖는다**(D7).

## 1.4 ⟪진행 중⟫ 경로 정합 — 게이트가 모든 Drive 분석을 거부한 건

D1 배포 뒤 실사용에서 마지막 결함이 나왔다. 폴더는 붙고 파일 5개가 잡혔는데 분석이 전부
`SECURITY_GATE:CANONICAL_CONTEXT_MISMATCH` 로 거부됐다.

게이트는 스냅샷의 경로 힌트로 아티팩트의 `logical_path` 를 다시 만들어 비교하는데, 그
값을 내는 세 자리(초기 훑기·가져오기·대조)가 서로 달랐다 — 초기 훑기는 경로를 비워
평평하게 등록했고, 가져오기는 부모를 따라 올라가되 **마운트 폴더 자신까지** 경로에
넣었다. 경로 해석이 "마운트 뿌리 기준 상대 경로"라고 적혀 있으면서 뿌리를 받지 않았고,
`drive.file` 시절에는 "읽지 못하는 조상"이 우연히 뿌리 노릇을 했던 것이다. D1 에서는
무엇이 읽히는가가 **사용자가 무엇을 공유했는가**에 달려 있으므로, 뿌리는 우연히 정해지면
안 된다.

세 자리가 같은 뿌리(`folder_id`)를 명시적으로 받도록 고쳤고, "등록한 경로 = 가져온
경로"를 직접 보는 시험 둘을 넣었다(옛 코드에서 실패 확인). **로컬 시험 1,138건 통과.
커밋·배포 전이다.** — 「제출 직전 재확인」: 이 문단은 배포되면 ⟪완료⟫로 옮긴다.

# ⟪완료 2⟫ 세 소스가 전부 "폴더"가 됐다 (1단계 완결)

이전 초안 시점에 실측 문서가 지적한 것 — "Drive 만 폴더가 아니다"(낱개 파일 명단) —
이 해소됐다. 이제 세 소스의 마운트 단위가 같은 모양이다.

| 소스 | 마운트 단위 | 처음 훑기 | 지속 추적 |
|---|---|---|---|
| GitHub | `owner/repo@branch` | 트리 재귀 | push webhook |
| Local | 기기 + 폴더 | watcher `emitExisting` | chokidar 감시 |
| **Drive** | **공유받은 폴더** | **폴더 재귀 (상한 300·깊이 10)** | **변경 피드 + 15분 대조** |

* **추적 판정이 명단에서 소속으로 바뀌었다.** "이 id 가 목록에 있는가"가 아니라 "지금 그
  폴더 안에 있는가"(부모를 따라 올라간다). **넣으면 잡히고 빼면 빠진다** — 이 서비스의
  운영 방식("추적할 파일을 지정 폴더에 넣어 둔다")이 그 판정 위에서만 성립한다.
* **1-A 실측이 끝났다** (이전 초안 「팀 확인」 1번). 권한 0인 버리는 SA 로 셋 다 "예" —
  넣으면 잡히고, 나가면 `removed` 로 오고, 되돌리면 다시 나타난다. 특히 **이탈과 삭제가
  피드에서 같은 모양**이라 폴더 대조 작업이 통째로 불필요해졌다. 부활은 공짜로 따라온다
  — 되돌아온 파일의 `fileId` 가 같아서 기존 아티팩트 정체성이 그대로 잡는다.
* **바로가기는 규칙으로 막는다.** 예전에는 mime 통과 목록에 없어서 우연히 막혔는데,
  공유 폴더 안에 바로가기를 두면 **폴더 밖이 읽히는** 구멍이므로 명시적 규칙이 됐다.
* **상한을 넘으면 잘랐다는 사실을 남긴다.** 조용히 자르면 "전부 검사했다"로 읽힌다.

## 2.1 ⟪신규⟫ Local 은 라이선스 위험을 **한 번도 만든 적이 없었다**

운영 검증에서 나온 가장 큰 단일 결함이다. 데스크톱 watcher 의 필터 표가 서버 표와 따로
관리되다 어긋나서, **의존성 파일(`requirements.txt`, `package.json`, …)이 감시 대상에서
빠져 있었다.** Local 마운트는 문서만 올려보냈고, 따라서 라이선스 분석이 한 번도 돌지
않았다 — 그런데 아무 오류도 없었으므로 "Local 은 잘 된다"로 보였다.

서버의 Python 표에서 TypeScript 필터를 **생성**하도록 바꿨고(`generate_source_filters.py`),
표가 어긋나면 배포 자산 시험이 실패한다. 고친 뒤 운영에서 Local 마운트가 처음으로
라이선스 위험(PyMuPDF → AGPL-3.0-only → HIGH)을 만들었다.

**교훈으로 옮길 것** — "언어 경계에서 표를 복사하면 반드시 어긋난다. 한쪽을 원본으로
정하고 다른 쪽을 생성하라." (SECTION 15.3 감이다)

## 3.1 ⟪신규⟫ 검증 자체가 낸 사고 — UTF-8 BOM (결함 32·33)

시험 데이터를 준비하던 PowerShell 명령이 BOM 을 붙여 썼고, 파서가 그 줄을 **조용히
건너뛰어** "COMPLETE + 선언 0건"이 됐다 — 열려 있던 `requests` 위험이 **해소로
오보**됐다. 0단계가 막으려던 바로 그 실패("망가진 읽기가 깨끗한 0건으로 보임")가 남아
있던 입구 하나로 재현된 것이다. 모든 파서가 BOM 을 벗기게 고치고, 걸러진 줄이 있으면
PARTIAL 로 강등되게 했다. 재현 절차는 회귀 시험으로 남겼다.

## 3.2 ⟪신규⟫ matplotlib 이 최고 위험으로 오보된 건 (결함 27 계열)

라이선스 이름을 찾으려고 **59,523자짜리 라이선스 문서 전문**을 훑다가 그 안에 인용된
FreeType 의 GPL 문구에 걸려 `GPL-2.0-only` 가 됐다. 자유 서술 스캔은 **선언 길이의
문자열**에만 허용하고, 문서는 거부하며, PEP 639 표현식과 trove classifier 를 먼저 읽게
바꿨다. "그럴듯한 오답이 최고 위험 자리에 앉는 것"이 이 제품이 없애려는 실패라, 우선
순위를 높여 즉시 고쳤다.

# ⟪정정 5⟫ 초기 스캔 비용 — **표본이 틀렸다**

이전 초안 §4.1 의 실측(Local 마운트 20,764파일 · 228,404회 · 월 한도의 228배)과 그
결론("소스 코드까지 빼야 한도 안에 들어오는 유일한 조합")은 **전제가 틀린 계산**이었다.
제출 보고서에 그대로 옮기면 안 된다.

* 그 수치는 **이 저장소 전체를 Local 마운트에 넣는다**는 가정으로 쟀다. 이 서비스의
  운영 방식은 그것이 아니다 — **보안을 고려해 추적할 파일만 지정 폴더에 넣어 두는
  것**이고, 그러면 파일 수가 수십 단위라 한도 문제가 다르게 보인다. 저장소 전체 실측은
  "상한 확인"으로만 의미가 있다.
* **월 1,000회는 설계 제약이 아니라 무료 티어의 성질이다.** 실사용 배포에서 유료 전환로
  풀리는 값을 아키텍처 결론("소스 코드 제외")의 근거로 쓰면 안 된다.

보고서 4.1 의 F-05 완료 조건, 11 장의 "비용·한도" 칸, 13 장의 "운영 시 주의사항"을 이
프레임으로 고쳐야 한다 — 수치는 남기되 "상한 실측"으로 표기하고, 폴더 마운트 미개방
사유로는 쓰지 않는다(이미 개방됐다).
