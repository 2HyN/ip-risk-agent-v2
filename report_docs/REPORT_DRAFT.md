# SECTION 01 프로젝트 개요

## 1.1 한 문장 서비스 소개

여러 협업 Source Workspace 를 하나의 Risk Workspace 에 연결하고, 변경을 지속적으로
감지하여 Patent·License 중심의 잠재적 IP Risk 를 근거 기반으로 분석함으로써,
사용자가 장기적으로 검토·추적·감사할 수 있게 하는 **Secure Human-in-the-Loop
AI Risk Management System**.

# SECTION 02 문제 정의

## 2.1 문제 배경 및 현황

협업 프로젝트에서는 코드와 문서가 지속적으로 수정되고, dependency 와 license 가
변경되며, 기술 아이디어가 문서화·구현되면서 기존 특허와의 관련성도 계속 달라진다.
즉 **검사 대상 자체가 고정되어 있지 않다.**

그러나 IP 점검은 이러한 변화와 무관하게 특정 시점에 1회성으로 수행되는 경우가 많아,
이전 점검 이후의 변경분에 대해 재점검이 반복되고, 변경 시점과 점검 시점 사이의
간격 때문에 리스크 발견이 늦어진다.

점검을 자동화하면 이 간격은 줄지만, **그것만으로는 도구가 실제로 쓰이지 않는다.**
자동화된 결과를 검증 없이 신뢰할 수 없다는 문제와, 점검을 위해 원본 소스를 외부
도구에 올려야 한다는 문제가 남기 때문이다. 앞의 문제는 결과에 **실재하는 근거**를
붙이고 최종 판단 권한을 사람에게 남기는 것으로, 뒤의 문제는 원본을 영구 저장하지
않고 필요한 최소 범위만 분석에 넘기는 것으로 풀어야 한다.

따라서 이 프로젝트는 "얼마나 정확히 찾는가" 보다 **"변화에 맞춰 계속 돌면서, 믿을
수 있는 형태로, 안심하고 쓸 수 있게 돌아가는가"** 를 문제 해결의 기준으로 삼는다.

## 2.2 핵심 문제 진술문

**Who** — 전담 법무·특허 인력 없이 GitHub·Drive·로컬 PC 등 여러 곳에 소스와 문서가
흩어진 채 개발하는 스타트업·SME 개발팀, 그리고 그 프로젝트의 IP 리스크를 책임지는
담당자.

**What** — 코드·문서·의존성이 계속 바뀌는데 IP 점검은 특정 시점 한 번에 그친다.
점검하려면 원본 전체를 외부 도구에 올려야 해서 보안상 부담스럽다. Risk 를 누가 언제
어떻게 판단했는지 이력이 남지 않는다.

**Why** — 검사 대상이 계속 변경되는데 점검이 1회성에 그치면 재점검이 반복되어
프로젝트 진행이 지연되고, 리스크 발견이 늦어져 이미 확산된 이후 대응하게 되므로
비용이 커진다. 실제 구현 과정에서도 공개 라이선스 메타데이터만으로는 강한 의무를
놓칠 수 있다는 점, 특허 초록만으로는 검토 우선순위 판단이 어렵다는 점이 확인되어
지속적·근거 기반 점검 체계의 필요성이 실증됐다.

## 2.3 문제 원인과 기대효과

표면적으로 드러나는 현상은 **한 번 점검한 결과가 금방 낡아 실질적인 보호 효과가
없다**는 것이다. 그러나 근본 원인은 점검 주기가 길다는 데 있지 않다. 기존의 IP
점검은 "특정 시점의 산출물을 검사해 목록을 내놓는 일" 로 정의되어 있어, **검사
대상이 바뀌었는지, 이번 결과가 지난번과 같은 건인지, 그 판단을 누가 왜 내렸는지**
는 애초에 다루지 않는다.

자동화만으로도 해소되지 않는다. 결과의 출처를 확인할 수 없으면 사용자는 그것을 업무
판단에 쓸 수 없고 검증하지 않은 책임은 인용한 사람에게 돌아오며(E2), 점검을 받기
위해 원본을 외부에 넘겨야 하는 구조라면 성능과 무관하게 도입 자체가 보류되기
때문이다(E3).

**해결 대상이 아닌 것** — 특허 침해나 라이선스 위반에 대한 법적 결론은 전문가와
사용자의 판단 영역이다. KIPRIS 의 청구항 미제공, 공개 라이선스 메타데이터의
부정확성 같은 원천 데이터의 한계도 이 프로젝트가 제거할 수 있는 대상이 아니다.
이 경우 **한계를 감추지 않고 불확실성으로 드러내는 것까지를 서비스의 책임**으로 둔다.

**기대효과** — 이 원인들이 해소되면 사용자는 변경이 생길 때마다 점검이 따라붙어
실사나 배포 직전에 몰아서 확인하며 일정을 지연시킬 일이 줄고, 각 결과의 출처가 함께
제시되어 그대로 신뢰할지 다시 확인할지를 스스로 정할 수 있으며, 과거의 판단이 사유와
함께 남아 같은 리스크가 재발해도 논의를 반복하지 않는다. 여기에 원본을 외부에
넘기지 않고도 점검이 가능하다는 조건이 더해져, 보안을 이유로 도구 도입을 미뤄 온
팀도 실제로 사용할 수 있게 된다.

| 사용자<br>**Viewer** | Risk 현황과 근거를 조회만 하는 최하위 권한 사용자 | 리스크가 있는지조차 모른 채 지나가다가, 나중에 문제가 불거진 뒤에야 뒤늦게 알게 됨 | Dashboard 와 Risk Detail 에서 현재 리스크 현황과 근거를 언제든 조회할 수 있어 상황 파악이 쉬워짐 | 하 |

네 역할은 **권한이 누적되는 구조**다 — Viewer ⊂ Risk Reviewer ⊂ Source Manager,
Owner 는 전부. 권한 11종과 액션 17종을 매핑표로 두고, 인가는 순수 함수 하나로 모아
거부 사유를 9종으로 구분한다.

주목할 점은 **어떤 역할에도 원본 소스 접근 권한이 없다**는 것이다. 애플리케이션
권한을 아무리 높여도 provider 자격증명의 소유자가 아니면 소스를 읽을 수 없고,
이 경우 별도의 거부 사유(`PROVIDER_AUTHORITY_MISMATCH`)로 갈린다. **애플리케이션
권한을 준다고 소스 권한을 날조하지는 않는다**는 것이 이 설계의 핵심이다.

## 3.1 핵심 사용자 페르소나

* **직업·역할** — 5인 이하 스타트업의 백엔드 리드 (기획·개발·배포를 겸임, 전담
  법무·특허 인력 없음)
* **사용 환경** — 코드는 GitHub, 문서는 Google Drive, 실험 코드는 로컬 PC 에 분산.
  팀원 3~4명이 여러 Source Workspace 를 오가며 동시 작업
* **목표** — 투자 유치·기술 실사 전에 특허·라이선스 리스크를 미리 파악하되, 개발
  속도는 늦추지 않는 것
* **행동 특성** — 오픈소스 패키지를 빠르게 도입하는 편이라 라이선스 조항 확인은
  뒷전으로 밀림. 점검을 미루다 배포 직전에 몰아서 확인
* **데이터·디지털 활용 수준** — 개발 도구(GitHub, CI/CD)는 능숙하지만 KIPRIS·SPDX
  같은 특허·법률 데이터베이스는 사용 경험 거의 없음
* **대표 불편** — ① 의존성·문서가 바뀔 때마다 처음부터 재점검 ② 원본을 외부 SaaS 에
  올려야 하는 도구는 보안상 꺼려짐 ③ 과거에 "괜찮다" 고 판단한 리스크도 근거 기록이
  없어 재발 시 처음부터 다시 검토

## 3.2 서비스 플로우

> 〔다이어그램 ⑤ 서비스 플로우 — 이 자리에 배치〕

```
Google 로그인 → Risk Workspace 생성/참여
  → Source Workspace Mount (Drive OAuth / GitHub App 설치 / Local 폴더 등록)
        ↓
  변경 감지 (Drive webhook·reconciliation / GitHub push webhook / Local watcher)
        ↓
  ChangeEvent 생성 — fingerprint 로 중복 제거
        ↓
  Cloud Tasks 큐 (45초 coalesce 지연)
        ↓
  Security Gate ──(미승인)──→ 분석 중단, 거부 사유 기록
        ↓ (승인)
  Patent / License 분석 (KIPRIS · deps.dev · Gemini)
        ↓
  Risk 반영 (신규 NEW / 기존 EXISTING / 해소 RESOLVED / 부활)
        ↓
  설명·권고 부착
        ↓
  Dashboard · Risk Detail · Timeline 에서 검토 및 판단
```

**주요 정책 (에러·예외 처리)**

| 상황 | 정책 |
|---|---|
| Snapshot 실패 | provider 실패로 기록. **빈 성공으로 위장하지 않는다** |
| 분석 결과 불확실(FAILED / INCONCLUSIVE) | 권위 없는 결과로 보고 **기존 Risk 상태를 바꾸지 않는다** |
| 근거 없는 ID 인용 | 그 대조 **결과 전체를 폐기** |
| 판본 추월 (분석 중 소스가 앞서 나감) | `SOURCE:REVISION_SUPERSEDED` 로 종료. 새 판본을 맡은 실행이 이어받는다 |
| provider 호출 한도 소진 | 다른 실패와 구분해 경고 톤으로 안내. 다시 검사해도 같은 결과임을 알린다 |
| 추적 해제 / mount 비활성화 | Risk 를 자동으로 RESOLVED 하지 않는다. `RESOLVED + EXCLUDED` 로 닫고, 다시 연결되면 되살린다 |
| worker 사망 (좀비 실행) | lease 만료를 기준으로 회수. 화면의 "다시 검사" 로 사람이 풀 수 있다 |

## 3.3 핵심 가치 제안

| 관점 | 사용자가 얻는 결과 |
|---|---|
| **시간** | 한 번 연결하면 변경마다 점검이 따라붙는다. 재점검을 위해 사람이 하는 일은 0 이다. 같은 문서를 다시 검사해도 외부 API 호출 **0회**로 끝나므로(캐시) 반복 점검의 비용이 사실상 사라진다 |
| **품질** | 모든 결과에 근거가 붙는다. 근거가 없으면 결과 자체를 만들지 않는다. 모델이 지어낸 인용은 코드가 본문 대조로 걸러내 화면까지 오지 않는다 |
| **접근성** | KIPRIS·SPDX 를 다뤄 본 적 없는 개발자도 "왜 위험인지" 와 "무엇을 하면 되는지" 를 자기 말로 읽는다. 원문 청구항은 근거로 함께 제공된다 |
| **보안** | 원본은 영구 저장되지 않는다. 제외 범위로 지정한 경로는 **변경 이벤트조차 만들어지지 않아** 시스템이 읽지 않는다 |
| **감사** | 누가 언제 무엇을 근거로 판단했는지가 append-only 로 남는다. 같은 리스크가 재발해도 과거 판단을 즉시 확인할 수 있다 |

검증이 **세 겹**인 것이 요점이다. 오프라인 고정 코퍼스는 비용 없이 파싱 경로를 지키고,
실호출은 외부 응답이 문서와 다른 것을 잡고, 실배포 실측은 **한 번도 눌러 보지 않은
동선**을 잡는다. 셋이 잡는 결함의 종류가 서로 다르다.

## 6.2 데이터 모델 / ERD

> 〔다이어그램 ⑦ ERD — 이 자리에 배치〕

**canonical 과 operational 을 나눈다.** canonical 은 판정의 근거가 되어 오래 남는
기록이고, operational 은 provider 런타임 상태(감시 커서, 추적 범위, 기기 자격증명)라
수명도 신뢰 수준도 다르다. 저장 위치를 나누면 workspace 삭제 순서도 명확해진다.

**canonical 16 컬렉션**

| 컬렉션 | 뜻 | 주요 관계 |
|---|---|---|
| `users` | 계정 | 1:N memberships |
| `risk_workspaces` | Risk Workspace | 1:N memberships · mounts · risks |
| `memberships` | 사용자 × Workspace 의 역할 | N:1 users, N:1 risk_workspaces |
| `source_connections` | provider 연결(계정 단위) | 1:N source_workspaces |
| `source_workspaces` | 연결 안의 소스 범위 | N:1 source_connections |
| `workspace_mounts` | Risk Workspace 에 붙인 소스 | N:1 risk_workspaces, N:1 source_workspaces |
| `artifacts` | 추적 대상 파일 | N:1 workspace_mounts |
| `artifact_states` | 파일의 현재 판본·가용성 | 1:1 artifacts |
| `change_events` | 감지된 변경 | N:1 artifacts |
| `analysis_jobs` | 변경 한 건의 분석 실행 | 1:1 change_events |
| `risks` | 판정된 위험 | N:1 artifacts |
| `risk_evidence` | 위험의 근거 발췌 | N:1 risks |
| `risk_events` | 위험의 이력(append-only) | N:1 risks |
| `audit_events` | 감사 기록 | N:1 risk_workspaces |
| `source_access_events` | 소스를 언제 무엇을 읽었는지 | N:1 risk_workspaces |
| `notifications` | 알림 | N:1 users |

**operational 컬렉션** — `source_operational_*` 12종(pending connections, mount
bindings, drive/github/local runtime·tracking, devices·credentials·challenges,
oauth states)과 `intelligence_patent_*_cache` 3종(search · document · extraction).

**고유키 sentinel** — Firestore 에는 유니크 제약이 없다. 그래서 `unique-*` 문서를
같은 컬렉션에 두고 소유자 문서 ID 를 적어 유일성을 보장한다. 예를 들어 한 artifact 에
같은 특허가 두 번 Risk 로 생기지 않는다.

**전체 말소** — Workspace 를 삭제하면 canonical·operational 은 물론
**Secret Manager 의 자격증명까지** 지운다. operational 을 먼저 지우고 canonical 을
나중에 지운다 — 반대로 하면 실패했을 때 남은 기록이 가리킬 곳을 잃는다.

## 6.3 데이터 검증(보안 검토)

| 위험 항목 | 해당 여부 | 대응 방법 |
|---|---|---|
| 개인정보/민감정보 포함 | **예** — 사용자 이메일, 소스 원문에 비밀값이 있을 수 있음 | 원본은 영구 저장하지 않는다. 근거 발췌만 남기며 보존 정책이 길이를 제한하고 비밀값 패턴을 마스킹한다. 제외 범위로 지정하면 읽지도 않는다 |
| 출처·라이선스 제한 | **예** — KIPRIS·deps.dev 이용약관 | 원문을 재배포하지 않고 근거 발췌와 출처 링크만 표시한다. corpus 는 공개 자료만 포함하고 manifest 에 원본 링크를 남긴다 |

## 7.1 핵심 프롬프트

**1. `patent_extract_v2`** — 문서에서 특허 검토에 필요한 기술 요소와 검색어를 뽑는다.
`is_technical` 은 구체적인 처리 방식·구조·알고리즘·장치 구성이 서술되어 있고 단순
일정·회의록·사업계획이 아닐 때만 참. `technical_elements` 는 문서에 실제로 서술된
구성만. `search_queries` 는 2~3단어 2~5개, 제품명·회사명 제외. 입력에 없는 조각 ID 를
만들지 않는다.

**2. `patent_compare_v2`** — 문서와 선행 특허를 대조해 겹치는 기술 구성을 찾는다.
*하지 않는 것* — 침해 여부, 권리 범위, 법적 결론. *matched_elements* 는 양쪽에 같은
구성이 나타날 때만 적고, 문서 인용과 특허 인용은 **그대로 옮긴 한 문장**이어야 한다.
요약하거나 다듬으면 안 된다. 같은 분야라는 이유만으로 겹친다고 적지 않는다.
*review_caveats* 는 검토자가 함께 알아야 할 한계(예: 초록만 제공되어 청구항 확인 불가).

**3. `risk_explain_v1`** — 이미 판정이 끝난 Risk 를 사람이 읽을 수 있게 설명한다.
*전제* — 판정은 이미 끝났다. 그 결과를 바꾸거나 반박하지 않는다. *summary* 는 왜
검토가 필요한지, *recommendation* 은 무엇을 하면 되는지를 **행동 수준**으로 적는다.
법적 결론을 내지 않는다. 제시된 근거 목록에 없는 ID 를 인용하면 설명 전체가 폐기된다.

## 7.2 환각·안전·오류 대응

* **근거 ID 검증** — 모델이 인용한 근거 ID 가 제시된 목록에 없으면 **결과 전체를
  폐기한다.** 대조의 특허 근거 ID, 설명의 근거 ID 모두 해당한다.
* **인용문 실재 검증** — ID 만으로는 부족하다. 모델이 적은 인용문이 **그 근거 본문에
  실제로 있는지** 코드가 대조한다. 없으면 그 대조 전체를 버린다. 통과한 인용은 문자
  구간으로 저장되어 화면이 그 문장만 강조한다.
* **판정 재판단 금지** — 설명기는 이미 내려진 판정을 바꾸지 않는다. 등급도 Risk 의
  존재도 건드리지 않으며, 설명이 실패해도 Risk 는 그대로 남는다.
* **실패를 성공으로 위장하지 않음** — provider 호출이 하나라도 실패하면 완전한
  범위를 주장하지 않는다. 권위 없는 결과는 기존 Risk 를 해소하지 못한다.
* **모델 비결정성 대응** — 형식이 어긋난 대조는 같은 프롬프트로 **한 번 더** 묻는다.
  후보 하나가 미끄러졌다고 분석 전체가 미판정이 되는 것을 막기 위해서다. 두 번 다
  어긋나면 그때는 버린다.
* **스키마 불일치 대응** — 내부 검증은 엄격하게 유지하되 API 전송용 스키마만 별도로
  정리하는 변환기를 둔다.
* **불확실성 표시** — 근거가 초록뿐이거나 발췌가 잘렸으면 그 사실을 기록하고 검토
  우선순위를 낮춘다. 감추지 않는다.

| 재정렬/후처리 | **주제 일치 게이트** | 아래 8.1 상술 |
| 출처 표시 | 검색된 조각이 `LICENSE_REFERENCE` 근거로 저장되고 화면에 원문 링크와 함께 표시 | 사용자가 원문을 직접 확인할 수 있다 |
| corpus 버전 기록 | 결과에 `rag_corpus_version` 기록 | 지식이 바뀌면 과거 판정의 뜻이 조용히 달라지는 것을 막는다 |

**배포에서 실제로 동작하고 있다.** Worker 에 corpus 가 연결되어 있고, 저장된 근거
중 `LICENSE_REFERENCE` **8건**이 세 문서에서 나왔다. 배선만 되어 있는 것이 아니라
근거를 만들고 있다.

> 「제출 직전 재확인」 — corpus 버전이 저장소 매니페스트(`2026-08-14.1`)와 배포

> 한쪽으로 맞춰야 한다.

## 8.1 RAG 처리 흐름

> 〔다이어그램 ② RAG 처리 흐름 — 이 자리에 배치〕

```
[색인 시점]
  rag-corpus/manifest.yaml (식별자 · 버전 · 체크섬 · covers)
      → 승인된 문서만 → RAG Engine 색인 → corpus_version 확정

[질의 시점]
  라이선스 정책 판정 (규칙 엔진)
      |
  검토가 필요한 분류인가? --아니오--> RAG 호출하지 않음 (고정 문구)
      | 예
  질의 생성: "{라이선스 표현식} 배포 시 의무사항 {분류}"
      |
  RAG Engine 검색 (top_k=3)
      |
  ★ 주제 일치 게이트 — 이 문서가 이 라이선스를 실제로 다루는가?
      |                                  |
   맞는 것 있음                      하나도 없음
      |                                  |
  근거로 등록(LICENSE_REFERENCE)     근거 없이 고정 문구
  corpus_version 기록                (실패가 아니다)
      |
  Risk 로 저장 → 설명기가 그 근거를 읽어 설명·권고 생성
```

**주제 일치 게이트가 이 설계의 핵심이다.** corpus 가 작고 임베딩 검색은 관련 문서가
하나도 없어도 **가장 덜 관련 없는 것**을 `top_k` 개 돌려준다. 그러면 `GPL-3.0-only`
분석에 AGPL 문서가 근거로 붙어도 근거 ID 검증과 프롬프트 제약을 **모두 통과한다.**
근거가 없는 것보다 **틀린 근거가 붙는 것이 나쁘다.**

임베딩 점수 임계값을 쓰지 않은 이유는 두 가지다. 점수는 provider 응답 필드에
의존해 실측 없이는 검증할 수 없고, 값이 바뀌면 **조용히 무력화된다.** 그래서 점수가
아니라 **주제 일치**로 결정적으로 거른다. 어느 문서가 어느 SPDX 식별자를 다루는지
표로 선언하고, 배포 validator 가 그 표를 corpus manifest 와 교차 검증한다.

부분 문자열로 판정하지 않는 것도 의도적이다 — `AGPL-3.0-only` 는 `GPL-3.0-only` 를
문자열로 포함하므로, 그렇게 하면 **이 게이트가 막으려는 바로 그 오류**를 만든다.

이 게이트는 **라이선스 경로에만** 적용된다. SPDX 표현식에 의존하므로 특허 경로에는
쓸 수 없고, 특허는 애초에 RAG 가 아니라 KIPRIS 실시간 조회를 쓴다.

표가 코드에 있는 이유는 `rag-corpus/` 가 **런타임 이미지에 포함되지 않아** 매니페스트를
실행 시점에 읽을 수 없기 때문이다. 대신 배포 validator 가 코드의 표와 매니페스트의
`covers` 선언을 **교차 검증**해 불일치하면 배포 전에 막는다. 설계 제약이 만든 이중화를
검증으로 묶은 것이다.

검색 자체가 실패하면 그것은 다르게 다룬다. 근거를 못 붙였다는 것은 "모른다" 이므로
범위를 낮춰 **권위 있는 결과로 취급하지 않는다.** 반면 주제가 맞는 문서가 없어서
근거가 비는 것은 정상 경로이고 실패가 아니다.

## 8.2 RAG 고도화 전략

| 단계 | 내용 | 기대 효과 |
|---|---|---|
| 1. corpus 확장 | GPL-3.0, MPL-2.0, EPL 등 커버리지 밖 라이선스 추가 | 지금 "근거 없음" 으로 가는 경로를 줄인다. **단 지금 구조에서는 문서를 늘릴 때마다 코드의 커버리지 표를 함께 고쳐야 한다** — 표를 매니페스트에서 읽어 오도록 먼저 정리하는 편이 낫다 |
| 2. 근거 충분성 자기평가 | 검색 결과가 질문에 답하기에 충분한지 판정하고, 부족하면 불확실성으로 표시 | 지금은 주제 일치만 보고 충분성은 보지 않는다 |
| 3. 특허 쪽 RAG 도입 | 지금 특허는 KIPRIS 실시간 조회만 쓴다. 내부 특허 DB 를 두고 임베딩 검색을 **보조 신호**로 | 검색어 변동에 덜 흔들리는 후보 발굴 |
| 4. Agentic RAG | 모델이 "무엇을 더 찾아야 하는지" 를 스스로 정해 재질의 | 복합 라이선스 표현식·다중 의무 상황 대응 |

우선순위는 **1 → 2 → 3 → 4** 다. 1 은 비용이 가장 작고 지금 바로 효과가 있으며,
4 는 호출 수가 늘어 KIPRIS·Gemini 한도와 충돌한다.

## 10.1 주요 변경 결정

* **FastAPI·Python·프론트 빌드 설정 통일** — 세 축이 서로 다른 버전과 도구를 썼다.
  검증 범위가 더 넓은 쪽을 기준으로 통일하고 재검증했다.
* **라이선스 설명기 제거** — 계약의 `LicenseCandidate` 에 설명을 담을 필드가 없어
  **호출하고 결과를 버리고 있었다.** 후보마다 한 번씩 모델을 부르고 아무 데도 쓰지
  않은 셈이다. 저장된 근거에서 동작하는 `RiskExplanationService` 로 대체했다.
  같은 근거(RAG 참조 포함)를 보므로 정보가 줄지 않는다.
* **검토 우선순위 규칙** — 초록만으로는 변별력이 없어 실측에서 전부 최하 등급이
  나왔다. 초록 근거 2건 이상 일치 시 한 단계 올리도록 조정했다. 파생 점수는
  **기록만 하고 판정에는 쓰지 않는다** — 사람이 매긴 라벨 없이 고른 임계값은 근거가
  없기 때문이다.
* **RAG 관련성을 점수가 아니라 주제로 판정** — 점수 임계값은 provider 응답 필드에
  의존해 검증이 어렵고 값이 바뀌면 조용히 무력화된다. 커버리지 표를 코드에 선언하고
  배포 validator 가 corpus manifest 와 교차 검증한다.
* **Workspace 삭제를 전체 말소로 정의** — 내보내기·가져오기는 기간상 제외하고,
  삭제는 canonical·operational·자격증명까지 지우는 것으로 확정했다.
* **분석 시작을 45초 미룸** — 한 번의 편집이 판본을 여럿 만들면 분석도 여럿 돈다.
  미뤄 두면 뒤엣것이 도착하고 앞엣것은 시작 전에 밀린 것을 알아 **비용을 치르지
  않는다.** 감지 지연이 늘지만 분석 자체가 1~2분이라 체감되지 않는다.

## 12.1 검증 결론

요구사항 UR-01~UR-06 은 **충족되었다.** 판단 근거는 배포 환경에서 수행한 시나리오
검증이다. 특히 이 서비스의 정체성인 "변화에 맞춰 계속 도는가" 는 세 가지가 함께
나와야 성립하는데, 셋 다 확인됐다.

1. 변경이 없으면 **아무 일도 일어나지 않는다** (재검사 외부 호출 0회, Risk 변화 0건)
2. 변경이 생기면 **그 변경분만** 비용을 쓴다 (새 검색어만 호출, 기존은 이월)
3. 겹침이 사라지면 **진짜로 해소된다** (판정해 보고 내리는 해소)

1 과 3 이 함께 나와야 한다는 점이 중요하다. 1 만 있으면 아무것도 안 하는 것이고,
3 만 있으면 보지도 않고 해소하는 것이다.

**추가 검증이 필요한 것** — Local·Desktop 경로의 실측, 사용자 테스트, 그리고
감시를 중단했다가 재개했을 때 Risk 가 되살아나는지(SECTION 13 참조).

**공통 교훈** — I-10 · I-11 · I-12 · I-16 · I-17 은 모두 **한 번도 실행된 적 없는
경로**에 있었고, 시험은 전부 통과하고 있었다. 통과하는 테스트는 실행된 적 없는
경로를 지켜주지 않는다.

I-16 은 한 단계 더 나아간 사례다. **어댑터 시험이 결함을 그대로 복제하고 있었다** —
등록 쪽에도 전체 경로를 넣어 두어 두 값이 시험 안에서는 항상 일치했다. 시험이
구현과 같은 오해를 공유하면 그 시험은 아무것도 지키지 않는다.

오늘 하루에 시험 함수가 **535개에서 643개로** 늘었고(테스트·프론트 +4,454줄),
늘어난 것은 대부분 **실측으로 터진 결함의 회귀 시험**이다.

## 14.1 시연 시나리오

**시연 전 준비** — 배포 URL 로그인 상태, Risk Workspace 하나에 GitHub 저장소가 이미
연결되어 분석이 끝나 있을 것. 저장소는 파일 수와 비용이 예측 가능한 점검용 저장소를
쓴다. 네트워크가 불안할 때를 대비해 **각 단계의 화면 캡처를 미리 준비**한다.

| 단계 | 조작 | 기대 화면 | 설명할 것 |
|---|---|---|---|
| 1 | Dashboard | 워크스페이스 현황 | 지금 무엇이 몇 건인지 한눈에 |
| 2 | Risks → HIGH 항목 | Risk 상세 | **설명·권고**가 먼저 보이고, 그 아래 근거가 있다 |
| 3 | 근거 영역 | 특허 청구항 + 문서 발췌, 겹치는 문장 강조 | 이 강조는 **코드가 본문 대조로 확인한** 인용이다 |
| 4 | 판단 기록 | Timeline 에 남음 | 누가 언제 왜 그렇게 판단했는지 |
| 5 | Sources | 연결된 저장소와 제외 범위 | 제외한 경로는 **읽지도 않는다** |
| 6 | **터미널에서 파일 수정 후 push** | 잠시 뒤 새 분석·새 Risk | **이것이 이 서비스의 정체성** |

6 번이 핵심이다. 시간이 부족하면 1·5 를 줄이고 6 은 반드시 남긴다.
push 부터 분석 시작까지 약 50초가 걸리므로, 그 사이에 3~4 를 설명하면 자연스럽다.

**실패 시 대체** — 준비한 캡처로 진행하고, "지금 화면은 어제 실측한 결과" 라고
밝힌다. 실측 로그(push → webhook → 분석 점유 시각)를 함께 보여주면 신뢰가 유지된다.

| **Gemini (Vertex AI)** | 구조화 출력을 스키마로 강제할 수 있어 **파싱 실패가 아니라 검증 실패**로 다룰 수 있다. RAG Engine 과 같은 플랫폼이라 인증·리전을 하나로 묶는다 | 자체 파싱은 형식 오류 처리 부담이 크다 |

| **deps.dev + 레지스트리 폴백** | 한 곳이 답하지 못해도 다른 곳에서 복원 | 단일 소스는 커버리지 구멍이 생긴다 |
| **Firestore** | 문서 단위 트랜잭션과 TTL 이 필요했고 스키마 변경이 잦았다 | 관계형은 초기 스키마 확정 부담 |
| **Cloud Run 2 서비스 · 1 이미지** | API 와 Worker 의 부하 특성이 다르나 **코드가 갈리면 안 된다.** 같은 digest 로 배포해 버전 어긋남을 구조적으로 막는다 | 단일 서비스는 긴 분석이 요청을 막는다 |
| **Cloud Tasks** | 재시도·지연·OIDC 인증이 필요했다 | 즉시 처리하면 provider 지연에 API 가 묶인다 |

## 14.3 예상 질문과 답변

| 질문 | 답변 |
|---|---|
| **환각은 어떻게 막았나** | 세 겹이다. ① 모델이 인용한 근거 ID 가 제시된 목록에 있는지 ② 인용문이 **그 근거 본문에 실제로 있는지** 코드가 대조 ③ 어긋나면 그 결과 전체를 폐기. 프롬프트로 부탁하는 것이 아니라 구조로 막는다 |
| **우리 소스가 외부로 나가는 것 아닌가** | 원본은 영구 저장하지 않는다. 제외 범위로 지정한 경로는 **변경 이벤트조차 만들어지지 않아** 읽지 않는다. 분석에 넘어가는 것은 승인된 조각뿐이고, 남는 것은 근거 발췌다 |
| **AI 가 틀리면 누가 책임지나** | 법적 결론을 내지 않는 것이 설계다. 모델은 검토가 필요한 지점을 좁히고 설명할 뿐, 판정은 규칙과 Control Plane 이 한다. 최종 판단은 사람이 하고 **누가 언제 왜 판단했는지가 남는다** |
| **비용은 얼마나 드나** | KIPRIS 무료 월 1,000회 안에서 동작하도록 설계했다. 검색 7일·상세 90일·추출 30일 캐시가 있어 재검사는 **0회**다. 분석 시작을 45초 미뤄 한 번의 편집이 여러 분석을 부르는 것도 막는다 |
| **특허 검색 정확도는** | KIPRIS 가 **청구항을 주지 않는다.** 초록만으로는 권리범위를 알 수 없어 최상위 등급을 매기지 않는다. 이 한계를 감추지 않고 불확실성으로 표시하며, **검토 우선순위 제시**에 집중한다 |
| **왜 RAG corpus 가 3건뿐인가** | 판정은 규칙 엔진이 하고 RAG 는 설명의 출처만 담당하므로 범위가 좁다. 커버리지 밖이면 **틀린 근거를 붙이는 대신 근거 없음**을 택한다. 확장이 고도화 1순위다 |
| **확장 가능한가** | Plane 경계가 계약으로 고정되어 있어 분석기를 추가해도 Control 과 Source 는 바뀌지 않는다. Cloud Run 은 요청 기반으로 늘어난다 |
| **테스트는 충분한가** | 수보다 **어떤 테스트인가**가 중요하다는 것을 배웠다. 모의로는 안 드러난 결함이 여러 건 있었고, 그래서 실호출 테스트를 분리 운영하고 배포 실측을 별도 단계로 뒀다 |

## 15.2 KPT 회고

**Keep**
* 세 축의 **디렉터리 단위 소유권 분리**와 동결 계약. 병렬 개발에서 backend 코드 충돌 0건.
* 모의와 실호출 테스트 분리. 이것이 없었으면 결함들이 시연 중에 드러났을 것이다.
* 결함을 고칠 때 **그 결함을 잡는 시험을 함께** 넣고, 수정을 되돌려 실패하는지 확인한 것.
* "실패를 성공으로 위장하지 않는다" 를 원칙으로 세우고 세 축 모두에서 지킨 것.

**Problem**
* 계약에 선언만 하고 구현이 빠져도 시험이 통과했다. Protocol 은 실행 중에 검사되지 않는다.
* 재검사·다중 마운트처럼 **한 번도 눌러 보지 않은 경로**에 결함이 몰려 있었다.
* 초안 문서가 통합 이전 상태로 남아 실제와 어긋났다. 문서 갱신이 구현을 못 따라갔다.
* 사용자 테스트를 하지 못했다.

**Try**
* 계약을 만들 때 **운영 구현이 그 계약을 만족하는지 검사하는 시험을 같은 커밋에** 넣는다.
* 기능을 만들면 **사람이 실제로 가는 동선에서** 한 번 눌러 본다. 기능이 있는 것과 닿을 수 있는 것은 다르다.
* 문서에 "이 시점의 상태" 를 적고, 상태가 바뀌면 문서도 같은 커밋에서 고친다.

## 15.3 프로젝트 레슨런

**통과하는 테스트는 실행된 적 없는 경로를 지켜주지 않는다.** 이번에 찾은 결함
대부분이 그 자리에 있었다. 재검사, 두 번째 저장소 마운트, 하위 폴더 파일, 설명기
배선 — 전부 시험이 통과하는 상태였고 배포에서 처음 눌렀을 때 드러났다.

**대역은 우리가 아는 것만 재현한다.** KIPRIS 응답 필드명이 문서와 달랐는데, 대역을
문서 보고 만들었으니 대역도 같이 틀렸다. 외부 경계에서는 실호출 검증이 대체 불가능하다.

**환각은 프롬프트가 아니라 구조로 막는 것이 확실하다.** "지어내지 마세요" 는
확률을 낮출 뿐이다. 인용문이 본문에 실재하는지 코드가 대조하면 지어낸 것은 화면까지
오지 못한다.

**모르는 것을 아는 척하지 않는 편이 낫다.** RAG 가 관련 없는 문서를 근거로 붙이면
근거 ID 검증도 통과하고 그럴듯해 보인다. 근거가 없는 것보다 **틀린 근거가 나쁘다**는
판단으로 근거 없음을 택했다.

**실패의 뜻을 나누면 사용자가 할 일이 달라진다.** 한도 소진·판본 추월·미판정을 전부
"실패" 로 보여주면 사용자는 매번 같은 대응을 시도한다. 코드로 구분하고 문구를 나누자
"기다리면 되는 것" 과 "손봐야 하는 것" 이 갈렸다.

**다른 구현을 대조하는 것이 값싼 검증이었다.** 같은 요구사항을 따로 구현한 v1 이
운영에서 겪은 증상을 커밋에 남겨 두었고, 그것을 v3 와 맞대 잠재 문제를 미리 찾았다.

## 16.1 README 재현 절차

저장소를 clone 한 뒤 **CPython 3.14.7** 과 **Node.js 24.19.0 / pnpm 11.19.0** 을
설치하고, 가상환경에서 `pip install -e ".[dev]"`, `pnpm install --frozen-lockfile`

`-m live` 로 **따로** 돌린다.

환경변수는 `.env.example` 의 **이름을 그대로** 쓰되 실제 값은 기록하지 않는다.
배포 환경의 값은 Secret Manager 에서 주입된다.

## 17.1 미확인 항목 또는 제출 비고

* **사용자 테스트 미수행** — 개발 기간을 실측 검증에 썼다. 팀 내부 실사용 관찰에서
  나온 개선은 SECTION 13 에 반영했다. 제출 후 3인 이상으로 수행할 계획이다.
* **자동 E2E 테스트 없음** — `tests/e2e` 는 디렉터리만 있고 비어 있다. 대신
  `samples/PATENT_E2E_SCENARIO.md` 등 **사람이 배포 환경에서 수행하는 시나리오**로
  대체했고, 그 결과가 SECTION 12 의 TC 표다. 자동화가 아니므로 회귀를 매번 잡지는
  못한다는 점을 그대로 밝힌다.
* **Local·Desktop 실측 미완** — 구현과 단위 테스트(70건)는 완료했으나 배포 환경
  실측이 남았다. Drive·GitHub 은 완료했다.
* **다이어그램 삽입** — 7종을 별도로 준비 중이며 삽입 후 SECTION 05·06·08·11 이
  완결된다.
* **테스트 수치·리비전·URL** — 제출 직전에 다시 세어 맞춘다.
