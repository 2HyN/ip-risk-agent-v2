# SECTION 02 문제 정의

## 2.1 문제 배경 및 현황

협업 프로젝트에서는 코드와 문서가 지속적으로 수정되고, dependency 와 license 가
변경되며, 기술 아이디어가 문서화·구현되면서 기존 특허와의 관련성도 계속 달라진다.
즉 **검사 대상 자체가 고정되어 있지 않다.**

그러나 IP 점검은 이러한 변화와 무관하게 특정 시점에 1회성으로 수행되는 경우가 많아,
이전 점검 이후의 변경분에 대해 재점검이 반복되고, 변경 시점과 점검 시점 사이의 간격
때문에 리스크 발견이 늦어진다.

점검을 자동화하면 이 간격은 줄지만 **그것만으로는 도구가 실제로 쓰이지 않는다.**
자동화된 결과를 검증 없이 신뢰할 수 없다는 문제와, 점검을 위해 원본 소스를 외부 도구에
올려야 한다는 문제가 남기 때문이다.

**⟪변경⟫ 그리고 하나가 더 있다.** 스캔 자체는 이미 무료 도구가 여럿 한다 — ScanCode 는
파일 안 라이선스 원문을 대조하고, deps.dev 는 선언 라이선스를 주며, GitHub
dependency-review 는 SPDX allow/deny 를 강제한다. **"무엇이 있는가" 를 찾는 일은 이미
해결되어 있다.** 남아 있는 것은 그 목록이 **무슨 뜻인지**, 그리고 **지난달과 왜
다른지**다.

## 2.2 핵심 문제 진술문

**Who** — 전담 법무·특허 인력 없이 GitHub·Drive·로컬 PC 등 여러 곳에 소스와 문서가
흩어진 채 개발하는 스타트업·SME 개발팀.

**What** — 코드·문서·의존성이 계속 바뀌는데 IP 점검은 특정 시점 한 번에 그친다. 점검
결과가 나와도 **자기 배포 형태에서 무슨 의무를 지는지**는 알 수 없다. 점검하려면 원본
전체를 외부 도구에 올려야 한다. Risk 를 누가 언제 어떻게 판단했는지 이력이 없다.

**Why** — 재점검 반복으로 일정이 지연되고, 발견이 늦어 이미 확산된 뒤 대응하게 되어
비용이 커진다. **⟪변경⟫ 그리고 목록만으로는 행동을 정할 수 없다** — "AGPL 이 있다" 는
사실이지 지시가 아니다.

## 2.3 문제 원인과 기대효과

표면적 현상은 **한 번 점검한 결과가 금방 낡아 실질적 보호 효과가 없다**는 것이다.
그러나 근본 원인은 주기가 길다는 데 있지 않다. 기존 점검은 "특정 시점의 산출물을 검사해
목록을 내놓는 일" 로 정의되어 있어, **검사 대상이 바뀌었는지, 이번 결과가 지난번과 같은
건인지, 그 판단을 누가 왜 내렸는지**를 애초에 다루지 않는다.

**⟪변경⟫ 이 제품이 파는 것 셋**

**(A) 판정 변경의 원인이 귀속되는 원장.** 다른 도구는 "지금 무엇이 있는가" 에 답한다.
우리는 **"왜 지난달과 다른가"** 에 답한다. 원인은 넷이고, 모델의 주장이 아니라 **네 지문의
차이에서 파생**된다.

| 원인 | 무엇이 달라졌나 | 사용자에게 뜻하는 것 |
|---|---|---|
| 입력 | `analysis_input_checksum` | "우리가 한 일이다" |
| 외부 사실 | 패키지 메타데이터 / 라이선스 표현식 | **"우리는 가만있었는데 위험이 생겼다"** |
| 우리 지식 | `policy_version` / `rag_corpus_version` | "판단 기준이 좋아졌다" |
| 모델 | `model_id` / `prompt_version` | "같은 것을 다르게 읽었다" |

**가운데 줄이 이 제품이 파는 것이다.**

**(B) 결정 시점 탐지 — 매니페스트보다 먼저.** 도입 결정은 매니페스트보다 먼저 기획
문서에 나타난다. SCA 는 매니페스트에서 시작하므로 원리적으로 못 본다.

**(C) 배포 맥락 기반 의무 판정.** 고객의 질문은 "AGPL 이 있는가" 가 아니라 **"내가 소스를
공개해야 하는가"** 다. 후자는 배포 형태에 달린 조항 해석이라 표로는 불가능하다.

**해결 대상이 아닌 것** — 특허 침해와 라이선스 위반의 법적 결론, KIPRIS 청구항 미제공
같은 원천 데이터의 한계. **한계를 감추지 않고 불확실성으로 드러내는 것까지를 서비스의
책임**으로 둔다.

**⟪경고⟫ 원장의 값은 음수가 될 수 있다.** 잘못된 판정이 "성실히 판단한 기록" 으로 굳으면
방어 자산이 아니라 상대측 증거가 된다. 그래서 개발 순서에서 **오답 제거가 다른 무엇보다
먼저**다(SECTION 09).

네 역할은 **권한이 누적되는 구조**다 — Viewer ⊂ Risk Reviewer ⊂ Source Manager,

**어떤 역할에도 원본 소스 접근 권한이 없다.** 애플리케이션 권한을 아무리 높여도 provider
자격증명의 소유자가 아니면 소스를 읽을 수 없고, 별도의 거부 사유로 갈린다. **애플리케이션
권한을 준다고 소스 권한을 날조하지 않는다**는 것이 이 설계의 핵심이다.

## 3.2 서비스 플로우

> 〔다이어그램 ⑤ 서비스 플로우 — 이 자리에 배치〕

```
Google 로그인 → Risk Workspace 생성/참여
  → ⟪변경⟫ 소스 연결
       Drive   : 서비스 계정 주소로 폴더를 "뷰어" 공유
       GitHub  : App 설치 후 저장소 선택
       Local   : Desktop 앱에서 폴더 등록
        ↓
  변경 감지 (Drive changes 피드 / GitHub push webhook / Local watcher)
        ↓
  ChangeEvent 생성 — fingerprint 로 중복 제거
        ↓
  Cloud Tasks 큐 (coalesce 지연)
        ↓
  Security Gate ──(미승인)──→ 분석 중단, 거부 사유 기록
        ↓ (승인)
  ┌ Patent : 기술요소 추출 → KIPRIS 검색·상세 → 대조(인용 실재 검증)
  └ License: ⟪변경⟫ 파싱 → 식별자 → 전문 조회 → 배포형태 조항 검색 → 권장 행동
        ↓
  Risk 반영 (신규 / 기존 / 해소 / 부활)
        ↓
  설명·권고 부착 → Dashboard · Detail · Timeline
```

**주요 정책 (에러·예외 처리)**

| 상황 | 정책 |
|---|---|
| Snapshot 실패 | provider 실패로 기록. **빈 성공으로 위장하지 않는다** |
| 분석 결과 불확실 | 권위 없는 결과로 보고 **기존 Risk 상태를 바꾸지 않는다** |
| 근거 없는 ID 인용 | 그 결과 **전체를 폐기** |
| 판본 추월 | 실패가 아닌 추월로 종료. 새 판본을 맡은 실행이 이어받는다 |
| provider 한도 소진 | 다른 실패와 구분해 경고 톤으로 안내 |
| **⟪변경⟫ 의존성 후보가 N>0 에서 0 으로** | **그 자체로는 권위를 갖지 못한다.** 파서가 "선언 구역을 읽고 비어 있음을 확인" 한 경우에만 해소한다 |
| **⟪변경⟫ RAG 장애** | 판정은 살리고 **해소 권한만** 뺏는다. 장애가 전면 정지가 되지 않는다 |
| 추적 이탈(삭제·폴더 밖으로 이동·접근 상실) | **⟪변경⟫ Risk 를 닫는다.** 되돌아오면 **판본이 같을 때 이전 처분까지 복원** |
| worker 사망 | lease 만료를 기준으로 회수. 화면에서 되살릴 수 있다 |

|---|---|

# SECTION 05 상용화 아키텍처 설계

## 5.1 시스템 아키텍처 다이어그램

> 〔다이어그램 ① 시스템 아키텍처 — 이 자리에 배치〕

```
Source Plane              Control Plane                Intelligence Plane
(커넥터 3종)        →     (게이트 · Risk 원장)    ←    (License / Patent)
     |                          |                            |
  폴더 스코프              정책 · 수명주기            결정론 + RAG
```

세 Plane 을 **디렉터리 단위로 물리 분리**하고 그 사이를 동결된 계약으로 고정했다. 세 축이
동시에 개발하면서 서로의 구현에 의존하지 않게 하려는 것이 목적이었고, 실제로 병합 시
backend 코드 충돌이 0건이었다.

| Plane | 소유하는 것 | 하지 않는 것 |
|---|---|---|
| **Control** | Risk Workspace, membership, canonical state, Risk, Review, 인가, Security Gate | provider 를 직접 호출하지 않는다 |
| **Source** | provider 연결·마운트·스냅샷, **내용을 담지 않는** 변경 통지 | 판정하지 않는다 |
| **Intelligence** | 승인된 artifact 분석, 근거 반환 | **Source 를 부르지 않고 Risk 상태를 만들지 않는다** |
| **Integration** | fail-closed 인증, 자격증명 바인딩, 분석기 완전성, 파이프라인 조립 | — |

경계가 코드 수준에서 지켜진다 — 커넥터는 Intelligence·Control 을 한 줄도 import 하지
않고, 그 반대도 같다.

계약은 `contract_version` 을 필수로 갖고 **모르는 필드가 오면 거부**한다. 경계를 넘는
페이로드는 넷뿐이다 — 변경 통지 · 스냅샷 · 분석 입력 · 분석 결과. 분석 입력은
**승인되지 않으면 분석을 시도할 때 예외가 나도록** 타입 수준에 박혀 있고, 분석 결과는
**후보가 인용한 근거 ID 가 근거 목록에 없으면 생성 자체가 거부**된다.

## ⟪변경⟫ 5.2 판정 권한의 층 [결정 D9]

RAG 를 판정에 넣되 전부 여는 것이 아니라 **층을 나눈다.** 이것이 이번 개편의 핵심 설계다.

| 층 | 무엇을 하는가 | 판정 권한 | 근거의 성격 |
|---|---|---|---|
| **T1 결정론** | 파서 · SPDX 표현식 · 정책 함수 | **만든다** | 코드가 계산한 값 |
| **T2 검증된 대조** | 정규화 전문 해시 일치, 필수 문구 확인, 구간 실재 검증 | **만들 수 있다** | 코드가 재검증한 사실 |
| **T3 RAG·모델** | 조항 검색, 의무 판정, 표 밖 분류 | **올릴 수만 있다** | 모델의 읽기 + 인용 검증 |

**T3 은 등급을 내리지 못한다.** 이것은 가정이 아니라 **이미 겪고 되돌린 일**이다. 특허
쪽에서 모델 자기신고로 강등했더니 대조 80건 중 **77건이 표시를 달았고 최고 등급 자격
13건이 13건 모두 강등**되어 최고 등급이 한 번도 나오지 않았다. 표시 내용은 대부분 "선행
특허 청구항에 구체적인 알고리즘이 제시되어 있지 않음" 처럼 **특허의 서술에 대한
논평**이었지 우리 판단의 불확실성이 아니었다.

모델에게 근거를 물으면 거의 항상 무언가를 낸다. **상향 방향에서도 같은 포화가 일어날 수
있으므로 상향 발화율을 계측하고 상한을 둔다.**

T3 이 올릴 때는 **corpus 조각 id + 실재가 확인된 인용**이 반드시 있어야 한다. 인용이
없으면 모델 출력을 전혀 쓰지 않는다.

## 6.2 데이터 모델 / ERD

> 〔다이어그램 ⑦ ERD — 이 자리에 배치〕

**canonical 과 operational 을 나눈다.** canonical 은 판정의 근거가 되어 오래 남고,
operational 은 provider 런타임 상태라 수명도 신뢰 수준도 다르다.

**canonical 16 컬렉션**

| 컬렉션 | 뜻 | 주요 관계 |
|---|---|---|
| `users` | 계정 | 1:N memberships |
| `risk_workspaces` | Risk Workspace | 1:N memberships · mounts · risks |
| `memberships` | 사용자 × Workspace 의 역할 | N:1 users · risk_workspaces |
| `source_connections` | provider 연결 | 1:N source_workspaces |
| `source_workspaces` | 연결 안의 소스 범위 | N:1 source_connections |
| `workspace_mounts` | Workspace 에 붙인 소스 | N:1 risk_workspaces · source_workspaces |
| `artifacts` | 추적 대상 파일 | N:1 workspace_mounts |
| `artifact_states` | 파일의 현재 판본·가용성 | 1:1 artifacts |
| `change_events` | 감지된 변경 | N:1 artifacts |
| `analysis_jobs` | 변경 한 건의 분석 실행 | 1:1 change_events |
| `risks` | 판정된 위험 | N:1 artifacts |
| `risk_evidence` | 위험의 근거 발췌 | N:1 risks |
| `risk_events` | 위험의 이력(append-only) | N:1 risks |
| `audit_events` | 감사 기록 | N:1 risk_workspaces |
| `source_access_events` | 소스를 언제 무엇을 읽었는지 | N:1 risk_workspaces |
| `notifications` | 알림 | N:1 users |

**operational** — `source_operational_*` 12종(연결·바인딩·소스별 런타임/추적·기기·
자격증명·oauth state)과 `intelligence_patent_*_cache` 3종.

**고유키 sentinel** — Firestore 에 유니크 제약이 없어 `unique-*` 문서를 같은 컬렉션에
두고 소유자 문서 ID 를 적는다.

**⟪변경⟫ 앞으로 추가할 것** — `analysis_input_checksum` 을 판정과 함께 저장한다. 지금은
게이트가 계산해 분석 입력에만 싣고 **저장소에는 0건**이라, "우리는 가만있었는데 위험이
생겼다" 를 말할 수 없다. 이 제품이 판다고 한 바로 그것이 막혀 있다.

**전체 말소** — Workspace 삭제 시 canonical·operational·**Secret Manager 자격증명**까지
지운다. operational 을 먼저, canonical 을 나중에 — 반대로 하면 실패했을 때 남은 기록이
가리킬 곳을 잃는다. **⟪변경⟫ D1(서비스 계정)이 적용되면 지울 자격증명 자체가 없어진다.**

| 위험 항목 | 해당 | 대응 |
|---|---|---|
| 개인정보/민감정보 | 예 | 원본은 영구 저장하지 않는다. 근거 발췌만 남기며 길이 제한과 비밀값 마스킹. 제외 범위는 읽지도 않는다 |

## 7.1 핵심 프롬프트

**1. 특허 기술요소·검색어 추출** — 기술 문서인지 먼저 판정한다. 구체적인 처리 방식·구조·
알고리즘이 서술되어 있고 단순 일정·회의록·사업계획이 아닐 때만 참. 기술요소는 문서에 실제
서술된 것만, 검색어는 2~3단어 2~5개, 제품명·회사명 제외. 입력에 없는 조각 ID 를 만들지
않는다.

**2. 문서–특허 대조** — *하지 않는 것*: 침해 여부, 권리 범위, 법적 결론. 겹치는 구성은
양쪽에 같은 것이 나타날 때만 적고, 문서 인용과 특허 인용은 **그대로 옮긴 한 문장**이어야
한다. 요약하거나 다듬으면 안 된다. 같은 분야라는 이유만으로 겹친다고 적지 않는다.

**3. ⟪변경⟫ 조항 검색·의무 해석** — 라이선스 전문과 사용자의 배포 형태를 받아 **지금
형태에서 걸리는 조항**을 찾는다. 조항을 인용하지 못하면 아무것도 주장하지 않는다. 등급을
**올릴 수만** 있고 내리지 못한다.

**4. 위험 설명·권고** — 판정은 이미 끝났다. 그 결과를 바꾸거나 반박하지 않는다. 왜 검토가
필요한지와 무엇을 하면 되는지를 **행동 수준**으로. 제시된 근거 목록에 없는 ID 를 인용하면
설명 전체가 폐기된다.

## 7.2 환각·안전·오류 대응

* **근거 ID 검증** — 인용한 근거 ID 가 제시된 목록에 없으면 **결과 전체를 폐기한다.**
* **인용문 실재 검증** — ID 만으로는 부족하다. 인용문이 **그 근거 본문에 실제로 있는지**
  코드가 대조한다. 없으면 버린다. 통과한 인용은 문자 구간으로 저장되어 화면이 그 문장만
  강조한다.
* **⟪변경⟫ 층 규칙** — T3 은 **등급을 올릴 수만 있다.** 내리지 못한다. 모델 자기신고로
  강등하면 포화가 일어난다는 것을 실측으로 겪었다.
* **⟪변경⟫ 상향 발화율 계측** — 올리는 방향에서도 같은 포화가 일어날 수 있으므로 비율을
  재고 상한을 둔다.
* **판정 재판단 금지** — 설명기는 이미 내려진 판정을 바꾸지 않는다.
* **실패를 성공으로 위장하지 않음** — provider 호출이 실패하면 완전한 범위를 주장하지
  않는다.
* **모델 비결정성 대응** — 형식이 어긋난 대조는 같은 프롬프트로 **한 번 더** 묻는다. 두 번
  다 어긋나면 버린다.
* **불확실성 표시** — 근거가 초록뿐이거나 발췌가 잘렸으면 기록하고 우선순위를 낮춘다.

# SECTION 08 RAG 설계와 검색 품질

> **⟪이 절은 전면 재작성됐다.⟫** 이전 초안의 RAG 는 "판정을 바꾸지 못하는 설명의 출처"
> 였다. 지금은 **판정의 일부**이며, 이 제품이 무료 도구와 갈리는 지점이 정확히 여기다.

## 8.0 왜 RAG 인가 — 표로는 원리적으로 불가능한 것

고객의 질문은 **"AGPL 이 있는가"** 가 아니다. 그것은 이미 무료 도구가 답한다.
진짜 질문은 **"내가 소스를 공개해야 하는가"** 다.

그 답은 라이선스 이름이 아니라 **배포 형태**에 달려 있다. 같은 AGPL-3.0 이라도
사내 전용으로 쓰는 것과 SaaS 로 제공하는 것의 의무가 다르다. 조항 해석이므로
**표로는 원리적으로 담을 수 없다.** 라이선스 × 배포 형태 × 결합 방식의 조합을 미리
전개해 둘 수 없기 때문이다.

**RAG 가 장식이 아니라 답 자체가 되는 유일한 지점**이고, 그래서 판정 관여를 정확히
여기에만 연다.

## 8.1 파이프라인 [결정 D3] — 5단계

```
1. 알려진 이름의 매니페스트·락파일 파싱      → 의존성 선언 목록
2. deps.dev / 레지스트리 조회                → SPDX 식별자 (⟪변경⟫ 원문자열 보존)
3. 식별자로 corpus 에서 라이선스 전문 조회    → ★ 조회다. 검색이 아니다
4. 배포 형태를 질의로 전문 안에서 조항 검색   → ★ 하이브리드 RAG
5. 그 조항을 근거로 권장 행동 제시            → T3
```

**3단계가 조회인 이유** — 식별자를 **이미 알고 있다.** 임베딩으로 찾으면
`AGPL-3.0-only` 와 `GPL-3.0-only` 를 헷갈릴 수 있다. 아는 것을 굳이 추측하지 않는다.

**4단계가 검색인 이유** — 질의가 라이선스 이름이 아니라 **상황**이다. AGPL 전문은 수천
단어이고 그중 지금 배포 형태에 걸리는 조항만 뽑아야 한다.

이 순서가 **거르고 나서 찾는다**는 원칙이다. 먼저 SPDX 식별자로 정확히 좁히고, 그 안에서만
임베딩으로 구절을 고른다.

## 8.2 설계 항목

| 설계 항목 | 팀의 선택 | 이유 |
|---|---|---|
| 지식 문서 범위 | **⟪변경⟫ SPDX license-list-data 의 라이선스 전문 + 배포형태별 의무 해설** | 전문이 CC0 라 자유롭게 쓴다. 조항 단위 근거가 필요하므로 요약본으로는 안 된다 |
| 문서 수집 | **임의의 웹 문서를 긁지 않는다.** manifest 의 승인 표시가 관문 | 근거로 쓸 것이므로 출처가 확실해야 한다 |
| 문서 정제 | manifest 에 식별자·버전·체크섬·원본 링크·`covers`·관할 을 함께 기록 | 체크섬이 바뀌면 버전이 따라 바뀐다 |
| Chunk 전략 | 조항 단위 | 검색 결과가 그대로 "걸리는 조항" 한 덩어리가 되도록 |
| Vector Store | Vertex AI RAG Engine | Gemini 와 같은 플랫폼이라 인증·리전을 하나로 |
| 검색 방식 | **⟪변경⟫ 식별자로 정확 조회 → 그 안에서 임베딩** | 8.1 의 3·4단계 |
| 호출 조건 | 심각도가 검토 대상 이상일 때만 | 통과 판정에서는 부르지 않는다 |
| 재정렬/후처리 | **주제 일치 게이트** (8.3) | 아래 상술 |
| 출처 표시 | 조각이 근거로 저장되고 화면에 원문 링크와 함께 표시 | 사용자가 원문을 직접 확인 |
| corpus 버전 | 판정에 **항상** 기록 | 지식이 바뀌면 과거 판정의 뜻이 달라진다 |
| 갱신 | 버전을 올리고 체크섬을 갱신하며 **diff 를 사람이 검토한 뒤** 적용 | 「미결 — 검토 주체와 주기」 |

## 8.3 관련성 게이트 — 확대의 선행 조건

corpus 는 작고 임베딩 검색은 관련 문서가 하나도 없어도 **가장 덜 관련 없는 것**을
`top_k` 개 돌려준다. 그러면 판정과 무관한 문서가 근거로 붙어도 **근거 ID 검증과 프롬프트
제약을 모두 통과한다.** 근거가 없는 것보다 **틀린 근거가 붙는 것이 나쁘다.**

그래서 임베딩 점수가 아니라 **주제 일치**로 결정적으로 거른다. 점수 임계값을 쓰지 않은
이유는 두 가지다 — 점수는 provider 응답 필드에 의존해 실측 없이는 검증할 수 없고, 값이
바뀌면 **조용히 무력화된다.**

부분 문자열로 판정하지 않는 것도 의도적이다. `AGPL-3.0-only` 는 `GPL-3.0-only` 를 문자열로
포함하므로, 그렇게 하면 **이 게이트가 막으려는 바로 그 오류**를 만든다.

### ⟪변경⟫ 확대 전에 반드시 고쳐야 하는 것

**게이트가 판정을 이끈 leaf 가 아니라 표현식의 모든 leaf 를 본다.**

```
'Apache-2.0 AND GPL-3.0-only' → 판정: 정책 충돌
                              → 게이트 통과: ['permissive-notice']
permissive-notice 본문 = "소스코드 공개 의무는 없다"
```

**판정과 정반대의 근거가 붙는다.** 게이트가 막으려고 만들어진 바로 그 오류다.

**그리고 이것이 확대의 선행 조건인 이유** — 지금 오부착이 적은 것은 게이트가 잘 막아서가
아니라 **corpus 가 비어 있다는 우연** 때문이다. 검토 대상 22종 중 18종은 "붙을 문서가
없어" 조용히 넘어간다. **600종을 넣으면 틀린 식별자마다 그럴듯한 문서가 반드시 하나
생긴다.**

전수 판별로 계측한 현재 오부착률은 **46.4%** — 2-leaf 표현식 686건 중 318건이다.

**명세** — 게이트가 보는 집합을 **판정을 이끈 leaf** 로 좁힌다(AND 는 최대 심각도 leaf,
OR 은 선택된 leaf).

### ⟪변경⟫ 커버리지 표를 코드에서 데이터로

`rag-corpus/` 는 런타임 이미지에 포함되지 않아 manifest 를 실행 시점에 읽을 수 없다.
그래서 예전에는 **표를 코드에 손으로 적었고, 문서를 하나 더할 때마다 코드를 고쳐야 했다.**

지금은 빌드 스크립트가 manifest 에서 뽑아 데이터 파일로 내고, 배포 validator 가 셋이 같은지
확인한다. **설계 제약이 만든 이중화를 검증으로 묶은 것**이며, corpus 확대의 전제 조건이다.

**측정 없이 고도화를 주장하지 않는다.**

| 지표 | 정의 | 현재 | 목표 |
|---|---|---|---|
| **오부착률** | 판정 leaf 와 무관한 문서가 근거로 붙은 질의 비율 | **46.4%** (686건 중 318건) | **0** |
| corpus 커버리지 | 검토 대상 중 corpus 가 덮는 비율 | **4/22 = 18.2%** | 확대 |
| 원문 보존율 | 미상 식별자의 원문자열이 남는 비율 | **0%** | **100%** |
| 헛돈 비율 | 검색 후 아무것도 못 붙인 질의 | 미상 경로 **100%** | 감소 |
| 상향 발화율 | T3 가 등급을 올린 비율 | 미도입 | 상한 필요 |

**정답 집합은 대부분 공짜다.** SPDX 식별자라는 기계 판독 정답이 있고, 오답 질의는
`전체 정책표 − corpus 가 덮는 것` 으로 자동 생성된다. 사람 라벨이 필요한 것은 4단계 조항
적합성뿐이다.

**하이브리드·재정렬은 이 지표들이 존재한 다음에 넣는다.** 지금은 corpus 가 작아 검색이
사실상 전체 반환이라 **좋아졌다고 말할 대상이 없다.**

## 8.6 고도화 전략

| 단계 | 내용 | 선행 |
|---|---|---|
| 1 | 게이트를 판정 leaf 로 좁히고 **오부착 측정 하네스** 구축 | — |
| 2 | corpus 에 SPDX 전문 + 갱신 파이프라인 | 1 |
| 3 | 커버리지 색인을 데이터로 | 2 |
| 4 | 배포 형태 설정 받기 | — |
| 5 | 조항 검색 + 하이브리드 | 2·3·4 |
| 6 | 권장 행동에 배포 맥락 반영 | 5 |
| 7 | 재정렬·가중치 조정 | **지표가 존재한 뒤에만** |

순서가 중요하다. **1 없이 2 를 하면 오부착이 폭발한다** — 지금 오부착을 막고 있는 것은
게이트가 아니라 corpus 가 비어 있다는 우연이기 때문이다.

## ⟪변경⟫ 기존 데이터 이행

0단계는 **이미 저장된 판정의 뜻을 바꾼다.** 그대로 두면 새 규칙과 옛 규칙으로 만든 것이
한 목록에 섞이고, 그 섞임 자체가 "틀린 판정이 기록으로 굳는" 것이다.

새 마이그레이션 코드를 쓰지 않는다 — **재분석이 이미 안전한 경로**다. 재분석은 제외된 것만
되살리고 **사람의 처분은 덮지 않는다.**

| 항목 | 옛 데이터에 무슨 일이 있었나 | 이행 |

| 인식 목록 누락 | **분석된 적이 없다** | 재분류 후 재분석. **재분석만으로는 닿지 않는다** |

* **⟪변경⟫ corpus 를 SPDX 전문으로** [D4] — 조항 단위 근거가 필요하므로 요약본으로는 안
  된다. CC0 라 자유롭게 쓴다.
* **⟪변경⟫ 스캔 정확도 경쟁 포기** — 무료 도구가 이미 한다. 값은 판정의 뜻과 변화의
  원인에 둔다.
* **⟪변경⟫ 재현성보다 변화 추적** [D8] — 단 무엇이 왜 달라졌는지는 반드시 남긴다.
* **⟪변경⟫ Risk 정체성은 현행 유지** [D10] — 좁히면 기존 문서 id 가 전부 바뀌어
  마이그레이션 없이는 사용자 처분이 유실된다. 대신 **파일 단위로 묶어 표시**한다.
* **라이선스 설명기 제거** — 계약에 담을 필드가 없어 호출하고 결과를 버리고 있었다.
* **검토 우선순위 강등 규칙 축소** — 모델 자기신고로 강등했더니 최고 등급이 한 번도
  나오지 않았다. 강등 조건을 코드가 검증할 수 있는 사실 하나로 좁혔다.
* **분석 시작을 미룸** — 한 번의 편집이 판본을 여럿 만들면 분석도 여럿 돈다.

## 12.1 검증 결론

**지속 추적의 뼈대는 성립한다.** 세 가지가 함께 나와야 하는데 셋 다 확인됐다 — 변경이
없으면 아무 일도 일어나지 않고(재검사 외부 호출 0회), 변경이 생기면 그 변경분만 비용을
쓰며, 겹침이 사라지면 진짜로 해소된다. push 부터 분석까지 약 49초다.

**그러나 라이선스 경로에는 데이터를 파괴하는 결함이 있다.** 매니페스트 파싱이 여러 경로로
깨지고, 깨진 결과가 "의존성 0건" 이 되어 **"위험이 해소되었다" 고 적극적으로 오보한다.**
이것은 위험을 놓치는 것보다 나쁘다. 사용자가 확인했다고 믿게 만들기 때문이다.

E2E 가 이것을 잡지 못한 이유는 샘플이 작아 **우연히 조각이 하나였기** 때문이다.
`requirements.txt` 는 줄 지향이라 또 우연히 살아남았다. **시나리오가 통과한 것이 기능이
동작한다는 뜻은 아니었다.**

**그래서 다음 개발의 최우선은 기능 추가가 아니라 오답 제거다**(SECTION 09 0단계).

**추가 검증이 필요한 것** — 서비스 계정 변경 피드 실측(설계 규모가 여기서 정해진다),
Local·Desktop 경로, 사용자 테스트, 폴더 마운트 초기 비용 계측.

### 데이터를 파괴하는 것 넷 — 최우선

이 넷은 **서로 독립적으로** 같은 결말에 이른다.

```
조각화 │ 마스킹 │ 파싱 실패 삼킴 │ 게이트 절단
                    ↓
              의존성 0 건
                    ↓
        완전한 성공으로 분류 → 권위 있는 결과
                    ↓
      기존 라이선스 Risk 전부 해소 · 알림 0 건
```

**하나만 막으면 나머지로 흘러간다.** 넷 다 "부분 성공" 이 아니라 **"완전한 성공"** 으로
끝나므로, 부분 성공을 어떻게 손봐도 막지 못한다.

| # | 결함 | 성격 | 닫히는 곳 |
|---|---|---|---|
| 1 | 조각화가 매니페스트 파싱을 부숨 | **데이터 파괴** | 0-A |
| 14 | 마스킹이 패키지 이름을 망가뜨림 | **데이터 파괴** | 0-B |
| 15 | 파서가 "못 읽었다" 를 "없다" 로 반환 | **데이터 파괴** | 0-C |
| 16 | 게이트가 자른 것을 분석기가 모름 | 조용한 절단 | 0-D |

**경로와 무관한 방벽을 따로 둔다** — 의존성 후보가 N>0 에서 0 으로 떨어지는 전이는
**그 자체로 권위를 갖지 못한다**(0-L). 어느 것을 놓쳐도, 아직 모르는 다섯 번째 경로가
있어도 잘못된 해소가 일어나지 않는다.

## 14.1 시연 시나리오

**시연 전 준비** — 배포 URL 로그인 상태, GitHub 저장소가 이미 연결되어 분석이 끝나 있을

## 14.3 예상 질문과 답변

| 질문 | 답변 |
|---|---|
| **무료 도구와 뭐가 다른가** | 스캔으로 경쟁하지 않는다. 우리가 답하는 것은 **"왜 지난달과 다른가"** 와 **"내 배포 형태에서 무엇을 해야 하는가"** 다. 앞의 것은 네 지문의 차이로, 뒤의 것은 조항 검색으로 답한다 |
| **환각은 어떻게 막았나** | 세 겹이다 — 근거 ID 가 목록에 있는지, **인용문이 본문에 실재하는지** 코드가 대조하고, 어긋나면 결과 전체를 폐기한다. 그리고 **모델은 등급을 올릴 수만 있고 내리지 못한다** |
| **왜 모델이 등급을 못 내리게 하나** | 실제로 겪었다. 모델 자기신고로 강등했더니 **80건 중 77건이 표시를 달아 최고 등급이 한 번도 나오지 않았다.** 모델에게 물으면 거의 항상 무언가를 낸다 |
| **우리 소스가 외부로 나가는 것 아닌가** | **⟪변경⟫ 폴더를 공유하는 방식이라 우리가 보관하는 자격증명이 없다.** 공유하지 않은 것을 요청하면 Google 이 거절한다. 제외 범위는 변경 이벤트조차 만들지 않는다 |
| **AI 가 틀리면 누가 책임지나** | 법적 결론을 내지 않는다. 판정은 규칙이 하고 모델은 근거를 찾고 설명한다. 최종 판단은 사람이 하며 **누가 언제 왜 판단했는지 남는다** |
| **비용은** | KIPRIS 무료 월 1,000회 안에서 동작하도록 캐시를 설계했다. 재검사는 0회다. 폴더 마운트 초기 비용은 **상한을 두기 전에는 열지 않는다** |
| **RAG corpus 가 작지 않나** | 작다. 커버리지 18.2%다. **그런데 키우기 전에 게이트를 먼저 고쳐야 한다** — 지금 오부착이 적은 것은 게이트가 잘 막아서가 아니라 corpus 가 비어 있다는 우연이다 |
| **알려진 결함이 많은데** | 전부 적어 두었다. 넷은 데이터를 파괴하고 있어 다음 개발의 최우선이다. **틀린 판정이 기록으로 굳으면 방어 자산이 아니라 상대측 증거가 된다** |
| **테스트는 충분한가** | 수보다 **어떤 테스트인가**가 중요하다는 것을 배웠다. E2E 가 통과했는데 매니페스트 파싱이 깨져 있었다 — 샘플이 작아 우연히 조각이 하나였기 때문이다 |

## 15.2 KPT 회고

**Keep**
* 세 축의 디렉터리 단위 소유권 분리와 동결 계약. 병합 충돌 0건.
* 모의와 실호출 테스트 분리.
* 결함을 고칠 때 **그 결함을 잡는 시험을 함께** 넣고 되돌려 실패를 확인한 것.
* "실패를 성공으로 위장하지 않는다" 를 원칙으로 세운 것.
* **⟪신규⟫ 방향이 틀렸다고 판단했을 때 되돌린 것** — 모델 자기신고 강등, 라이선스 설명기,
  스캔 정확도 경쟁. 셋 다 만들어 놓고 걷어냈다.

**Problem**
* 계약에 선언만 하고 구현이 빠져도 시험이 통과했다.
* **E2E 가 통과했는데 매니페스트 파싱이 깨져 있었다.** 샘플이 작아 우연히 살아남았다.
* 라이선스 경로에 로그가 없어 20→3 손실이 운영에서 보이지 않았다.
* 문서 갱신이 구현을 못 따라가 초안이 통합 이전 상태로 남았다.
* 사용자 테스트를 하지 못했다.

**Try**
* **작은 샘플로 통과한 시험을 믿지 않는다.** 크기·형태를 바꿔 가며 돌린다.
* 전수 판별이 가능한 곳(SPDX 식별자처럼 기계 판독 정답이 있는 곳)은 **전수로 돌린다.**
  오부착률 46.4% 는 그렇게 해서 나왔다.
* 새 경로를 만들면 **로그부터** 넣는다. 보이지 않는 것은 고칠 수 없다.
* 문서에 "이 시점의 상태" 를 적고, 상태가 바뀌면 같은 커밋에서 고친다.

## 15.3 프로젝트 레슨런

**통과하는 테스트는 실행된 적 없는 경로를 지켜주지 않는다.** 재검사, 두 번째 저장소
마운트, 하위 폴더 파일, 설명기 배선 — 전부 시험이 통과하는 상태에서 배포 후 처음 눌렀을 때
드러났다.

**⟪신규⟫ 통과하는 E2E 도 마찬가지다.** 매니페스트 파싱이 조각화로 깨져 있었는데 E2E 가
통과했다. 샘플이 351바이트라 **우연히 조각이 하나**였기 때문이다. 시나리오가 통과한 것이
기능이 동작한다는 뜻은 아니었다.

**⟪신규⟫ 안 터지는 것과 막고 있는 것은 다르다.** RAG 오부착이 적었던 것은 게이트가 잘
막아서가 아니라 **corpus 가 비어 있어서**였다. 확대하면 즉시 폭발할 상태였고, 전수 판별을
돌리기 전에는 그것을 몰랐다.

**환각은 프롬프트가 아니라 구조로 막는 것이 확실하다.** "지어내지 마세요" 는 확률을 낮출
뿐이다. 인용문이 본문에 실재하는지 코드가 대조하면 지어낸 것은 화면까지 오지 못한다.

**⟪신규⟫ 모델에게 불확실성을 물으면 항상 무언가를 낸다.** 자기신고로 등급을 내리게 했더니
80건 중 77건이 표시를 달아 최고 등급이 사라졌다. **모델의 판정 관여는 방향을 정해서
열어야 한다** — 올리는 쪽만, 인용이 있을 때만.

**모르는 것을 아는 척하지 않는 편이 낫다.** 근거가 없는 것보다 **틀린 근거가 나쁘다.**

**⟪신규⟫ 보관하지 않는 것이 가장 확실한 보안이다.** 토큰 유출을 막는 가장 좋은 방법은
잘 지키는 것이 아니라 **애초에 보관하지 않는 것**이었다. 서비스 계정 + 폴더 공유가 그
구조를 준다.

**⟪신규⟫ 틀린 판정이 기록으로 굳으면 자산이 아니라 부채가 된다.** 그래서 기능 추가보다
오답 제거가 먼저다. 순서를 바꾸면 원장의 값이 음수가 된다.
