문서와 선행 특허를 대조해 겹치는 기술 구성을 찾는다.

## 하지 않는 것

침해 여부, 권리 범위, 법적 결론을 판단하지 않는다.
그것은 사람이 판단할 영역이며, 이 결과는 검토가 필요한 지점을 좁히는 데만 쓴다.

## matched_elements

**기술 요소 목록의 요소 하나하나에 대해**, 그 요소가 특허 근거의 어느 조각과
겹치는지 요소 단위로 따로 적는다.

- `element_index` 는 기술 요소 목록의 `[E숫자]` 에서 그 숫자다.
  목록에 없는 번호를 만들면 결과 전체가 폐기된다
- `source_segment_id` 는 입력 segment 목록에 있는 ID 여야 한다
- `patent_evidence_id` 는 제시된 특허 근거 목록에 있는 ID 여야 한다
- 목록에 없는 ID 를 만들면 결과 전체가 폐기된다
- `explanation` 은 어느 구성이 어떻게 겹치는지를 한두 문장으로 적는다
- `source_quote` 는 그 문서 segment 에서, `patent_quote` 는 그 특허 근거에서
  **겹치는 부분을 그대로 옮긴 한 문장**이다. 요약하거나 다듬지 않는다.
  본문에 없는 글자를 넣으면 결과 전체가 폐기된다. 옮길 만한 한 문장이 없으면 비워 둔다

같은 분야라는 이유만으로 겹친다고 적지 않는다. 처리 방식이 같아야 한다.

**한 요소가 여러 조각과 겹치면 항목을 여러 개 적는다. 여러 요소를 한 항목에
묶지 않는다.** 반대로 같은 요소·같은 조각 쌍을 표현만 바꿔 반복하지 않는다.

## distinct_elements

문서에만 있고 특허에는 없는 구성을 적는다.
겹치는 부분만 보면 사람이 판단할 수 없다. 다른 점도 함께 있어야 한다.

## review_caveats

검토자가 이 대조 결과를 읽을 때 **함께 알아야 할 한계**를 적는다.
없으면 비워 둔다. 억지로 채우지 않는다.

여기에 적는 것은 우선순위를 바꾸지 않는다. 사람이 읽을 참고사항이다.

적지 않는 것 — **특허 청구항이 구현 세부를 한정하지 않았다는 관찰.**
청구항이 상위 개념으로 쓰이는 것은 정상이고, 그것은 한계가 아니라 특허의 성질이다.
그런 내용은 `distinct_elements` 에 적는다.

## 입력

문서 segment

```
{segments}
```

기술 요소 목록

```
{elements}
```

특허 근거 — 각 조각의 머리에 근거 ID 와 (독립항 / 제N항의 종속항 / 초록) 구분이 있다

```
{patent_evidence}
```
