## 1. 제품 — 무엇을 파는가

여러 협업 소스(Local / GitHub / Google Drive)를 하나의 Risk Workspace 에 연결하고,
변경을 지속 감지해 Patent·License 위험을 **근거 기반**으로 분석하며, 사람이 장기적으로
검토·추적·감사하게 하는 Secure Human-in-the-Loop 시스템.

값 네 가지 — **1) 지속 추적 2) 근거 기반 3) HITL 4) 보안.**

### 1.1 포기하는 것 — 스캔 정확도 경쟁 [결정]

ScanCode 는 파일 안 라이선스 원문을 대조하고, deps.dev 는 선언 라이선스를 주고,
GitHub dependency-review 는 SPDX allow/deny 를 강제한다. 전부 무료다.

**스캔은 "돈 받는 이유" 가 아니라 "대화가 시작되는 조건" 이다.** 스캔 실질이 최소선을
넘어야 아래 셋이 성립하므로 버릴 수는 없지만, 그것으로 경쟁하지 않는다.

### 1.2 이 제품만 할 수 있는 것 셋

**(A) 판정 변경의 원인이 귀속되는 원장**

다른 도구는 "지금 무엇이 있는가" 에 답한다. 우리는 **"왜 지난달과 다른가"** 에 답한다.
원인은 넷이고, 모델의 주장이 아니라 **네 지문의 차이에서 파생**된다.

| 원인 | 무엇이 달라졌나 | 사용자에게 뜻하는 것 |
|---|---|---|
| 입력 | `analysis_input_checksum` | "우리가 한 일이다" |
| 외부 사실 | 패키지 메타데이터 / 라이선스 표현식 | **"우리는 가만있었는데 위험이 생겼다"** |
| 우리 지식 | `policy_version` / `rag_corpus_version` | "판단 기준이 좋아졌다" |
| 모델 | `model_id` / `prompt_version` | "같은 것을 다르게 읽었다" |

가운데 줄이 이 제품이 파는 것이다.

**(B) 결정 시점 탐지 — 매니페스트보다 먼저**

도입 결정은 매니페스트보다 먼저 기획 문서에 나타난다. SCA 는 매니페스트에서 시작하므로
원리적으로 못 본다. 우리는 Drive 커넥터와 `DOCUMENT_TEXT` 경로가 이미 있고, 특허 쪽에
**문서에서 주장을 뽑아 인용으로 검증하는 파이프라인**이 이미 있다.

**(C) 배포 맥락 기반 의무 판정**

고객의 질문은 "AGPL 이 있는가" 가 아니라 **"내가 소스를 공개해야 하는가"** 다. 후자는
배포 형태에 달린 조항 해석이라 표로는 원리적으로 불가능하다. **RAG 가 장식이 아니라
답 자체가 되는 유일한 지점**이고, 판정 관여 완화를 정확히 여기에 쓴다.

### 1.3 경고 — 원장의 값은 음수가 될 수 있다

잘못된 판정이 "성실히 판단한 기록" 으로 굳으면 방어 자산이 아니라 상대측 증거가 된다.
**그래서 §8 의 오답 제거가 다른 무엇보다 먼저다.** 순서를 바꾸면 안 된다.

### 2.1 D1 이 구조적으로 없애는 것 [확인]

서비스 계정은 Cloud Run 에 이미 붙어 있어 키 파일이 필요 없다. 그래서 **보관할
자격증명이 없다.** workspace 를 전부 지운 뒤에도 Drive refresh token 19 개가 남아 있던
사고(`1849f37` 로 고침)가 **구조적으로 재발하지 않는다.**

범위 계산에 버그가 있어도 공유되지 않은 것을 요청하면 Google 이 거절한다. 봉쇄가 우리
신뢰 경계 **밖**에 남는다.

| | 접근 범위 | 봉쇄를 누가 하나 | 보관할 자격증명 |
|---|---|---|---|
| `drive.file` + Picker (지금) | 고른 항목 | Google | 사용자 refresh token |
| `drive.readonly` 사용자 OAuth | 계정 **전체** | **우리 코드** | 사용자 refresh token |
| **서비스 계정 + 폴더 공유** | **공유받은 것만** | **Google** | **없음** |

**변경 피드도 함께 좁아진다.** 서비스 계정의 `changes` 피드는 공유받은 범위다. 사용자
OAuth 였다면 계정 전체의 변경을 받아 우리가 걸러야 했고, **범위 밖 파일의 이름과 변경
사실이 우리 시스템을 지나갔을 것이다.** 봉쇄는 보관하는 토큰만의 문제가 아니다.

`drive.readonly` 를 택했다면 더 필요했을 것 — 게이트에 "이 파일이 마운트된 폴더 안에
있는가" 검사를 새로 넣어야 했고(지금 게이트는 ignore·mime·정합성만 본다), Drive 폴더가
파일시스템 트리가 아니라는 점(바로가기·다중 부모)을 전부 우리 코드가 감당해야 했다.

## 4. 판정 권한의 층 [결정 D9]

RAG 를 판정에 넣되 전부 여는 것이 아니라 층을 나눈다.

| 층 | 무엇을 하는가 | 판정 권한 | 근거의 성격 |
|---|---|---|---|
| **T1 결정론** | 파서 / SPDX 표현식 / 정책 함수 | **만든다** | 코드가 계산한 값 |
| **T2 검증된 대조** | 정규화 전문 해시 일치, 필수 문구 확인, 구간 실재 검증 | **만들 수 있다** | 코드가 재검증한 사실 |
| **T3 RAG·모델** | 조항 검색, 의무 판정, 표 밖 분류 | **올릴 수만 있다** | 모델의 읽기 + 인용 검증 |

**T3 은 등급을 내리지 못한다.** 이것은 가정이 아니라 **이미 겪고 되돌린 일**이다. 특허
쪽에서 모델 자기신고로 강등했더니 대조 80 건 중 77 건이 표시를 달았고 **HIGH 자격 13 건이
13 건 모두 강등되어 HIGH 가 한 번도 안 나왔다.** 표시의 내용은 대부분 "선행 특허 청구항에
구체적인 알고리즘이 제시되어 있지 않음" 처럼 **특허의 서술에 대한 논평**이지 우리 판단의
불확실성이 아니었다. 지금 코드는 그 규칙을 이미 버렸고 강등 조건을 "대조가 본 근거가
잘렸는가" 하나로 좁혀 두었다 — `grounding.py` 의 `suggested_priority` docstring 이 그
경위를 기록으로 남긴다. **인용하는 것은 현재 동작이 아니라 그 기록이다.** 모델에게 근거를 물으면 거의 항상 무언가를
낸다. 상향 방향에서도 같은 포화가 일어날 수 있으므로 **상향 발화율을 계측하고 상한을
둔다** (§10).

T3 이 올릴 때는 **corpus chunk id + 실재가 확인된 인용**이 반드시 있어야 한다. 인용이
없으면 모델 출력을 전혀 쓰지 않는다. 특허 쪽 `quote.py` / `grounding.py` 의 규칙을 그대로
쓴다.

## 5. 라이선스 명세

### 5.1 파이프라인 [결정 D3]

```
1. 알려진 이름의 매니페스트·락파일 파싱          → 의존성 선언 목록
2. deps.dev / 레지스트리 조회                    → SPDX 식별자 (원문자열 보존)
3. 식별자로 corpus 에서 라이선스 전문 조회        → 조회다. 검색이 아니다
4. 배포 형태를 질의로 전문 안에서 조항 검색       → 하이브리드 RAG
5. Gemini 가 그 조항을 근거로 권장 행동           → T3
```

**3 단계가 조회인 이유** — 식별자를 이미 알고 있다. 임베딩으로 찾으면 `AGPL-3.0-only` 와
`GPL-3.0-only` 를 헷갈릴 수 있고, 그것이 `reference_gate` 가 존재하는 이유다.

**4 단계가 검색인 이유** — 질의가 라이선스 이름이 아니라 **상황**이다. AGPL 전문은 수천
단어이고 그중 지금 배포 형태에 걸리는 조항만 뽑아야 한다.

### 5.2 원문자열 보존 — 다른 모든 것의 선행 조건

**[확인]** 미상 식별자가 **저장 경계 이전에** 문자열 `UNKNOWN` 으로 치환된다. 소거하는
곳은 `spdx.normalize` 가 아니라 그 아래의 `spdx.canonicalize` 이고, **운영에서 실제로 도는
레지스트리 폴백 경로는 `normalize` 를 부르지 않는다** (`package_metadata.py:130-166` 이
`try_parse_expression` / `from_free_text` 를 쓰는데 둘 다 안에서 같은 소거를 한다).
0-F 로 고칠 곳은 세 군데다 — `package_metadata.py` 의 120-126 · 152-166 · 228-234.
`normalize` 호출부만 고치면 레지스트리 경로에서 원문이 계속 사라진다. `spdx._CANONICAL` 과 `policy._OUTCOME_BY_ID` 가 정확히 같은 42 개이고 차집합이
양방향 공집합이다.

```
'BUSL-1.1'          → 'UNKNOWN'
'MIT AND BUSL-1.1'  → 'MIT AND UNKNOWN'      ← 부분 소거
```

귀결 — **정책 표에 행을 추가해도 무효다.** 저장된 표현식으로 다시 계산하는 방식은
UNKNOWN 을 하나도 못 고친다. `BUSL-1.1 → Elastic-2.0` 전이를 구분할 수 없다.

**명세** — `PackageLicenseFact` 에 원문 표현식을 함께 싣는다. `normalize` 의 치환은
**판정 입력에만** 쓰고 저장 경계를 넘지 않는다. `LicenseRef-*` 는 보존한다.

이것 없이는 §5.1 의 2→3 단계가 42 종에만 닿는다.

### 5.3 표현식 평가

**[확인·실측]** 표현식 파서는 `WITH` 를 제대로 읽어 `exception` 에 담는데
(`spdx.py:227`), 정책이 그 필드를 **한 번도 보지 않는다** (`policy.py:90-92`).

| 표현식 | 지금 결과 | 무엇이 잘못됐나 |
|---|---|---|
| `GPL-2.0-only` | `POLICY_CONFLICT` | (기준) |
| `GPL-2.0-only WITH Classpath-exception-2.0` | `POLICY_CONFLICT` | 링크를 허용하려고 존재하는 예외인데 **맨 GPL 과 같다** |
| `MIT WITH totally-made-up` | `NOTICE_REQUIRED` | **없는 예외를 조용히 받아들인다** |
| `0BSD OR GPL-3.0-only` | `NO_ACTION` | → LOW → Risk 미생성 |
| `AGPL-3.0-only OR MIT` | `NOTICE_REQUIRED` | AGPL 갈래가 **기록 없이** 사라진다 |

가운데 둘은 방향이 서로 반대다. Classpath 예외는 OpenJDK 전체가 쓰는 가장 흔한 예외라
**오탐이 자바 생태계 전반에 걸린다.** 반대로 예외 식별자는 아무 검증도 받지 않아 오타든
날조든 맨 라이선스 결과로 통과한다.

**명세**

* `WITH` 예외를 평가에 반영한다. 예외가 의무를 완화하는 경우를 표에 담는다.
* **예외 식별자를 SPDX 예외 목록으로 검증한다.** 목록에 없으면 완화하지 않고 `UNKNOWN`
  으로 다룬다 — 모르는 라이선스를 통과시키지 않는 것과 같은 이유다.
* `OR` 선택은 결과에 **어느 쪽을 택했는지 기록**한다. 지금은 조용히 최소 심각도를 고르고
  그 선택이 원장에 남지 않는다. T1 의 결정론적 하향이라 §4 위반은 아니지만, §7.3 이
  요구하는 "보이는 하향" 에 해당한다.
* 어휘를 SPDX 전체로 넓힌다. 정책 표에 없는 식별자는 `UNKNOWN` 이되 **원문자열이 남으므로**
  나중에 표가 넓어지면 재평가로 구제된다.

### 5.4 corpus [결정 D4]

**[확인]** 이 절을 쓸 때 corpus 는 손으로 쓴 문서 3 개, 총 **2,120 바이트**였고 RAG 를
부르는 대상 22 개 중 4 개만 덮었다. **지금은 675 편이 113 종을 전부 덮는다** — 아래 명세대로
SPDX 목록에서 직접 뽑게 바꾼 결과다.

**[확인·전수]** `permissive-notice` 가 덮는 MIT·BSD·Apache·ISC 는 전부
`needs_review=False` 라 **자기가 판정을 이끈 경로에서는 검색조차 되지 않는다.** 2-leaf
조합을 전수로 돌려 이 문서가 정당하게 붙는 경우를 찾았으나 **한 건도 없다.** 구조적 이유가
있다 — permissive 는 심각도가 가장 낮아 AND 의 최대가 될 수 없고, OR 의 최소가 되면 결과가
`NOTICE_REQUIRED` 로 내려가 RAG 자체가 불리지 않는다.

**그래서 이 문서는 판정에 손해 없이 지금 뺄 수 있다.** 0-G 를 기다리지 않고 corpus 에서
빼는 것만으로 오부착이 즉시 줄어든다. 다만 §10 의 오부착률을 재기 전에 빼면 개선을 측정할
대상이 사라지므로, **재고 나서 뺀다.**

**명세**

* 내용: SPDX license-list-data 의 라이선스 **전문**(CC0 라 자유롭게 쓴다) + 배포 형태별
  의무 해설.
* **무엇을 넣을지 정책 표에서 파생하지 않는다 [결정].** 예전에는 `needs_review` 인
  식별자만 골라 넣었고, 그래서 정책 표를 넓힐 때마다 corpus 를 다시 만들어야 했다. 실제로
  표가 158 → 226 이 되자 커버리지가 100% 에서 74.3% 로 떨어졌다. **SPDX 전문을 전부
  넣는다** — 727 종이 약 11.8 MB 라 규모가 문제되지 않고, 그러면 표와 corpus 가 서로를
  기다리지 않는다.
* 임의의 웹 문서를 긁지 않는다. manifest 의 `approved_for_rag` 가 그 관문이다. 전문을 전부
  넣어도 이 관문은 그대로다 — SPDX 는 승인된 출처 하나이지 "아무거나" 가 아니다.
* manifest 에 이미 `jurisdiction: KR` 필드가 있다. 지금은 한 값뿐이지만 corpus 가 커지면
  이 축이 뜻을 갖는다 — 넣을 때 채워 두고 쓰는 것은 나중이다.
* 갱신: 버전을 올리고 checksum 을 갱신하며, 변경 diff 를 사람이 검토한 뒤 적용한다.
* **corpus 버전은 판정에 항상 기록된다** (§5.6).

**[확인] 배포 검증기가 확대를 막는다.** `scripts/validate_gcp_deployment.py:288-294`
(문자열 리터럴은 289 행)가
`corpus_version` 을 문자열 `"2026-08-14.1"` 로, 소스를 **정확히 3 건**으로, source_id 집합을
`RAG_SOURCE_IDS` 로 하드코딩해 검사한다. 문서를 하나만 더해도 배포가 막힌다. 같은 파일
`:640-666` 은 `CORPUS_SUBJECT_COVERAGE` 를 manifest 와 교차검증하므로 2-D 로 표를 데이터로
옮기면 이 검증기도 함께 고쳐야 한다. **2-C 와 2-D 는 배포 검증기 수정을 포함한다.**

### 5.5 관련성 게이트 — 확대 전에 반드시

**[확인·재현]** `reference_gate.is_relevant` 가 판정을 이끈 leaf 가 아니라 **표현식의
모든 leaf** 를 본다.

```
'Apache-2.0 AND GPL-3.0-only' → POLICY_CONFLICT, 게이트 통과 = ['permissive-notice']
permissive-notice.md 본문 = "소스코드 공개 의무는 없다"
```

**판정과 정반대의 근거가 붙는다.** 게이트가 막으려고 만들어진 바로 그 오류다.

**그리고 이것이 확대의 선행 조건인 이유** — 지금은 18/22 가 "붙을 문서가 없어" 조용히
넘어간다. 오부착을 막고 있는 것은 게이트가 아니라 **corpus 가 비어 있다는 우연**이다.
600 종을 넣으면 **틀린 식별자마다 그럴듯한 문서가 반드시 하나 생긴다.**

**명세**

* 게이트가 보는 집합을 **판정을 이끈 leaf** 로 좁힌다 (AND 는 최대 심각도 leaf, OR 은
  선택된 leaf).
* 커버리지 표를 코드에서 **데이터로** 옮긴다. manifest 에서 생성한 색인을 package-data 로
  싣는다 — 프롬프트 `.md` 가 `pyproject.toml:46` 에서 이미 그렇게 실린다.
  그래야 문서를 늘릴 때 코드를 고치지 않는다.
* 검색은 **거르고 나서 찾는다**: SPDX 식별자로 정확 조회 → 그 안에서만 임베딩으로 구절 선택.
* **corpus 를 전부 채워도 게이트는 남는다.** 임베딩은 관련 문서가 없어도 언제나 `top_k` 개를
  돌려주므로, 덮는 문서가 없는 질의에는 **가장 덜 관련 없는 엉뚱한 것**이 나온다. 게이트가
  보는 것은 정책 표가 아니라 각 문서가 manifest 에 선언한 `covers` 라, 표와 독립이다.
  전문을 다 넣으면 게이트가 거절할 일이 드물어질 뿐 없어도 되는 것이 아니다.

### 5.9 없는 버전을 최신 버전으로 대체하지 않는다

**[확인]** npm 레지스트리 폴백이 `info["versions"].get(version, info)` 다
(`package_metadata.py:142`). 요청한 버전이 없으면 **문서 전체로 폴백**해 최신 버전의
라이선스를 그 버전의 라이선스로 기록한다. `inferred_from_free_text` 같은 표시도 붙지 않는다.

버전이 `None` 인 경우(§6.5 의 redaction 손상이 만드는 상태)에도 같은 자리로 들어온다.

**명세** — 요청한 버전이 레지스트리에 없으면 **모른다**. 최신 버전으로 대체하지 않고
`UNKNOWN` + 불확실 표시로 남긴다. 라이선스는 버전마다 달라질 수 있고, 실제로 라이선스를
바꾼 패키지들이 이 제품이 잡으려는 대상이다.

### 5.10 workspace 정책이 분석기에 닿는 길 [결정 D7]

§5.7 의 배포 형태 축과 D7 의 workspace 별 정책은 **분석기 안에서 값이 필요한데 분석기는
workspace 를 모른다.** 계약을 고치지 않고 이 다리를 놓는 방법이 이미 있다.

**[확인] 선례** — 특허 쪽이 같은 문제를 이미 풀었다. Control 의 메서드를 composition 에서
Intelligence 로 넘긴다.

```
public_facade/service.py:298    async def previously_matched_patents(...)
composition/production.py:422   previously_matched_patents=context.control_facade.previously_matched_patents
intelligence/public.py:107,125  받아서 분석기에 전달
```

**명세** — 같은 모양으로 `workspace_license_policy(risk_workspace_id)` 를 넘긴다.

* Control 이 `RiskWorkspace` 에서 배포 형태 축(§5.7)과 정책 표 판본을 읽어 돌려준다.
* `LicenseAnalyzer.__init__` 이 이것을 키워드로 받는다 — 지금 `retriever` 를 받는 자리와
  같다 (`analyzer.py:66-73`).
* §3 의 경계를 지킨다. 넘어가는 것은 **함수 하나**이고 Intelligence 는 그것이 어디서
  오는지 모른다.

**정책 버전 [확인]** — 지금 `POLICY_VERSION` 은 모듈 상수이고
(`policy.py:24` = `global-license-policy-2026-08-14.1`) `analyzer.py:85` 가 결과에 그대로
싣는다. **workspace 마다 다른 값이 되어야 한다.**

```
{risk_workspace_id}:{정책표 판본}:{배포형태축 해시}
```

세 조각이 모두 필요하다. 표가 바뀌어도, 사용자가 배포 형태를 SaaS 에서 사내 전용으로
바꿔도 판정이 달라지고, §7.4 의 원인 귀속이 그 차이를 읽어야 한다.
`AnalysisVersions.policy_version` 이 자유 문자열이라 계약 변경이 없다 (§12.1).

**설정 전에는 등급을 매기지 않는다 [결정]** — 가장 무거운 쪽으로 가정하는 방법(재배포함 ·
수정함 · 정적 링크)도 있으나 채택하지 않는다. 설정 전 workspace 의 라이선스 Risk 가 전부
HIGH 로 뜨고, **첫 화면이 전부 빨강이면 사용자는 진짜 HIGH 도 함께 무시한다.** 안전한
방향의 기본값이 안전을 떨어뜨린다.

대신 파이프라인을 나눈다 (§5.1).

| 단계 | 배포 형태 설정 전 |
|---|---|
| 1~3 파싱 · 식별 · 전문 조회 | **그대로 돈다.** 무엇을 쓰고 있는지는 설정과 무관하다 |
| 4~5 조항 검색 · 의무 판정 | **하지 않는다.** 등급 대신 "설정이 필요합니다" 로 둔다 |

거짓 경보를 만들지 않으면서 안전 방향을 지킨다. 판정을 낮추는 것이 아니라 **아직 하지
않았음을 정직하게 말하는 것**이므로 §4 의 층 규칙과도 어긋나지 않는다. 설정이 채워지면
그때 4~5 단계가 돌고, 그 변화는 `policy_version` 의 셋째 조각이 달라진 것으로 남는다 (§7.4).

설정을 어느 자리에서 받을지는 [미결] (§13-9).

### 5.12 판정을 못 내린 것에 칸을 준다 [결정]

`UNKNOWN` 이 `MEDIUM` 이었다. 그래서 **강한 copyleft 가 중간으로 묻혔다** — `CECILL-1.0` 이
`AGPL-3.0-only` 와 같은 성질인데 하나는 HIGH, 하나는 MEDIUM 이었다.

`ReviewPriority` 에 **`INDETERMINATE`** 를 더해 `HIGH` 바로 아래에 둔다 (§12.1).

| 판정 | 뜻 | 등급 |
|---|---|---|
| `NO_ACTION` | 알아봤고 관리 대상이 아니다 | `LOW` — Risk 를 만들지 않는다 |
| `NOTICE_REQUIRED` | 안다. 할 일이 적다 | `MEDIUM` |
| `REVIEW_REQUIRED` | 안다. **조건에 따라 갈린다** | `HIGH` |
| `POLICY_CONFLICT` | 안다. 우리 배포와 충돌한다 | `HIGH` |
| `UNKNOWN` | **모른다** | **`INDETERMINATE`** |

**셋이 같은 자리에 모인다.** 표에 없는 라이선스, 일부만 본 결과(§7.2), 조회 실패 — 이유는
다르지만 결론이 같다. **자동으로 결론 내지 않는다.** 화면은 이유를 구분해 보여 준다.

§7.3 의 비대칭이 방향을 정한다 — 틀린 상향은 검토 시간을 쓰고 보이지만, 틀린 하향은
조용하다. 그래서 **모르는 것은 위에 둔다.**

### 5.11 RAG 작동 정책 [결정]

§5.1~§5.10 에 흩어진 결정을 한자리에 모은다. **RAG 가 언제 돌고, 무엇을 붙이고, 무엇이
무엇을 기다리는가.**

#### 무엇이 무엇을 정하지 않는가

셋을 서로 떼어 놓는다. 붙여 두면 한쪽을 고칠 때마다 다른 쪽이 일감이 된다.

| | 무엇에서 정해지나 | 무엇과 무관한가 |
|---|---|---|
| **corpus 내용** | SPDX 라이선스 목록 | 정책 표 · 게이트 |
| **판정** | 정책 표(`_OUTCOME_BY_ID`) | corpus 에 문서가 있든 없든 |
| **근거 부착** | 게이트 — 문서의 `covers` ∩ 판정을 이끈 leaf | 정책 표 |

**corpus 를 정책 표에서 파생하지 않는다.** 그렇게 했더니 표를 158 → 226 으로 넓혔을 때
커버리지가 100% → 74.3% 로 떨어졌다. 아무것도 나빠지지 않았는데 두 작업이 서로를 기다린
것이다. 지금은 SPDX 에서 직접 뽑아 675 편이고, 표를 넓혀도 corpus 는 그대로다.

**판정은 corpus 를 보지 않는다.** 문서가 없어도 등급은 표가 낸 그대로다. corpus 는 "왜
그런가" 를 붙일 뿐이다. 그래서 corpus 가 비어도 **판정이 틀리지 않는다** — 설명이 없을 뿐이다.

#### 게이트는 corpus 를 다 채워도 남는다

임베딩 검색은 관련 문서가 없어도 언제나 `top_k` 개를 돌려준다. 그래서 게이트가 없으면
**가장 덜 관련 없는 엉뚱한 문서**가 근거로 붙는다.

게이트가 보는 것은 정책 표가 아니라 **각 문서가 manifest 에 선언한 `covers`** 이고,
맞추는 대상은 표현식의 모든 leaf 가 아니라 **판정을 이끈 leaf** 다 (0-G). 그래서
`Apache-2.0 AND GPL-3.0-only` 에 "소스 공개 의무 없음" 문서가 붙던 일이 **구조적으로**
일어나지 않는다 — 오부착은 이제 재는 값이 아니라 정의상 생길 수 없는 것이다.

#### 언제 부르는가

지금은 `needs_review` 가 참일 때만 부른다 — `UNKNOWN` · `REVIEW_REQUIRED` ·
`POLICY_CONFLICT`. MIT·Apache 같은 `NOTICE_REQUIRED` 는 의무가 "고지와 사본" 뿐이라 붙일
조항이 없다.

**사용자 추가 조항 질의(§12.2)가 생기면 이 조건을 넓힌다.** "이거 UI 에 저작자 표시해야
하나" 같은 질문은 MIT 에도 적용되므로 심각도로 막아 두면 안 된다. 캐시가 있으면 조건 한
줄을 바꾸는 일이다.

#### 캐시 — 키가 넷이다

```
(정규화된 표현식, 판정, corpus 버전, 배포형태축 해시)
```

**corpus 갱신 때 캐시를 지우지 않는다.** 버전을 키에 넣으면 같은 결과를 내면서 셋이 낫다 —
무효화 실패라는 실패 모드가 없고, 되돌리면 옛 캐시가 살아 있어 롤백이 싸고, 두 판본을
나란히 두고 차이를 잴 수 있다.

**배포형태축을 빠뜨리면 안 된다.** 질의가 workspace 설정에서 만들어지므로(§5.10) 빠뜨리면
SaaS workspace 의 조항 결과가 사내 전용 workspace 에 서빙된다. D7 이 금지하는 것이다.

#### 순서

```
빌더 독립  →  캐시(2-F)  →  주기적 재평가(결함 24, §7.6)
```

주기적 재평가가 캐시 뒤인 이유는 조회 수가 **의존성 수에 비례**하기 때문이다. 캐시 없이는
그 비용이 주기를 정하지 못하게 만든다.

#### 분류는 수요가 부른다

어휘 727 종 중 226 종이 분류돼 있다. 나머지를 전부 분류하지 않는다.

| | 무엇 | 왜 |
|---|---|---|
| **개선** | copyleft 23 종 (`CECILL`·`NPL`·`QPL`·`copyleft-next` 등) | 분류하면 "확인 필요" 가 "소스 공개를 요구한다" 로 **정밀해진다.** 다만 안 해도 놓치지 않는다 — `INDETERMINATE` 가 이미 눈에 띄는 자리에 올린다 |

**corpus 가 다 찼는데 왜 표가 남는가.** 둘이 다른 일을 하기 때문이다 — 표는 **등급**을,
corpus 는 **왜 그런가**를 정한다. `CECILL-1.0` 은 이미 corpus 문서가 붙는데도 화면은 이렇게
나온다.

```
등급   MEDIUM
문장   "라이선스를 식별하지 못했다"
근거   CECILL-1.0 조항 원문   ← 붙어 있다
```

**근거는 그 라이선스가 무엇을 요구하는지 말하는데 판정은 모른다고 말한다.** 전문을 아무리
넣어도 "이것이 결합 저작물의 소스 공개를 요구하는가" 는 검색이 답할 수 없다. 그 판단이
§4 의 T1 이고, T3 에게 맡기면 특허 쪽에서 HIGH 자격 13 건이 13 건 모두 강등된 그 일이
라이선스에서 되풀이된다.

다만 **이제는 분류만 하면 끝난다.** 예전에는 "분류해도 전문이 없으면 근거가 안 붙는다" 가
함께 걸렸는데, corpus 가 675 편이 되면서 23 종이 전부 덮였다. 표에 23 줄을 넣으면 등급이
고쳐지고 근거는 따라온다.
| **수요가 부르면** | 실제 의존성 파일에 나타나는 것 | 유한하고 영향 순서대로 정렬된다 |
| **하지 않는다** | 폰트·문서·벤더 라이선스 448 종 | `UNKNOWN` = MEDIUM 이 **정확한 표현**이다. 정말 모르고, 자동 허용도 안 한다 |

전부 분류하면 지금까지 한 법적 판단이 두 배가 되고, 얻는 것은 거의 나타나지 않는 라이선스의
정밀도다. **틀릴 기회만 늘어난다.**

`UNKNOWN` 이 나올 때 그 SPDX 식별자를 로그에 남기면 실제 분포가 무엇을 분류할지 알려 준다.
로그 정책상 [미결] (§13-10).

### 5.13 레지스트리가 한 말을 어떻게 읽는가 [결정]

의존성 하나의 라이선스는 레지스트리에 묻는다. 그런데 레지스트리는 **한 가지 방식으로
대답하지 않는다.** PyPI 하나만 봐도 답이 세 군데 있다.

| 어디 | 무엇 | 믿을 만한가 |
|---|---|---|
| `license_expression` | PEP 639 가 들여온 정규 SPDX 표현식 | **사실.** 이미 표현식이다 |
| `classifiers` 의 `License ::` | 닫힌 어휘에서 고른 항목 | **거의 사실.** 다만 판을 안 말할 때가 있다 |
| `license` | 자유 서술. 이름일 수도, **전문 전체**일 수도 있다 | 경우에 따라 다르다 |

마지막 칸이 문제를 만들었다. 예전에는 `license` 에서 라이선스 이름을 **정규식으로
찾았다.** 그 필드에 이름이 들어 있을 때는 맞지만, 라이선스 전문이 통째로 들어 있을 때는
**남의 라이선스를 찾는다** — 라이선스 문서는 원래 다른 라이선스를 이름으로 언급하기
때문이다.

실측한 결과가 이렇다.

| 패키지 | 예전 답 | 실제 | 왜 |
|---|---|---|---|
| `matplotlib` | **GPL-2.0-only → 최고 위험** | PSF-2.0 | 전문이 품고 있는 FreeType 을 "FTL OR GPL-2.0-or-later" 로 설명한다 |
| `pandas` | Apache-2.0 | BSD-3-Clause | 전문 안에 Apache 코드 고지가 있다 |
| `weasyprint` | UNKNOWN | BSD-3-Clause | `license` 가 비어 있고 분류자에만 있다 |

첫 줄이 이 제품에서 가장 나쁜 종류의 오답이다. **파이썬 생태계에서 가장 널리 쓰이는
패키지 하나가 최고 위험으로 올라간다.** 등급이 틀린 것으로 끝나지 않는다 — 사용자가
근거를 열어 보면 우리가 GPL 이라고 적어 둔 것이 있고, 그것이 근거처럼 보인다.

**이름과 전문은 길이로 갈린다.** 실측에서 이름·설명문은 0–141 자였고 (가장 긴 것이
`pyinstaller` 의 예외 설명이다), 전문은 50,087 자와 59,523 자였다. 350 배 사이라 눈금을
맞출 필요가 없어 512 자로 잡았다.

그래서 읽는 순서를 이렇게 정한다.

1. **`license_expression`** — 표현식이므로 그대로 쓰고 **추정으로 표시하지 않는다.**
2. **`license` 가 등록된 식별자만으로 된 표현식일 때** — 역시 사실이다. 별칭은 여기
   해당하지 않는다 (아래).
3. **분류자** — 닫힌 어휘라 훑지 않고 맞춘다. 판을 안 말하는 항목("BSD License")은
   좁혀 적으므로 **추정으로 표시한다.**
4. **`license` 훑기** — 마지막이고, **이름 길이일 때만** 한다.
5. 아무것도 없으면 `UNKNOWN` → `INDETERMINATE` (§5.12).

분류자가 자유 서술보다 앞에 오는 이유는 더 정확할 때가 있어서다. `license: "LGPL"` 로는
2.0 인지 2.1 인지 or-later 인지 알 수 없는데, 옆의 분류자가 "v2 or later (LGPLv2+)" 라고
적어 둔다.

**별칭은 사실이 아니다.** `"LGPL"` 을 `LGPL-2.1-only` 로 읽는 것은 편하지만 **우리가 판을
고른 것**이다. 그래서 2 번 자리에서는 등록된 식별자만 받는다 — 별칭이 사실 행세를 하면
더 정확한 분류자를 밀어낸다. 4 번 자리에서는 별칭을 쓰되 추정으로 표시한다.

**거절은 검토 필요를 늘린다.** 그것이 의도다. §5.12 가 그 칸을 만든 이유가 여기 있다 —
검토 필요는 답이지만, 자신 있는 오답은 답이 아니다. 다만 거절만 하고 분류자를 안 읽으면
검토 필요만 늘고 얻는 것이 없으므로 둘은 함께 간다.

**남아 있는 것** (결함 29). 예외는 여전히 사라진다. `"GPLv2-or-later with a special
exception which allows to use PyInstaller to build and distribute non-free programs"` 는
141 자라 훑기를 통과하는데, 나오는 값은 `GPL-2.0-only` 다. `or-later` 도 예외도 없다.
과보고 방향이라 급하지 않지만, PyInstaller 를 쓰는 모든 저장소가 최고 위험을 하나씩
받는다.

### 5.14 관대한 것과 조용한 것은 다르다 [결정]

파서는 관대해야 한다. 한 줄이 깨졌다고 파일 전체를 버리면 나머지 의존성까지 놓친다.
그런데 **넘어간 사실을 말하지 않으면** 그 결과가 `COMPLETE` 로 올라가고, `COMPLETE` 에는
**해소 권한**이 있다 (§7.2). 그러면 읽지 못한 것이 "없다" 가 되어 멀쩡한 Risk 가 닫힌다.

0 단계가 이 실패를 없앴다고 봤는데, **다른 문으로 들어왔다.** 0-C 는 파서가 **예외를 던지는**
경우를 다뤘다. 줄 단위 형식은 예외를 던지지 않는다 — 한 줄씩 건너뛴다.

통합 시험 2 회차에서 실제로 일어났다. `requirements.txt` 를 PowerShell 의
``Set-Content -Encoding utf8`` 로 썼더니 **UTF-8 BOM** 이 붙었고, 첫 줄이
``﻿requests==2.31.0`` 이 되어 이름 패턴에 걸리지 않았다. 결과는 `SUCCEEDED` ·
`COMPLETE` · 0 건이었고, **지우지도 않은 `requests` 의 Risk 가 `RESOLVED` 로 닫혔다.**

윈도우에서는 드문 일이 아니다. 메모장도 붙이고 PowerShell 도 붙인다.

| | 고침 |
|---|---|
| BOM | 파서 다섯 개가 모두 맨 앞 BOM 을 뗀다. 인코딩 표시이지 내용이 아니다 |
| 건너뛴 줄 | 넘어가되 **남긴다** (`unreadable_requirement_lines`). 하나라도 있으면 coverage 가 `PARTIAL` 이다 |

**읽어 낸 것은 버리지 않는다.** `PARTIAL` 은 해소 권한만 없을 뿐 후보는 그대로 올린다 —
관대함의 목적이 나머지 의존성을 살리는 것이었으므로 그것까지 버리면 고친 것이 아니다.

거절이 지나쳐도 안 된다. 주석과 지시자(``-r other.txt``)는 **못 읽은 것이 아니고**, 정말
비어 있는 파일은 `COMPLETE` 여야 한다. 그러지 않으면 모든 파일이 미결이 되어 등급이 뜻을
잃는다.

## 6. 소스 통합 명세

### 6.1 Drive — 서비스 계정 + 폴더 공유 [결정 D1]

**선행 실측** — 폴더 하나를 서비스 계정에 뷰어로 공유한 뒤 세 가지를 확인한다.
**이 결과가 설계의 크기를 정한다.**

1. 폴더에 파일을 새로 넣으면 SA 의 `changes` 에 잡히는가
2. 폴더 밖으로 옮기면 `removed` 로 오는가
3. 되돌리면 다시 나타나는가

셋 다 잡히면 이탈·재진입이 **이미 있는 DELETE / UPDATE 경로**로 들어오고 폴더 대조 작업이
필요 없다. 안 잡히면 주기적 대조를 새로 만들어야 한다.

**v1 의 동작을 근거로 읽으면 안 된다.** v1 의 폴더 펼침은 **연결 시점의 스냅샷**이라 이후
폴더에 새로 들어온 파일은 자동으로 추적되지 않았다 — v1 이 `ea70787` 에 스스로 적어 두었다.
v1 이 스코프를 넓힌 이유(`f50a15b`)도 **펼치기가 409 로 실패해서**였지 지속 추적 때문이
아니다. 지속 추적은 이 프로젝트가 새로 만드는 부분이므로 1-A 의 결과를 "v1 도 됐으니
된다" 로 읽으면 틀린다.

**명세**

* 공유받은 폴더만 읽는다. 폴더 안은 소유자를 구별하지 않고 전부 검사한다.
* 바로가기(`application/vnd.google-apps.shortcut`)는 따라가지 않는다. 문서 종류를 넓힐 때
  **실수로 들어오지 않도록 규칙으로 막는다** — 지금은 목록에 없어서 막히는 것이지 규칙이
  아니다.
* 폴더 확장에 **상한**을 둔다. v1 이 쓴 값이 **항목 300 개 / 깊이 10** 이고 잘라낸 사실을
  로그로 남겼다 — 새로 정할 이유가 없으면 그 값을 그대로 쓴다. 조용히 자르면
  "전부 검사했다" 로 읽힌다.
* `logical_path_hint` 에 **부모 경로**를 넣는다. **[확인]** 지금
  `google_drive/adapter.py:211,299` 가 `None` 이라 Drive artifact 의 `logical_path` 가
  `alias/파일이름` 으로 평평하다. UI 트리의 전제이고 스코프 결정과 독립이다.

  **[구현됨]** `google_drive/paths.py` 가 부모를 따라 올라가 경로를 만든다.

  | | |
  |---|---|
  | 클라이언트 값 | **쓰지 않는다.** 지금 마운트는 picker 가 보낸 메타데이터를 쓰는데, 경로는 제외 패턴 판정(§9.1)에 쓰이므로 클라이언트가 정하게 두면 게이트를 지나갈 방법이 생긴다 |
  | 부모가 여럿이면 | 첫 번째만 따라간다. 경로가 하나여야 트리가 하나가 된다 |
  | 깊이 상한 | **10** (v1 값). 잘리면 맨 앞에 `…` 를 남긴다 — 조용히 자르면 뿌리부터인 것처럼 읽힌다 |
  | 읽지 못하는 조상 | 거기서 멈춘다. 오류가 아니라 **우리가 볼 수 있는 만큼**이 경로다 |
  | 이름 속 `/` | `_` 로 바꾼다. Drive 이름에는 `/` 가 들어갈 수 있고, 그대로 이으면 조각 하나가 둘이 되어 경로의 뜻이 바뀐다 |

  **대조와 가져오기가 같은 값을 내야 한다.** 아티팩트의 `logical_path` 를 정하는 곳은
  대조(`reconcile`)이고, 가져오기가 다른 값을 내면 게이트가
  `CANONICAL_CONTEXT_MISMATCH` 로 **거부**한다. 지운 파일처럼 메타데이터를 못 읽을
  때는 지어내지 않고 `None` 을 넘긴다 — 그러면 검사 자체가 건너뛰어진다.

  같은 폴더가 여러 파일의 조상이므로 한 번 훑는 동안 조회를 재사용한다.

### 6.2 문서 종류를 세 소스에서 같게

**[확인]** Drive 는 `SELECTABLE_MIME_TYPES` 네 개(Google Doc / `text/plain` /
`text/markdown` / `application/json`)만 통과시킨다. 게이트도 mime 만 보고 확장자는 보지
않아 `application/octet-stream` 으로 온 `.md` 는 거부된다.

**명세** — mime 이 텍스트이거나 **확장자가 텍스트 계열**이면 읽고, 내용이 실제 바이너리면
UTF-8 디코드 실패를 정직한 "미지원" 으로 처리한다. 허용 목록이 **어댑터와 게이트 두 곳에
나뉘어 있으므로 함께** 고친다.

**[구현됨]** `core/artifacts/text_files.py` 하나가 표를 갖고 네 곳이 그것을 본다 —
세 커넥터와 게이트다. `dependency_files` 와 같은 이유다.

발견한 것이 명세보다 넓었다.

| | 예전 | 지금 |
|---|---|---|
| GitHub · Local | **같은 표를 각자 복사**해 들고 있었다 | 한 곳에서 온다 |
| Drive | 표가 없어 의존성이 아닌 것은 **전부 문서**였다 — `main.py` 도 | 같은 표를 본다 |
| 목록 범위 | `.py .js .ts .java .go .c .h .cpp .rs` / `.md .txt .rst` | `.yaml`·`.csv`·`.json`·`.sh`·`.sql` 등 포함 |
| Drive 읽기 문 | 고정 mime 네 개. `text/x-python` 도 떨어졌다 | `text/*` 전부 + 이름 |
| GitHub 디코드 | `errors="replace"` — 바이너리가 **깨진 글자로 통과** | `utf-8-sig` 엄격, 실패는 "미지원" |

**뒤집어도 되는 mime 과 아닌 mime 을 가른다.** `application/octet-stream` 은 "무엇인지
말하지 않겠다" 이므로 이름이 대신 판단한다. `image/png` 은 **이미지라고 주장하는 것**이라
뒤집지 않는다 — 그것을 이름 추측으로 덮으면 확장자만 바꿔 게이트를 지나갈 수 있다.

**라이선스 전문 파일은 어느 쪽도 아니다** (결함 26). `LICENSE` 는 확장자가 없어
`UNKNOWN` 이었고 `LICENSE.txt` 는 `.txt` 라 **특허 경로**를 탔다. 이름 하나 차이로
KIPRIS 를 11 회쯤 쓰고, 나오는 것은 라이선스 전문에서 찾은 특허 유사도다. 원문 대조를
유예했으므로 (§5.9) 지금은 할 말이 없는 것이 맞고, 세 소스 모두 `UNKNOWN` 으로 둔다.

폴더 마운트가 열리기 전에 들어가야 한다. 폴더 안의 `.py`·`.csv`·`.yaml` 이 조용히 빠지면
§6.1 의 "폴더 안은 소유자를 구별하지 않고 전부 검사한다" 와 동작이 어긋난다.

### 6.3 아티팩트 이름 규칙 통일

**[확인]** 같은 artifact 에 이름을 붙이는 곳이 둘인데 서로 다르다.

| 어디서 | `display_name` |
|---|---|
| 마운트 (`github/adapter.py:225`) | 경로의 **마지막 조각** |
| push (`github/webhook_processor.py:158`) | `file.filename` = **전체 경로** |

실패하지는 않는다(등록이 갱신하고 `display_name` 은 불변 조건이 아니다). 다만 하위 폴더
파일의 이름이 첫 push 이후 바뀐다.

**명세** — 한 규칙으로 모은다. `logical_path` 가 이미 폴더를 들고 있으므로
`display_name` 에 폴더가 없어도 트리는 나온다.

**[구현됨]** `core/artifacts/naming.py` 의 `display_name_for()` 하나를 **다섯 곳**이
부른다. 명세가 둘이라고 했는데 실제로는 다섯이었다 — GitHub 마운트·push·이름 변경,
Local 두 곳, Drive 두 곳이다. 구분자는 둘 다 받는다. Local 은 기기가 보낸 상대 경로를
그대로 넘기고 **윈도우 기기는 역슬래시**를 쓴다.

빈 값을 그럴듯한 것으로 바꾸지 않는다. 이름을 지어내면 부르는 쪽의 `require_non_empty`
가 영영 통과한다.

시험이 `connectors/` 를 훑어 **규칙을 옮겨 적은 곳이 있으면 실패한다.** 값이 같을 때
복사본은 조용하고, 한쪽만 고칠 때 갈라지기 때문이다.

### 6.4 분할(segmentation)을 아티팩트 종류에 맞춘다 — 최우선

**[확인·재현]** 커넥터 셋이 종류를 가리지 않고 `split_document` 를 적용하고
`LicenseAnalyzer` 가 조각마다 파서를 부른다.

| 파일 | 통짜 | 조각 경유 |
|---|---|---|
| `pyproject.toml` | 20 | **3** |
| `package.json` | 1 | **0** |

그리고 뒤가 더 나쁘다 — 확인한 연쇄:

```
의존성 0건 → succeeded([]) → coverage COMPLETE
  → analysis_is_authoritative = True (core/risk/transitions.py:50)
  → _reconcile 실행, 후보 0건 → 기존 라이선스 Risk 전부 RESOLVED
```

**위험을 놓치는 것이 아니라 "위험이 해소되었다" 고 적극적으로 오보한다.** 지속 추적을
정면으로 부순다.

E2E 가 통과한 이유 — `samples/license/**` 가 351 바이트라 조각이 1 개였고
`requirements.txt` 는 줄 지향이라 우연히 살아남았다.

**명세** — 의존성 파일은 **통짜로** 분석기에 넘긴다. 분할은 문서·소스 코드에만 적용한다
(줄 범위·인용 구간이 필요한 것은 그쪽이다).

**그런데 조각화를 고쳐도 같은 결말에 이르는 경로가 셋 더 있다.** 넷을 함께 닫지 않으면
하나를 막고 나머지로 흘러간다.

### 6.5 손실 경로 2 — redaction 이 의존성 선언을 망가뜨린다

**[확인·재현]** 게이트의 비밀 마스킹이 **패키지 이름**에 걸린다. 마스킹 규칙이
`secret|token|credential|password|api[_-]?key|...` 어휘를 보는데, 이것이 실제 패키지
이름과 겹친다.

```
[project]
dependencies = ["httpx==0.28.1", "secret==1.0.0", "pydantic==2.13.4"]
   → redact → '"secret=[REDACTED_SECRET],'   ← 닫는 따옴표가 먹혔다
   → TOML 파싱 실패 → 3건 → 0건
```

**드문 이름이 아니다.** 실측으로 확인한 손상:

| 줄 | 원본 | redact 후 |
|---|---|---|
| `tokenizers==0.15.0` | `('tokenizers', '0.15.0')` | `('tokenizers', **None**)` |
| `secretstorage==3.3.3` | `('secretstorage', '3.3.3')` | `('secretstorage', **None**)` |

`tokenizers` 는 HuggingFace 를 쓰는 거의 모든 프로젝트에 있고 `secretstorage` 는
`keyring` 의 의존성이다.

**두 가지로 나빠진다.** TOML·JSON 처럼 구조가 있는 형식은 **파일 전체가 0 건**이 되고,
줄 지향 형식은 버전을 잃어 `EXACT_PIN` → `RANGE` 로 떨어진다. 버전이 `None` 이면
deps.dev 조회를 건너뛰고 **레지스트리 최신 버전의 라이선스로 판정**한다.

**명세** — 의존성 artifact 에서는 마스킹을 **파싱 안전한 형태**로 한다(따옴표·구분자
보존). 또는 의존성 선언 섹션을 마스킹 대상에서 뺀다. 매니페스트에 실린 것은 이름과
버전이지 비밀이 아니다.

### 6.6 손실 경로 3 — 파서가 "못 읽었다" 와 "없다" 를 구분하지 않는다

**[확인·재현]** 파서 전부가 깨진 입력을 삼키고 빈 목록을 돌려준다.

```
pyproject      깨진 TOML  → []   (예외 없음)
package.json   깨진 JSON  → []   (예외 없음)
poetry.lock    깨진 TOML  → []   (예외 없음)
```

그래서 **잘린 JSON 과 "의존성이 없는 파일" 이 구분되지 않는다.** 그리고 §6.4 의 연쇄가
"없다" 를 권위 있는 사실로 받아 기존 Risk 를 닫는다.

**명세** — 파서 반환을 **"읽었는데 없었다" / "못 읽었다"** 로 쪼갠다. 후자는 성공이
아니다. 파싱 실패·절단·미인식은 전부 `PARTIAL` 로 가고 **해소 권한을 갖지 않는다**
(§7.2).

### 6.7 손실 경로 4 — 게이트가 자른 것을 분석기가 모른다

**[확인]** `content_scope` 가 계약에 있고 게이트가 채워 보내는데
**`intelligence/` 전체에서 참조가 0 건**이다. 게이트가 바이트 상한으로 입력을 잘라도
분석기는 온전한 파일로 알고 파싱한다.

**명세** — 의존성 artifact 는 잘린 입력으로 판정하지 않는다. `content_scope` 가 온전하지
않으면 `PARTIAL` 이다. 아울러 락파일은 크므로 의존성 종류에 한해 바이트 상한 특례가
필요하다.

### 6.8 인식 목록의 구멍

**[확인]** 이 저장소 자신의 `requirements.lock` 이 `dependency_format()` 에 없다.
**기존 `requirements` 파서로 그대로 읽으면 68 건**이 나오는데 지금은 한 건도 안 보인다.

**명세** — 인식 목록에 `requirements.lock`, `constraints.txt`, 하위 경로의
`requirements/*.txt` 를 더한다. 형식은 이미 읽을 수 있는 것들이다.

함께 볼 것 — `requirements` 계열 파서는 `EXACT_PIN` 을 내는데 잠금 파일은 `LOCKFILE`
이어야 한다. 지금 두 값이 동률이라 먼저 온 쪽이 이긴다. 형식과 resolution 의 대응을
함께 정리한다.

## 7. Risk 수명주기 명세

### 7.1 추적에서 벗어난 artifact 의 Risk 를 닫는다

**[확인]** `exclude_artifact_risks` 를 부르는 곳은 수동 "추적 해제" 하나뿐
(`public_facade/service.py:356`). DELETE 변경은 이벤트를 곧바로 `DONE` 으로 둔다
(`process_change/service.py:163`). **파일을 지워도 그 Risk 는 활성 목록에 남는다.**

**명세** — 경로 하나로 모은다. **삭제 · 폴더 이탈 · 접근 상실**이 모두 이리로 들어간다.

**재진입 되살리기는 새 경로다 [확인].** `should_revive` 를 부르는 곳은
`risk_reconcile/service.py:304` 하나뿐이고 그 자리는 `_reconcile` 안, 즉
`analysis_is_authoritative` 게이트 **뒤**다. 분석 결과가 있어야만 닿는다. "분석 없이
되살린다" 를 하려면 reconcile 밖에 되살리기 경로를 새로 만들어야 하고, 그것이
`risk_exclusion.py` 의 반대 연산을 쓴다. **1-D 는 "기존 코드에 붙이기" 가 아니다.**

* 판본이 그대로면 — 분석 없이 되살린다. 새 경로가 한다.
* 판본이 달라졌으면 — fingerprint 가 달라지므로 평소의 변경 경로가 돈다.

**[확인] 되살릴 때 사람의 처분이 사라진다** — `decide_exclusion`
(`core/risk/transitions.py:149-163`)이 이전 처분이 무엇이든 `EXCLUDED` 로 덮고,
`should_revive` 는 되살릴지 여부만 답한다. 되살아난 Risk 는 `NEW`/`UNREVIEWED` 로 돌아간다.

지금은 이것이 안전하다. 부르는 곳이 수동 "추적 해제" 하나뿐이라 **사용자가 방금 스스로
한 일**이기 때문이다. 그런데 이 절이 방아쇠를 **삭제 · 폴더 이탈**로 넓힌다. 파일을 잠깐
옮겼다 되돌리는 흔한 일에 **사용자가 검토해 수용한 판단이 조용히 지워진다.**

**명세** — 제외할 때 이전 처분을 남기고 되살릴 때 복원한다. 재료는 이미 있다 —
`ExclusionDecision.previous_disposition` 이 값을 들고 있고 `risk_exclusion.py:46` 이
이벤트에 적기까지 한다. 읽어 되돌리는 쪽이 없을 뿐이다. 판본이 그대로면 처분도 그대로다.
판본이 달라졌으면 재분석이 도는 평소 경로이므로 §7.3 의 "사람이 처분한 Risk 의 하향은
되묻는다" 가 받는다.

**[결정] 이것은 `RISK_DISPOSITION_POLICY.md` 를 개정한다.** 그 문서는 "제외되어 있던
동안의 판단은 더 이상 유효하지 않으므로 처음 본 것처럼 다시 시작한다" 고 적는다. 그 규칙은
방아쇠가 **수동 "추적 해제" 하나뿐일 때** 옳았다 — 사용자가 스스로 그만둔 것이므로 다시
시작하는 것이 맞다. 방아쇠가 삭제·폴더 이탈로 넓어지면 전제가 깨진다.

개정 내용 — **판본이 같으면 처분을 복원하고, 다르면 지금처럼 `NEW`/`UNREVIEWED` 로
시작한다.** "제외되어 있던 동안 세상이 달라졌다" 는 근거는 판본이 달라진 경우에만
성립하므로, 규칙을 판본에 걸면 원래 의도가 그대로 유지된다. 1-D 는 **정책 문서 개정을
포함한다.**

이것이 `docs/INTEGRATION_V1_CROSSCHECK.md` 1 번(감시를 재개해도 Risk 가 되살아나지
않는다)을 함께 닫는다. **선행 조건이 아니라 같은 작업이다.**

### 7.2 `PARTIAL` 의 의미를 좁힌다

**[확인]** `_attach_reference_evidence` 가 RAG 예외에서 coverage 를 PARTIAL 로 낮추고,
`risk_reconcile/service.py:196` 이 `analysis_is_authoritative(SUCCEEDED, COMPLETE)` 안에서만
`_reconcile` 을 부른다. **RAG 가 죽으면 표가 낸 판정도 함께 버려진다.**

`explanation.py` 머리말의 "두 기능이 모두 실패해도 정책 결과는 그대로 남는다" 는 canonical
계층에서 사실이 아니다.

**명세** — `PARTIAL` 을 **"해소 권한 없음"** 으로 좁힌다. Risk 생성·근거 저장·이력 기록은
허용하고, **후보 부재로 인한 RESOLVED 만** 막는다. 부분성은 근거 행 자체에 표시한다.

이것 없이는 RAG 를 판정 경로에 넣을 수 없다. 장애가 곧 전면 정지가 된다.

### 7.3 하향을 보이게 만든다

위험이 한 방향으로 쏠려 있다.

* 틀린 **상향** — 검토자 시간을 쓴다. 화면에 보인다.
* 틀린 **하향** — 알림 0 건, `RESOLVED` 이력이 `evidence_refs=()` 로 근거 없이 남고,
  `NO_ACTION` 은 Risk 자체가 만들어지지 않는다. **소리 없이 사라진다.**

**명세**

* 하향(해소·등급 강등) 알림을 추가한다.
* `RESOLVED` 이력에 **근거를 싣는다.**
* 사람이 처분한 Risk(`MONITORING` / `ACCEPTED_RISK`)의 하향은 **되묻는다.**
* 하향 전부에 관문을 두지는 않는다 — 정상적인 의존성 제거까지 검토 대기에 쌓인다.

### 7.4 변화 원인 귀속

§1.2 (A) 의 네 원인을 구분해 기록한다. **재료가 셋은 있고 하나는 없다 [확인].**

| 원인 | 지문 | 지금 저장되는가 |
|---|---|---|
| 우리 지식 | `policy_version` · `rag_corpus_version` | **예** — `AnalysisOutcome` 에 있다 |
| 모델 | `model_id` · `prompt_version` | **예** — 같은 자리 |
| 외부 사실 | 패키지 메타데이터 · 라이선스 표현식 | 판정 결과로 남는다 |
| **입력** | `analysis_input_checksum` | **아니다** |

`analysis_input_checksum` 은 게이트가 계산해 `AnalysisArtifact.security_context` 에만 싣고
특허 추출 캐시 키로만 쓰인다. `persistence/**` 전체에 **0 건**이다. 비슷해 보이는
`ArtifactState.latest_checksum` 은 **원본 소스 체크섬**이라 다른 값이다 — redaction 도
분석기 라우팅도 `content_scope` 도 반영하지 않는다.

**이것이 §1.2 (A) 의 가운데 줄을 막는다.** "우리는 가만있었는데 위험이 생겼다" 를 말하려면
입력이 그대로였음을 보여야 하는데 그 값이 남지 않는다. 이 제품이 판다고 한 바로 그것이다.
§8.1 의 0-L 판별식도 같은 값을 쓴다.

**명세** — `analysis_input_checksum` 을 판정과 함께 저장하고, 직전 판정을 찾는 질의 경로를
만든다. 3-B 는 "이미 있는 재료를 조합하는 일" 이 아니다.

**명세** — 판정이 바뀔 때 어느 지문이 달라졌는지 판별해 이력에 남기고 화면에 표시한다.
"등급이 바뀌었다" 가 아니라 **"왜 바뀌었는지"** 를 답한다.

**사용자 설정과 우리 표를 가른다** — 둘 다 `policy_version` 을 바꾸므로 지문 하나로는
구분되지 않는다. §5.10 의 세 조각(`{workspace}:{정책표 판본}:{배포형태축 해시}`)에서 어느
조각이 달라졌는지를 본다. 가운데가 바뀌면 "판단 기준이 좋아졌다", 끝이 바뀌면 **"당신이
배포 형태를 바꿨다"** 다. 사용자에게는 전혀 다른 문장이고, 뒤쪽은 §1.2 의 네 원인 어디에도
없던 다섯 번째다.

### 7.6 외부 사실 변화는 무엇이 촉발하는가 — 지금은 아무것도 없다

§1.2 (A) 는 네 원인 중 **가운데 줄이 이 제품이 파는 것**이라고 적었다. "우리는 가만있었는데
위험이 생겼다" — 의존성은 그대로인데 그 패키지가 라이선스를 바꾼 경우다. Redis · Elastic ·
MongoDB · HashiCorp 가 실제로 한 일이다.

**[확인] 그것을 촉발하는 것이 없다.**

분석은 **변경 이벤트**에서만 시작한다. 예약 작업은 넷뿐이고(`deploy/scheduler-jobs.yaml`)
Drive watch 갱신 · Drive 대조 · 만료 상태 정리 · 소스 상태 갱신이다. **어느 것도 내용이
그대로인 의존성 파일을 다시 분석하지 않는다.** `request_reanalysis` 는 있으나
`change_event_id` 를 받는 사람 손 경로다(`api/security/router.py:182`).

귀결 — `requirements.txt` 를 여섯 달 안 건드리면 그 안의 패키지가 MIT 에서 BUSL-1.1 로
바뀌어도 **우리는 모른다.**

**부분적인 완화가 있기는 하다.** 분석기는 파일이 바뀌면 그 안의 **모든 선언**을 다시
평가하므로, 다른 이유로 매니페스트가 한 줄이라도 바뀌면 그때 함께 잡힌다. 패키지
메타데이터에는 캐시가 없어(`package_metadata.py`) 매번 새로 조회한다. 즉 **재료는 다
있고 방아쇠만 없다.**

**명세** — 추적 중인 의존성 아티팩트를 **주기적으로 다시 평가한다.**

* 파일이 아니라 **패키지 메타데이터**가 대상이다. 파일은 그대로이므로
  `analysis_input_checksum` 도 그대로이고, 그래서 §7.4 가 원인을 **"외부 사실"** 로
  정확히 귀속할 수 있다 — 입력이 같은데 결과가 달라진 것이 그 뜻이다.
* 주기는 [미결] (§13-9). 라이선스 변경은 드물지만 늦게 알수록 손해가 크다.
* KIPRIS 를 쓰지 않는 경로라 비용은 레지스트리 조회뿐이다. 다만 조회 수가 의존성 수에
  비례하므로 **2-F 의 캐시가 선행**이다.
* 이것이 §1.2 (A) 를 실제로 성립시키는 유일한 작업이다. 없으면 그 논거는 **말뿐이다.**

### 7.5 Risk 정체성 [결정 D10]

현행 유지한다. 라이선스가 바뀌면 key 가 바뀌어 흐름이 끊기지만, **파일 단위로 묶어
표시**하므로 "이 파일에 라이선스 위험이 있다" 는 흐름은 이어진다. 해소 추적은 artifact
로그로 되짚는다.

정체성을 좁히는 것은 [유예] (§12.2) — `risk_id` 가 key 해시라 기존 문서 id 가 전부
바뀌고, 마이그레이션 없이는 사용자 처분과 검토 이력이 유실된다.

### 8.1 조용한 해소로 가는 길이 넷이다

1·14·15·16 은 **서로 독립적으로** 같은 결말에 이른다.

```
조각화(1) │ redaction(14) │ 파싱 실패 삼킴(15) │ 게이트 절단(16)
                          ↓
                   의존성 0 건
                          ↓
        succeeded([]) → coverage COMPLETE → 권위 있는 결과
                          ↓
            기존 라이선스 Risk 전부 RESOLVED · 알림 0 건
```

**하나만 막으면 나머지로 흘러간다.** 그런데 여기서 방벽을 잘못 세우기 쉽다 — 위 그림이
말하듯 네 경로는 전부 **`COMPLETE` 로 끝난다.** `PARTIAL` 을 어떻게 손봐도 `COMPLETE` 로
들어온 0 건은 막지 못한다.

방벽은 두 층이고, 한 층만으로는 서지 않는다.

| 층 | 무엇을 하는가 | 항목 |
|---|---|---|
| 분류 | 망가지거나 잘린 읽기를 **`COMPLETE` 가 아니게** 만든다 | 0-C · 0-D |
| 처분 | `PARTIAL` 이 판정을 버리지 않되 **해소도 못 하게** 한다 | 0-E |

0-C·0-D 없이 0-E 만 넣으면 아무것도 막히지 않는다. 반대로 0-E 없이 0-C·0-D 만 넣으면
분류는 맞는데 `PARTIAL` 이 결정론적 판정까지 함께 버린다 (§7.2).

**그리고 경로와 무관한 방벽을 따로 둔다** — 의존성 아티팩트에서 후보가 **N>0 에서 0 으로
떨어지는 전이는 그 자체로 권위를 갖지 못한다** (0-L). coverage 가 무엇이든 걸리므로 넷 중
어느 것을 놓쳐도, 아직 모르는 다섯 번째 경로가 있어도 잘못된 해소는 일어나지 않는다.
**판별식** — "정상적으로 지워진 것" 을 무엇으로 아는가. 방향만 적으면 구현이 갈리므로
규칙으로 적는다.

| 무엇이 참인가 | 후보 0 건이 권위를 갖는가 |
|---|---|
| `analysis_input_checksum` 이 **그대로**다 | **아니다.** 같은 입력에서 다른 출력이 나온 것이므로 판단 기준이 바뀌었거나 우리 결함이다 |
| 체크섬이 달라졌고, 파서가 **선언 구역을 읽고 비어 있음을 확인**했다 | **그렇다.** 사람이 의존성을 지운 것이다 |
| 체크섬이 달라졌으나 파서가 못 읽었거나 구역을 찾지 못했다 | **아니다.** §6.6 이 이 둘을 가르는 일을 한다 |
| 파일 자체가 사라졌다 | 0-L 의 일이 아니다. §7.1 의 경로로 간다 |

첫 줄이 가장 값싸다. **입력이 같은데 결과가 달라졌다면 원인은 언제나 우리 쪽에 있다.**
다만 지금은 쓸 수 없다 — `analysis_input_checksum` 이 저장되지 않는다 (§7.4). 2 걸음은 그
저장을 포함한다.
그러나 이것만으로는 부족하다 — 네 손실 경로는 파일이 **바뀐 뒤** 재분석에서도 터지고, 그때는
체크섬도 함께 달라져 첫 줄에 걸리지 않는다. 둘째·셋째 줄을 가르려면 파서가 "못 읽었다" 와
"없다" 를 구분해야 하므로 **완전한 판별식은 §6.6(0-C)을 기다린다.**

**그래서 0-L 은 두 걸음이다. 막는 쪽은 기다릴 필요가 없다.**

1. **지금** — 의존성 아티팩트의 N>0 → 0 전이는 **예외 없이** 권위를 갖지 못한다. 사람이
   실제로 지운 경우까지 함께 막히므로, 해소되어야 할 Risk 가 열린 채 남는다. 그것은 눈에
   보이는 과경보이지 **조용한 유실이 아니다** (§7.3 의 비대칭).
2. **0-C 이후** — 위 표의 둘째 줄을 되살려 정상적인 제거는 해소되게 한다.

1 번을 먼저 두는 이유는 규칙 한 줄이고 **네 손실 경로를 그날로 멈추기** 때문이다.

**순서 규칙**

1. **0-L 이 가장 먼저다.** 규칙 하나이고, 나머지를 고치는 동안 잘못된 해소를 즉시 멈춘다.
2. 그다음이 **1·14·15·16**(0-A·0-B·0-C·0-D). 지금 운영 데이터를 잘못 만들고 있고, 서로
   독립이라 함께 닫아야 한다. 0-E 는 0-C·0-D 와 짝이므로 같이 간다.
3. **2·3**(0-G·0-F)은 corpus 확대의 선행 조건이라 2 단계 전에만 끝나면 된다.

### 9.1 폴더 마운트를 열기 전에

**[확인]** 저장소·폴더를 마운트하면 추적 대상 파일마다 변경 이벤트가 하나씩 생기고, 문서·
소스는 특허 경로로 가 **파일당 Gemini 추출 1 + KIPRIS 검색 최대 5 + 상세 최대 6** 을 쓴다.
KIPRIS 무료 등급은 **월 1,000 회**다.

거를 수단 셋이 **모두 비어 있다.**

| 수단 | 걸리는 지점 | 현재 |
|---|---|---|
| 소스의 `.ipriskignore` | 변경 이벤트가 생기지 않는다 | 점검 저장소에만 |
| workspace `global_ignore_text` | 관문이 막아 provider 호출 없음 | 빈 문자열 |
| `include/exclude patterns` | 스코프 단계 | API 는 받는데 **프론트가 빈 배열** |

**[확인·실측] 그리고 셋이 서로 다른 매처를 쓴다.**

| 수단 | 구현 | 패턴이 안 맞으면 |
|---|---|---|
| source `.ipriskignore` | `connectors/common/ipriskignore.py` — `fnmatch(path, pattern)` | **조용히 0 개를 거른다** |
| workspace `global_ignore_text` | `application/security_gate/ignore.py` — 정규식 `fullmatch`, 선행 `/` 필수 | `POLICY_INVALID` 로 거부 |
| tracking scope `exclude_patterns` | `connectors/github/tracking_scope.py:26` — `fnmatch` | 조용히 0 개를 거른다 |

`/backend/node_modules/a/b.js` 로 실측한 결과다.

| 쓴 패턴 | `.ipriskignore` | workspace |
|---|---|---|
| `node_modules` | 안 거른다 | 오류 |
| `**/node_modules/**` | 안 거른다 | 오류 |
| `*node_modules/*` | **거른다** | 오류 |
| `/**/node_modules/**` | 안 거른다 | **거른다** |

**두 곳 모두에서 동작하는 문자열이 하나도 없다.** 그리고 사람이 가장 자연스럽게 적는
`node_modules` 는 어느 쪽에서도 안 걸린다 — 한쪽은 오류로 보이기라도 하지만
`.ipriskignore` 는 **조용히 아무것도 안 거른다.** 제외 목록을 적어 두고 다 걸러진다고
믿는 상태가 된다.

GitHub 은 추적 파일만 보므로 `.gitignore` 가 걸러 준다. **Local 은 디스크를 본다** —

**한도 안에 들어오는 유일한 조합**이 된다.

**명세** — 폴더 마운트를 열기 전에 세 가지를 함께 한다.

1. **매처를 하나로 통일한다.** 세 수단이 같은 문자열을 같게 해석해야 한다. 사람이
   `node_modules` 라고 적으면 세 곳 모두에서 걸려야 한다.
2. **안 맞는 패턴을 조용히 넘기지 않는다.** 어느 패턴도 아무것도 거르지 않았다면 그것을
   말한다. workspace 쪽이 오류로 거부하는 것이 옳은 방향이다.
3. **기본 제외 목록을 둔다** (`node_modules/`, `.venv/`, `dist/`, `vendor/` 등). 다만
   1 이 없으면 이 목록도 조용히 아무것도 안 거른다.

**[구현됨 — 1]** `core/security/ignore_patterns.py` 하나가 문법과 매칭을 정하고 세 수단이
그것을 부른다. 문법은 **gitignore** 다 — 파일 이름이 `.ipriskignore` 이고 사람들은
`.gitignore` 를 안다.

| | 지금 |
|---|---|
| `node_modules` | 세 곳 모두에서 걸린다. 어느 깊이에서나 |
| `**/node_modules/**` · `/**/node_modules/**` | 같이 걸린다 |
| `/` 를 품은 패턴 | 마운트 뿌리에 고정된다. `src/*.py` 는 `a/src/x.py` 를 안 거른다 |
| 끝의 `/` | 디렉터리를 뜻한다. `dist/` 는 `dist/a.js` 를 거르고 `dist` 라는 파일은 안 거른다 |
| `!` 부정 | 받지 않는다. 거르기 전용이라야 "이 패턴이 무엇을 걸렀는가" 를 줄 단위로 따질 수 있다 |
| 읽을 수 없는 줄 | **예외**다. 조용히 넘기면 목록을 적어 두고 걸러진다고 믿게 된다 |

**[결정] 패턴은 마운트 뿌리 기준이다. 별칭은 대조하지 않는다.**

예전 게이트는 별칭에 고정돼 있었다 — 마운트 별칭이 `Backend` 이면 `/backend/**` 가
맞았다. 그러면 **저장소가 스스로 쓴 `.ipriskignore` 는 게이트에서 영영 맞지 않는다.**
저장소 저자는 우리 마운트 별칭을 모른다. 실제로 같은 `.ipriskignore` 파일이 두 번
평가됐다 — 커넥터는 저장소 상대 경로로 `fnmatch`, 게이트는 별칭 포함 경로로 정규식.

별칭을 대조하면 **마운트 이름이 정책을 바꾼다.** 같은 문자열이 마운트를 갈아 끼우면
다르게 동작한다.

잃는 것이 있다. workspace 전역 목록에서 `/backend/**` 로 **특정 마운트만** 겨냥하던
방법이 없어진다. 그것은 마운트 자신의 `exclude_patterns` 가 있어야 할 자리다.

**[남음 — 2·3]** "아무것도 거르지 않은 패턴을 말한다" 는 마운트 훑기 단위로 세어야 하고,
기본 목록(`DEFAULT_IGNORE_PATTERNS`)은 정의만 해 두고 아직 어디에도 걸지 않았다. 어디에
거는지가 동작을 크게 바꾸므로 폴더 마운트(1-F)와 함께 정한다.

### 9.2 캐시

**[확인]** 재검사 비용은 이미 0 에 가깝다 — 추출 캐시(내용 체크섬 키)와 출원번호 캐시가
받는다. S3 실측에서 KIPRIS 실호출 0 회를 확인했다.

**처음 보는 파일의 비용은 그대로다.** 그것을 §9.1 이 막는다.

**명세 [결정]** — 라이선스 쪽에도 같은 구조를 둔다. 4 단계 조항 검색은 **라이선스 단위**로
캐시한다. 같은 라이선스가 여러 패키지에 반복되므로 이득이 크다.

키는 넷이다.

```
(정규화된 표현식, 판정, corpus 버전, 배포형태축 해시)
```

**corpus 버전을 키에 넣지, 갱신 때 캐시를 지우지 않는다.** 같은 결과를 내면서 세 가지가
낫다 — 지우는 절차가 없으니 **무효화 실패라는 실패 모드가 없고**, corpus 를 되돌리면 옛
캐시가 그대로 살아 있어 **롤백이 싸며**, 두 판본을 나란히 두고 비교할 수 있다(§10 의
"이행 차이 수" 를 재는 자리다).

**배포형태축이 키에 없으면 안 된다.** §5.10 이후 질의는 workspace 설정에서 만들어지므로,
빠뜨리면 SaaS workspace 의 조항 결과가 사내 전용 workspace 에 그대로 서빙된다. D7 의
"워크스페이스는 서로 완전히 독립" 이 깨진다.

**이 캐시가 §7.6(주기적 재평가)의 선행이다.** 주기적으로 도는 조회는 의존성 수에 비례하고,
캐시 없이는 그 비용이 주기를 정하지 못하게 만든다.

### 9.3 큐 재시도

**[확인]** `maxAttempts: 8`, `maxRetryDuration: 86400s`. 백오프가 5→10→20→40→80→160→320
초라 실질 창은 **약 10 분**이다. 하루가 아니다.

`bfc615d` 로 사람이 손으로 되살릴 수 있게 되어 급한 정도는 줄었다. 값 조정은 배포 영역이다.

### 9.4 workspace 삭제가 끝나지 못한다

**[확인]** `deploy/iam-policy-contract.yaml` 이 런타임에 주는 Secret 권한은 셋뿐이다 —
`secretmanager.secrets.create`(project scope), `versions.add`, `versions.access`(뒤의 둘은
`iprisk-v2-cred-` prefix 조건). **`secrets.delete` 는 없다.** 파일 전체에 `secrets.delete`
가 0 건이다.

그런데 `gcp/secret_vault.py` 의 `delete()` 는 `delete_secret` 을 부르고 `NotFound` 만
잡는다. 권한 거부는 그대로 올라간다. 그리고 `gcp/operational_eraser.py:90-99` 의
`_erase_credential` 은 그 실패를 **일부러 올린다** — 주석이 이유를 적어 두었다:
"workspace 는 `DELETING` 으로 남아 다시 시도할 수 있고, 그것이 자격증명을 남기는 것보다
낫다."

의도는 옳은데 전제가 틀렸다. **다시 시도해도 권한이 없다.** 자격증명이 붙은 workspace 는
영영 지워지지 않고 `DELETING` 에서 재시도만 반복한다. 조용한 실패보다 나쁘다 — 실패가
눈에 보이는데 끝나지 않는다.

전에 고아 secret 19 개를 지운 적이 있으나 그것은 **사용자 자격증명**으로 한 것이라 런타임
권한을 증명하지 않는다.

**명세** — 배포 영역이다. 문서 표시로 닫히지 않는다.

1. 실제 IAM 에 무엇이 붙어 있는지 **먼저 확인한다.** 계약 파일과 실제 정책이 다를 수 있다.
2. 없으면 런타임 SA 에 `secretmanager.secrets.delete` 를 `iprisk-v2-cred-` prefix 조건으로
   붙인다. `secrets.create` 와 달리 삭제는 **존재하는 secret resource 에 대해 평가되므로**
   prefix 조건이 실제로 걸린다 (§12.1 이 인용한 create 의 한계가 여기엔 적용되지 않는다).
3. `deploy/iam-policy-contract.yaml` 의 표와 custom role 을 함께 고친다.
4. 고친 뒤 **자격증명이 붙은 workspace 를 실제로 지워** 끝나는지 본다. 계약 파일만 고치면
   같은 상태가 남는다.

**오부착률은 이제 재지 않는다.** 0-G 이후 게이트가 "문서가 판정을 이끈 leaf 를 덮으면
통과" 이고 오부착의 정의가 "통과했는데 그 leaf 를 안 덮는 것" 이라, **정의상 나올 수 없다.**
전수로 확인할 대상이 아니라 구조로 보장되는 값이 됐다.

**정답 집합은 대부분 공짜다.** SPDX 식별자라는 기계 판독 정답이 있고, 오답 질의는
`전체 정책표 − corpus 가 덮는 것` 으로 자동 생성된다. 사람 라벨이 필요한 것은 4 단계
조항 적합성뿐이다.

**하이브리드·re-rank 는 이 지표들이 존재한 다음에 넣는다.** 이 문장을 쓸 때는 corpus 가
2,120 바이트에 `top_k=3` 이라 검색이 사실상 전체 반환이었다. 지금은 675 편이므로 **검색이
실제로 고른다** — 그래서 이제부터는 좋아졌다고 말할 대상이 있다.

### 11.6 기존 데이터 이행

0 단계는 **이미 저장된 판정의 뜻을 바꾼다.** 그대로 두면 새 규칙으로 만든 것과 옛 규칙으로
만든 것이 한 목록에 섞이고, 그 섞임 자체가 §1.3 이 경고한 "틀린 판정이 기록으로 굳는" 것이다.

**[확인]** 새 마이그레이션 코드를 쓰지 않는다. 재분석이 이미 안전한 경로다 — 재분석은
`EXCLUDED` 만 되살리고 **사람의 처분은 덮지 않는다** (`RISK_DISPOSITION_POLICY.md` §5).

| 항목 | 옛 데이터에 무슨 일이 있었나 | 이행 |
|---|---|---|
| 0-A · 0-B · 0-C · 0-D | 선언이 통째로 또는 부분으로 사라져 **Risk 가 없거나 잘못 해소됨** | 재분석 |
| 0-F | `UNKNOWN` 으로 굳은 표현식은 **되살릴 수 없다** — 원문이 어디에도 없다 | 재분석 필수 |
| 0-G | 판정과 반대인 `LICENSE_REFERENCE` 근거 행이 남아 있음 | 재분석이 근거를 다시 씀 |
| 0-H | `rag_corpus_version=None` 인 15 건 | 재분석. **소급해 채울 수 없다** |
| 0-J | 인식 목록에 없어 **분석된 적이 없다.** Risk 가 만들어진 적도 없다 | 재분류 후 재분석. **재분석만으로는 닿지 않는다** |
| 0-K | 최신 버전의 라이선스가 그 버전의 것으로 기록됨 | 재분석 |

**명세**

* 0 단계 배포 뒤 **추적 중인 아티팩트 전체를 한 번 훑는다.** "지금 라이선스로 분류된
  것" 을 열거하면 0-J 가 새로 인식시키는 이름이 그 목록에 없어 §6.8 의 실종 68 건은 이행
  뒤에도 그대로 남는다. **훑을 대상을 고르는 기준이 유일한 관문**이므로 거기서 좁히지 않는다.

  **[확인] 별도의 재분류 단계는 필요 없다.** 게이트는 저장된 종류가 아니라
  `snapshot.artifact_kind` 를 보고(`security_gate/service.py:259,271,280,290,304`), 그 값은
  커넥터가 `fetch_snapshot` 안에서 매번 다시 정한다 (`github/adapter.py:164`,
  `google_drive/adapter.py:213`, `local/adapter.py:105`). 재분석하면 넓어진 인식 목록으로
  **자동으로 다시 분류된다.**

* **이행 작업은 `LICENSE` 만 요청한다.** `requested_analysis_types` 는 작업마다 정하는
  값이다 (`analysis_jobs/models.py:123`). 라이선스가 아닌 아티팩트는 게이트가 맡을 분석기를
  찾지 못해 사유를 붙여 끝내고, 그것은 실패가 아니다.

  **[확인] 이것이 없으면 KIPRIS 를 쓴다.** 검색 캐시 수명이 **7 일**이다
  (`patent/cache.py:64`). §9.2 가 재검사 비용 0 을 실측한 것은 직전 실행 직후였다. 이행이
  그보다 뒤에 돌면 문서마다 검색이 되살아나 파일당 최대 5 회를 쓴다. 추출 캐시(30 일)와
  상세 캐시(90 일)는 이것을 막지 못한다 — 막는 것은 검색 캐시뿐이다.

* 남는 비용은 Gemini 와 레지스트리 조회뿐이고, 그마저 캐시가 대부분 받는다 (§9.2).
* 이행으로 바뀐 판정은 §7.4 에서 원인을 **"우리 지식"** 으로 적는다. 사용자가 "왜 어제와
  다른가" 를 물을 때 답이 있어야 한다.
* 이행 전후로 **판정이 달라진 수를 센다.** 이 수가 0 단계가 실제로 무엇을 고쳤는지에 대한
  유일한 실측이고, §10 의 "원문 보존율 0% → 100%" 를 확인하는 자리다.
* 옛 이력을 **지우지 않는다.** 감사가 값이므로 판정만 갱신하고 기록은 남긴다.

**순서** — 이행은 0 단계 **전체가 끝난 뒤 한 번**이다. 항목마다 돌리면 같은 아티팩트를
여러 번 재분석하면서 그때마다 §7.4 가 원인을 적어 **원장이 우리 배포 일정으로 오염된다.**

**부분 이행** — 전부 성공하는 이행은 없다. 그리고 옛 규칙과 새 규칙이 한 목록에 섞인
상태가 §1.3 이 경고한 바로 그것이므로, 중간 상태를 **숨기지 않고 보이게** 둔다.

* workspace 에 **이행 판본**을 기록하고, 아티팩트마다 어디까지 이행됐는지 남긴다.
* 화면은 아직 이행되지 않은 Risk 를 **"옛 기준으로 판정됨"** 으로 표시한다. 조용히 섞으면
  사용자는 두 규칙의 결과를 같은 것으로 읽는다.
* **몇 번 돌려도 같은 결과여야 한다.** 그래야 재개가 "남은 목록을 다시 훑는 것" 으로 끝난다.
  실패한 것만 다시 태우고, 이미 이행된 것은 다시 건드리지 않는다.
* 이행이 끝나기 전에는 §10 의 "이행 차이 수" 를 확정하지 않는다. 부분 집계는 0 단계가
  무엇을 고쳤는지에 대한 답이 되지 못한다.

### 12.1 계약 변경 — 한 번 연다 [결정]

**`ReviewPriority` 에 `INDETERMINATE` 를 더한다.** 이 명세가 계약을 여는 유일한 지점이고,
우회로를 찾지 못해서가 아니라 **우회로가 틀렸기 때문**이다.

`HIGH` 는 "심각하다" 이고 `INDETERMINATE` 는 "판정을 못 내렸다" 라 축이 다르다. 셋뿐인
칸에 넣으려면 어느 쪽으로든 틀린다 — 분류하지 않은 라이선스를 `MEDIUM` 에 두면 **강한
copyleft 가 중간으로 묻히고**(`CECILL`·`NPL` 이 실제로 그랬다), `HIGH` 에 두면 폰트
라이선스가 AGPL 과 같은 칸에 앉는다.

`uncertainty_flags` 에 표시를 넣고 화면에서만 4 번째처럼 보여 주는 우회도 있었으나 버렸다.
정렬도 필터도 안 되고, 무엇보다 **저장된 값이 여전히 `MEDIUM`** 이라 "그때 우리가 뭐라고
판단했나" 를 되짚을 때 원장이 거짓말을 한다. 원장이 이 제품이 파는 것이므로 그 값이 정확해야
한다.

순서는 `HIGH` 바로 아래다. 심각한 것이 먼저 보이고, 그다음이 "모르겠으니 봐 달라" 다.

**나머지는 그대로 계약을 요구하지 않는다.** [확인]

* `AnalysisVersions.policy_version` 이 **자유 문자열**이라 `ws-abc:license-policy:3` 형태로
  workspace 별 정책을 실을 수 있다.
* `LicenseCandidate.ecosystem` 도 **자유 문자열**이라 생태계 추가에 계약 변경이 필요 없다.

  저장 경계를 넘긴다. 이 경로를 쓰지 않으면 0-F 는 계약 변경 없이 불가능하다.

**[확인] 하향 알림도 계약 변경이 아니다.** `NotificationType` 은 `shared/contracts/**` 가

파이프라인은 §5.1 의 다섯 단계를 그대로 간다.

```
매니페스트 파싱 → 레지스트리 조회 → 전문 조회 → 조항 검색 → 권장 행동
```

**두 번째 단계가 준 이름을 그대로 믿는다.** 레지스트리가 `Apache-2.0` 이라 하면 그 패키지의
실제 `LICENSE` 파일을 보지 않고 `Apache-2.0` 의 전문을 가져와 판단한다.

**그래서 못 보는 것.**

* 표준 라이선스를 조금 고쳐 조항이 하나 더 붙은 경우
* 사내 라이선스에 비슷한 이름을 붙인 경우
* 벤더가 추가 조항을 넣은 경우

셋 다 실무에서 실제로 걸리는 것들이고, **메타데이터는 계속 표준 이름을 말한다.**

**왜 감수하는가** — 인식(어떤 파일이 라이선스 원문인가) · 라우팅(세 커넥터가 같게 봐야
한다) · 정규화 대조(공백·저작권 줄이 달라도 같은 라이선스로 봐야 한다) 셋이 다 필요하고,
이번 일정에 들어가지 않는다. **막고 있던 것은 이제 시간이지 corpus 가 아니다** — 대조 기준이
될 675 편은 이미 있다.

**전제** — 패키지 저자가 자기 라이선스를 정직하게 선언했다고 본다. 대부분 맞고, 틀릴 때
조용하다는 것이 이 위험의 성질이다.

**이것이 이름 기반 분류(§5.11)를 남기는 이유이기도 하다.** 원문 대조가 서면 이름은 검증된
전문을 가리키는 포인터가 되어 표의 성격이 달라지지만, 그때까지는 이름이 곧 근거다.

### 12.3 관찰만 하는 것

**게이트가 `/` 선행 경로를 내보낸다** — 지금 터지지 않는다. 특허 분석기가
`source_reference()` 로 떼고, License 는 경로를 reference 로 쓰지 않는다. 다만 소비자
한 곳에서 막고 있어, `logical_path` 를 보존 필드에 쓰는 코드가 새로 생기면 다시 밟는다.

**파일을 옮기면 GitHub 은 삭제+생성으로 본다** — `source_artifact_id` 가 경로를 담고 있어
저장소 안에서 파일을 옮기면 다른 artifact 가 된다. Drive 는 파일 id 라 옮겨도 같은
artifact 다. 그래서 §7.1 의 "판본이 그대로면 분석 없이 되살린다" 는 **같은
`source_artifact_id` 안에서만** 성립하고, GitHub 에서 그것은 같은 경로를 뜻한다. 1-D 의
완료 조건도 이 범위로 읽는다. 지금 정체성을 고치지 않는 이유는 §7.5 와 같은 마이그레이션
위험을 지기 때문이다.

**`RiskEvent` 는 hash chain 이 아니다** — append-only 이지만 암호학적 사슬은 만들지 않았다.
`CODING_AGENT_SPEC_1` 이 권장만 했고 끝내 구현하지 않았다. **§1.3 이 말한 "원장" 의 값은
여기까지다.** 우리 저장소를 신뢰하는 사람에게는 온전한 이력이지만, 변조를 증명해야 하는
자리에서는 사슬이 없다는 사실이 먼저 나온다. 대외 주장에 쓰기 전에 알고 있어야 한다.

**나머지 관찰 항목** — 전부 의도한 생략이고 각각 이유가 있다.

* signed offset pagination 은 live write 중 native cursor 와 다르게 동작한다.
* Dashboard 의 failed count 는 canonical read 다. scale 근거 없이 projection 을 두지 않았다.
* Risk 목록 캐시는 request scope 다.
* session version 과 global ignore 의 backfill 은 legacy 데이터가 있을 때만 필요하다.

## 13. 미결

1. **서비스 계정 변경 피드가 이탈·재진입을 주는가** (§6.1). 설계 규모가 여기서 정해진다.
2. **타깃 고객.** SaaS 스타트업 / 국내 SI·제조 / M&A 실사 중 어디냐에 따라 2 단계 안의
   우선순위가 바뀐다. 0·1 단계는 어느 쪽이든 같다.
3. **corpus 갱신 주기와 검토 주체.** 누가 diff 를 승인하는가.
4. **기본 제외 목록의 내용** (§9.1).
5. `manifest.yaml` 의 `corpus_version`(`2026-08-14.1`)과 배포 환경변수(`2026-08-21.1`)가
   다르다. 어느 쪽이 실제로 올라간 corpus 인가. **[확인]** 배포 검증기가 강제하는 쪽은
   manifest 값이다 (§5.4).
6. **예외가 의무를 완화하는 표를 누가 채우는가** (§5.3). SPDX 는 예외 **목록**만 주고
   효과는 주지 않는다. Classpath · GCC · LLVM 처럼 널리 쓰이는 것부터 손으로 채우게 된다.
7. **근거의 수명을 어떻게 정하는가** (§5.6, 결함 22). `clear_evidence` 가 같은 작업이 넣은
   행만 지우므로 옛 corpus 판본에서 나온 근거가 현재 판정에 계속 붙어 있다. 0-H 는 기록만
   보장하고 이것을 닫지 않는다. 확인 방법 — 한 Risk 의 작업 `rag_corpus_version` 과 그
   근거 행의 `metadata_safe` 를 함께 읽는다.
8. **외부 사실 재평가의 주기** (§7.6). 라이선스 변경은 드물지만 늦게 알수록 손해가 크다.
   하루인지 주 단위인지, workspace 마다 다르게 둘지.
9. **배포 형태 설정을 어느 자리에서 받는가** (§5.10).
10. **`UNKNOWN` 식별자를 로그에 남겨도 되는가** (§5.11). 실제 분포를 알아야 무엇을 분류할지
    정해지는데, SPDX 식별자는 공개 문자열이면서도 사용자가 무엇에 의존하는지를 간접적으로
    드러낸다. 0-I 가 이미 남기는 `dependency_format` 과 같은 부류로 볼 것인가. 등급을 매기지 않기로 한 것은
   정해졌고, 남은 것은 유도 시점이다 — 마운트할 때인지, 첫 라이선스 Risk 가 나올 때인지,
   workspace 를 만들 때인지.

절에는 대체 표시가 붙어 있다. 표시된 절은 **그때의 결정을 읽는 기록**이고, 무엇을 만들지는
이 문서에서 읽는다. 뒤집힌 본문을 지우지 않은 이유가 그것이다 — 무엇이 왜 바뀌었는지를
보려면 양쪽이 다 있어야 한다.

**`docs/DEVELOPMENT_PROGRESS.md` 가 진행 상황을 든다.** 이 명세가 "무엇을·왜" 라면 그쪽은
"어디까지·다음은" 이다. 끝난 항목을 이 문서에서 지우지 않는 이유가 그것이다 — 왜 그렇게
만들었는지는 여기 남아야 한다. 진행 문서는 **규범이 아니다.**

**추적 세션 소유 문서 둘은 이 명세가 고치지 않는다.** §11.5 의 완료 조건이 기대는 재현
절차가 `V3_DEVELOPMENT_WATCH.md` 에 있으므로 지우거나 번호를 다시 매기지 않는다.
