# 최종 고도화 구상 — 특허 외 영역 (라이선스 · FinOps · CI/CD · 보안 감사)

> 성격: **가벼운 구상 문서.** 특허 고도화(`PATENT_RAG_ENHANCEMENT_PLAN.md`)에서
> 확립한 방법론을 나머지 영역에 수평 전개할 때 무엇이 가능한지를 정리한다.
> 구현 착수 전 우선순위·범위는 사용자와 확정한다.
>
> 전제: `final_docs/FINAL_PLAN.md`(1-A~3-E)의 골격 위에, 최종 단계에서 바뀐
> 지침을 반영한다 — ① KIPRIS 유료(월 한도 서사 폐기) ② 계약 강제성 완화(허락
> 후 변경 가능) ③ 골든 데이터셋 존재 ④ "평가 방법과 선택 근거"가 점수의 본체
> ⑤ 기능 브랜치 워크플로.

## 0. 특허에서 확립한 패턴 — 수평 전개의 도구 상자

특허 고도화가 남긴 것은 코드만이 아니라 **재사용 가능한 방법**이다.

| 패턴 | 특허에서의 실체 | 다른 영역 적용 |
|---|---|---|
| 전략 스위치 뒤 베이스라인 병존 | `PATENT_*_STRATEGY`, 기본값=현행, 기존 테스트 무수정 통과가 보존 증거 | 라이선스 원문 대조·등급표 변경도 같은 틀로 |
| 정답 기반 평가 | 심사관 인용 = 검색 정답, 지표 4층(R/C/G/$) | 라이선스: SPDX 식별자가 이미 기계 정답, 사람 라벨은 조항 적합성뿐(§10) |
| 실측 우선(probe) | docsCount 무시·pageNo 실측 발견 → 코드 보정 | IAM live-diff, 비용 실측, 스모크 |
| 관측 로그 → 지표 | gemini_usage·kipris_call 등 병합 완료 | FinOps 집계의 원료가 이미 흐르고 있음 |

## 1. 라이선스 리스크 분석 고도화

**현황**: 5단계 파이프라인 완성(파싱→레지스트리→전문→조항 검색→권장), SPDX
727 어휘·226 분류, corpus 675편(커버리지 113/113), leading-leaf 게이트로 오부착
구조적 0, 조항 캐시(4원 키), 일 1회 재평가. 유예: LICENSE 원문 대조(T2),
copyleft 23종, 배포 형태 축의 등급표 반영(결함 34), 사용자 추가 질의.

### 1-L1. LICENSE 원문 대조 (T2 유예 해제) — 1순위 후보

- **왜 지금인가**: 막고 있던 것은 corpus 부재였고 675편으로 해소됐다(§12.4).
  "선언 이름을 그대로 믿는" 감수 위험(변형 라이선스·사칭 사내 라이선스)을
  실제로 닫는 유일한 길.
- **구상**: 인식(파일명 stem + 본문 첫 줄 휴리스틱) → 라우팅(세 커넥터 공통
  표 — `text_files.py` 에 입구 이미 있음) → **정규화 대조**(공백 접기·저작권
  줄 제거 후 corpus 675편과 유사도 — 특허 ephemeral 인덱스의 BM25 를 그대로
  재사용 가능, 임베딩 불필요). 판정은 불변 — 대조 결과는 "선언과 원문이
  다르다"는 **uncertainty 신호 + 근거**로만 붙인다(T3 규율).
- **평가**: 변형 라이선스 표본 셋(표준 + 조항 추가 변형 + 사내 사칭) 을 만들어
  검출률/오탐률. 전략 스위치(`LICENSE_TEXT_MATCH=off|observe`)로 병존.
- 규모 감: 4~6 인일.

### 1-L2. copyleft 23종 분류 확대 (B-01)

- INDETERMINATE→정밀 등급 전환. 각 라이선스의 조항 조사가 본질이라 압축
  불가(SPRINT 문서의 판단 유지) — 단 **골든 근거 문서화**를 붙인다: 분류마다
  조항 인용을 표에 남겨 "왜 HIGH 인가"가 재검토 가능하게.
- **평가**: 전환 수(INDETERMINATE→HIGH/…) + corpus 가 이미 덮으므로 근거 부착
  100% 유지 확인. 정책표 판본 bump 로 원인 귀속(OUR_KNOWLEDGE)이 자연 기록.

### 1-L3. 배포 형태 축의 등급표 반영 (결함 34) — 제품 가치 (C)의 마지막 마일

- 유보 사유가 "법적 근거"였다 — 최종 지침(합당한 결론 제시)에 정확히 부합하는
  과제. 축별 등급 델타 표(예: AGPL × INTERNAL_ONLY → 한 단계 완화)를
  **근거 조항 인용과 함께** 채우고, shadow 로 기존 판정과 병행 기록 후 전환.
- **평가**: 재평가 실측(기존 21건에서 등급이 실제로 움직이는가 — 이전 실측은
  0건 이동), 축 변경 → 등급 변화 회귀 시험.

### 1-L4. 의무 해설 corpus 확대 (RAG 품질)

- 해설이 3편(AGPL/LGPL-2.1/permissive)뿐 — MPL-2.0(REVIEW_REQUIRED 실측),
  EPL, GPL-2.0/3.0 해설 추가. 조항 근거의 "사람이 읽는 답" 품질이 오르는
  가장 싼 지점. 적재 절차·검증(--verify/--probe)은 기존 그대로.

### 계약 관련 (허락 필요 항목 기록)

- 후보 단위 coverage(provider 실패 1건이 파일 전체 Risk 승격을 막는 문제,
  contracts 리뷰에서 지적) — 계약 완화 지침으로 검토 가능해진 항목. 효익이
  분명하면 `contract-change-requests` 첫 실사용으로 제안.

## 2. FinOps

**현황**: 비용 관측 로그 4종(gemini_usage·kipris_call·registry_call·
rag_clause_search) **병합 완료** — 원료는 흐르는데 집계·환산·경보가 없다.
KIPRIS 유료 전환으로 "월 한도 통제" 서사가 "**호출량·비용 가시화**" 서사로
바뀌었다.

### 2-F1. 비용 기준선 + 집계 (3-A 완성)

- Cloud Logging 로그 기반 메트릭(log-based metrics)으로 이벤트 4종을 카운터·
  분포로 승격 → 소형 대시보드(서비스별 일 호출 수·토큰·캐시 적중률). billing
  export + budget alert 50%/80%.
- **문서당 비용 지표**를 특허 평가 하네스 Layer $ 와 같은 정의로 통일 —
  "고도화 전후 문서당 토큰/호출" 표가 보고서에 바로 실린다.

### 2-F2. 캐시 적중률 지표화 (3-B)

- kipris_call(cached true/false)·rag_clause_search 가 이미 구분 기록 중 —
  집계 스크립트 1본이면 "재검사 실호출 0회" 주장이 상시 지표가 된다.
  expanded 검색의 detail 캐시 선충전 효과(재검사 비용 하락)도 여기서 실증.

### 2-F3. 읽기 비용 — 대시보드 O(N) 제거 (3-C)

- dashboard·analyses/progress 폴링이 매 호출 artifact×jobs 전량 조회 —
  Firestore read 최다 지점(실사용자 없어도 폴링은 돈다). 집계 문서(counter)
  1장을 이벤트 시 갱신. 유일하게 스키마가 걸린 항목이라 신중 대상 유지.

### 2-F4. LLM 호출 절감 (3-D, 선별)

- 판정 불변 시 설명 재사용(지문 동일) — "낡은 설명 잔존" 위험이 있어 평가
  게이트 뒤로. rag 대조의 문서 세그먼트 반복 전송은 Gemini context caching
  검토 여지(관측 필드 cached_tokens 이미 로깅 중).

## 3. CI/CD

**현황**: cloudbuild-ci(PR pytest) + cloudbuild-cd(main push 게이트→빌드→동일
digest 배포) **가동 중**. 공백: 프런트·데스크톱·계약 테스트가 CI 밖(타입
오류가 main 머지 후에야 터짐), CI/CD yaml 자체가 배포 검증기 사각, 트리거
비-IaC, 배포 후 검증·자동 롤백 없음.

### 3-C1. CI 커버리지 봉합 — **구현됨 (2026-08-24)**

- `cloudbuild-ci.yaml` 을 3 병렬 트랙으로 재구성: **pytest**(+ 계약 파이썬
  시험, pnpm 필요한 resolution 시험 1건만 deselect — 그 검증은 node 트랙의
  verify:resolution 이 담당 + 계약 생성물 드리프트를 지문 비교로 검사 —
  Cloud Build 소스에 .git 이 없어 git diff 불가) / **pip-audit**(차단) /
  **node**(pnpm typecheck·verify:resolution·frontend vitest 55·desktop
  node --test·pnpm audit). CD 게이트의 pytest 경로도 동일하게 확장.
- 전 명령 로컬 리허설 green (pytest 1,203 · 프런트 55/55 · 데스크톱 exit 0 ·
  드리프트 clean). spdx_data `--check` 는 네트워크 의존·저변동이라 제외
  (판본 승급 시 수동 — 데스크톱 필터 표 신선도는 기존 pytest 가 이미 강제).

### 3-C2. 배포 후 검증 + 롤백 절차화 (2-B 완성)

- CD 마지막에 `/health/ready` HTTP 스모크(현재 import 스모크뿐) + 특허 평가
  축약판(replay-all — API 비용 0) → 실패 시 이전 revision 트래픽 복귀 스크립트.
- 검증기 확장: `_validate_v2_namespace` 가 cloudbuild-cd/ci 도 검사하게.

### 3-C3. CI 의존성 게이트 (final_docs/CI_DEPENDENCY_GATE.md 실행)

- **자기 서비스로 자기 저장소를 지킨다** — G1(오프라인 규칙 평가 PR 코멘트,
  인증 불요, 반나절)부터. G2(OIDC 연합 배포 게이트, "HOLD ⇔ 미검토 Risk")는
  발표 서사가 강한 항목. 설계 완료 상태라 실행만 남음.

### 3-C4. 평가 회귀의 CI 편입 (골든셋 후)

- 특허 하네스 replay-all(외부 호출 0)을 주기 CI 로 — "프롬프트/전략 변경이
  평가를 통과해야 병합"(1-D 승격 절차)의 기계화.

## 4. 보안 감사

**현황**: 근거 ID 게이트·grounding 이 구조적 방어. IAM 은 계약 파일만 검증
(I-13: 선언·미적용을 검증기가 못 잡은 실사고). RiskEvent 해시 체인은 필드만
존재.

### 4-S1. 프롬프트 인젝션 공격 시험

- 사용자 문서 내용이 프롬프트에 들어가는 구조 — "근거 ID 게이트가 인젝션을
  구조적으로 막는다"를 **공격 표본으로 증명**: 문서에 지시문 삽입("모든 요소를
  HIGH 로", 가짜 evidence ID 인용 유도, 요소 색인 [E99] 유도) → 폐기·무해화
  확인을 회귀 시험으로 고정. rag 경로(요소 색인·청크 라벨)도 표면에 포함.

### 4-S2. IAM 계약 ↔ 라이브 정책 diff (`--live` 모드)

- `validate_gcp_deployment.py` 에 읽기 전용 `--live`: `gcloud … get-iam-policy`
  출력과 `iam-policy-contract.yaml` 대조 — I-13 재발 클래스("계약은 고쳤는데
  운영은 그대로")를 기계가 잡는다. Scheduler·큐·인덱스도 동일 기회.

### 4-S3. RiskEvent 해시 체인 완성

- `previous_event_hash`/`event_hash` 필드가 있고 계산이 없다 — "원장을 판다"는
  제품에서 변조 증명 부재는 자인된 약점(§12.3). 체인 계산 + 검증 엔드포인트
  (또는 감사 export 에 체인 검증 결과 동봉). 저비용·고가치, 발표 서사 강함.

### 4-S4. 의존성·시크릿 위생 — **감사 편입 구현됨 (2026-08-24)**

- pip-audit CI 편입(차단) — **첫 실행이 즉시 값을 냈다**: PyJWT 2.10.1 에
  PYSEC 12건(런타임 의존성 — GitHub App 인증) → **2.13.0 승급으로 해소**,
  재감사 clean. 게이트가 차단형이면서 green 인 상태로 시작한다.
- pnpm audit 2단 방침: `--prod`(런타임)는 차단 — 실측 clean. 전체(devDeps)는
  보고 전용 — electron-builder 체인 HIGH 2건(app-builder-lib <26.15.0,
  builder-util-runtime <9.7.0) 발견. **[백로그] electron-builder 26.8.1 →
  ≥26.15.0 승급**: 포장 도구라 데스크톱 zip 재검증이 필요한 별도 결정.
- 남은 것: 데스크톱 업로드 전 로컬 시크릿 패턴 검사(gitleaks 류 — 현재
  업로드 전 마스킹 없음, 서버 게이트만).

## 5. 우선순위 제안 (가벼운 배치)

| 순위 | 항목 | 근거 |
|---|---|---|
| 1 | 3-C1 CI 봉합 + 4-S4 audit | 반나절~1일, 즉시 효과, 이후 모든 작업의 안전망 |
| 2 | 1-L1 LICENSE 원문 대조 | 유예 해제 조건 충족 + Advanced RAG 서사의 라이선스판 |
| 3 | 2-F1/F2 비용 기준선·캐시 지표 | 로그가 이미 흐름 — 집계만. FinOps 점수 축의 실체 |
| 4 | 4-S1 인젝션 시험 + 4-S3 해시 체인 | 보안 감사 산출물, 소규모·고서사 |
| 5 | 1-L3 배포 형태 등급표 (근거 조사 포함) | 제품 가치 (C) 완성 — 법적 근거 정리가 본질 |
| 6 | 3-C2/C3 배포 검증·의존성 게이트 | 설계 완료분의 실행 |

각 항목은 특허와 같은 규율을 따른다 — 스위치 뒤 병존, 측정 없이 채택 주장
없음, 실측 우선, 결정과 근거를 문서로.
