## 지금 막혀 있는 것

**corpus 적재와 배포는 한 리비전으로 함께 나가야 한다.**

0-G(관련성 게이트)는 끝났지만 **커밋만 됐고 배포되지 않았다.** 배포본은
`78a6490`/`79207f2` 라 아직 옛 게이트가 돈다. 그 상태로 corpus 만 키우면 틀린 근거가 붙는
양이 늘어난다 — 전수 측정에서 게이트 통과 질의의 오부착이 옛 게이트로는 29.4%,
새 게이트로는 **0%** 였다.

그래서 순서가 하나로 묶인다.

```
빌더 재실행(727 편) → 실제 corpus 에 한 번에 적재 → --verify --probe
   → 0-G 가 든 리비전 + RAG_CORPUS_ID + RAG_CORPUS_VERSION 을 함께 배포
```

**`RAG_CORPUS_VERSION` 은 조용히 어긋난다.** `optionalEnvironment.worker` 라 값이 저장소가
아니라 라이브 service 에만 있고, worker 전용이라 API 를 봐서는 모르며, optional 이라 낡아도
배포가 실패하지 않는다. 지금 매니페스트는 `2026-08-23.3`, 배포 env 는 `2026-08-21.1` 이다.
**적재 → 매니페스트 첫 줄 읽기 → worker env 갱신 → 배포** 순서를 지켜야 한다. 값만 먼저
맞추면 라벨만 바뀌고 corpus 는 그대로다.

### 라이선스 지식

* 빌더에서 정책 표 의존을 뺀다 → 727 편
* 전문 없는 29 종을 덮는다 (빌더 재실행이면 끝난다)
* copyleft 23 종 분류 — `CECILL`·`NPL`·`QPL`·`copyleft-next` 등. 지금 `UNKNOWN`(MEDIUM)
  인데 실제로는 `POLICY_CONFLICT`(HIGH) 여야 한다. 분류만 하면 등급만 고쳐지므로
  **전문도 함께** 넣어야 근거가 붙는다
* 나머지 448 종(폰트·문서·벤더)은 두는 것을 권한다 — `UNKNOWN` = MEDIUM 이 정확한 표현이다

### 실측 1-A — 막혀 있다

Drive 서비스 계정 변경 피드가 이탈·재진입을 주는지. **이 답이 폴더 마운트 설계의 규모를
정한다.**

`gcloud` 재인증은 풀렸으나 **가장(impersonation) 권한이 없다** —
`iam.serviceAccounts.getAccessToken` 이 사람 계정에 붙어 있지 않다.

푸는 방법 둘 중 **(2)를 권한다.**

1. 사람 계정에 `iprisk-v2-worker` 가장 권한을 준다 — 빠르지만 **운영 신원을 사람이 가장할
   수 있게 된다.** 그 SA 는 Firestore·Secret·Drive 에 닿는다.
2. **권한 0 인 버리는 시험용 SA 를 만든다.** D1 의 핵심이 "Drive 접근은 IAM 이 아니라
   폴더 공유에서 온다" 는 것이므로, 권한이 없어도 세 물음의 답은 똑같이 나온다. 운영
   신원을 안 건드리고 끝나면 지운다 — 오히려 D1 이 실제로 그렇게 도는지를 함께 확인한다.

탐침은 만들어져 있다 (`check` / `start` / `poll`).

### 배포

## 안 끝났는데 조용한 것들

명세의 결함표에 있으나 아직 아무도 안 잡은 것 중, 잊기 쉬운 것만 적는다.

* **결함 24 — 외부 사실 변화를 촉발하는 것이 없다** (§7.6). 파일이 안 바뀌면 라이선스
  변경을 영영 모른다. §1.2 (A) 가 파는 바로 그것인데 방아쇠가 없다. 2-F 캐시가 선행이다.
* **결함 25 — 제외 수단 셋이 다른 매처를 쓴다** (§9.1). `.ipriskignore` 는 안 맞으면
  **조용히 0 개를 거른다.** 폴더 마운트를 열기 전에 반드시 고쳐야 한다.
* **결함 22 — 이전 작업이 남긴 근거가 그대로 붙어 있다** (§5.6). `clear_evidence` 가 같은
  작업이 넣은 행만 지운다. 0-H 가 닫지 않는다.
