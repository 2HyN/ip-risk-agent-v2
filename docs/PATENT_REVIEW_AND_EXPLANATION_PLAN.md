# 특허 검토 마무리와 설명·권고 — 실행 계획

> 2026-08-22 작성. 로드맵의 1 번(특허 검토 완결)과 2 번(Gemini 설명·권고)을
> 실행 단위로 쪼갠다. 3 번(GitHub·Local·Desktop 점검)과 4 번(UI 대개편)은 이 문서
> 밖이다.

## 0. 계획의 전제 — 지금까지 확인된 것

| 사실 | 근거 |
|---|---|
| 문서가 조각으로 갈리고 근거에 줄 범위가 실린다 | `connectors/common/segmentation.py`, 근거 `metadata_safe.line_start/line_end` |
| 등급 규칙이 확정됐다. 강등은 코드가 아는 사실로만 | `PATENT_PRIORITY_DESIGN_NOTE.md` §4.3 |
| 등급이 실제로 갈린다 | 실측 LOW 38 · MEDIUM 47 · HIGH 5 |
| `match_count == 1` 이 MEDIUM 47 건 중 38 건 | `patent_priority_diagnostic` |

그리고 이 계획을 좌우하는 **구조적 사실 하나**를 새로 확인했다.

> **설명이 앉을 자리가 없다.**
>
> `LicenseCandidate` 에는 설명을 담을 필드가 없고, `PatentCandidate` 의
> `provider_metadata_safe` 는 Risk 로 투영되지 않는다 (`_CandidateProjection` 은
> risk_key·priority·summary·evidence_ids 만 옮긴다).
>
> 그래서 지금 **license 설명은 만들어진 뒤 버려진다.** `GeminiLicenseExplainer` 가
> 내놓은 `summary` 와 `obligations` 는 참조 검증과 버전 기록에만 쓰이고 저장되지
> 않는다. Gemini 를 부르고 결과를 버리는 셈이다.

`shared/contracts/**` 는 Frozen 이므로 계약 필드를 늘릴 수 없다. 대신 core 의
`Risk` 는 우리 것이므로 거기에 자리를 만든다. 이것이 **2-A** 이고, 1-B 와 2-B
양쪽의 선행 조건이다.

## 1. 특허 검토 완결

### 1-A. `match_count == 1` 지배 해소

MEDIUM 47 건 중 38 건이 겹치는 구성 1 개다. 이것이 HIGH 를 막지는 않지만
(§4.3 이후 HIGH 는 나온다) A 안 점수의 분자를 사실상 상수로 만든다.

가설 둘.

1. **대조가 구성을 크게 묶는다.** 프롬프트 v2 에 "서로 다른 구성이 겹치면 각각
   따로 적는다" 를 넣었으나 효과를 아직 측정하지 않았다
2. **조각이 적어 조합이 적다.** 문서당 4 조각이면 (조각 × 청구항) 쌍의 상한이 낮다

**측정으로 가른다.** `patent_priority_diagnostic` 이 이미 `segment_count` 와
`distinct_segments` 를 남긴다. 문서 크기별로 `match_count` 와 함께 보면 2 번이면
조각 수와 상관이 보이고, 1 번이면 보이지 않는다. 새 코드가 필요 없다.

### 1-B. 문장 단위 하이라이트 (데이터 층)

목표는 "문서의 어느 줄·문장·어구가 문제인지 소스와 근거 양쪽에 하이라이트" 다.
지금은 조각 단위까지 좁혀졌고, 그 안에서 다시 좁히는 일이 남았다.

`MatchedElement` 에 인용 두 개를 받는다 (우리 스키마이므로 계약과 무관하다).

```
source_quote  : 문서 조각 안의 문장/어구
patent_quote  : 청구항 근거 안의 문장/어구
```

**코드가 실재를 검증한다.** 인용이 해당 조각·근거 본문에 실제로 있는지 확인하고,
없으면 지어낸 것이므로 그 후보 전체를 폐기한다 — 근거 ID 검증과 같은 원칙이다
(Agent 3 Spec 19). 공백·개행 차이는 정규화한 뒤 비교한다.

검증을 통과하면 조각 안에서의 offset 을 계산해 근거 `metadata_safe` 에
`quote_start` / `quote_end` 로 남긴다. 줄 범위는 이미 있으므로, 화면은
"조각을 보여 주고 그 안의 구간만 강조" 하면 된다.

원문을 저장하지 않는 제약과도 맞는다. 하이라이트가 가리키는 대상이 우리가 이미
저장한 근거 본문 자체이기 때문이다.

### 1-C. A 안 파생 점수 — 기록만 (§6-3)

```
score = w1 * (일치 구성요소 / 추출 구성요소)
      + w2 * (청구항 근거 비율)
      + w3 * (적중 질의 수 / 전체 질의 수)
```

분모는 모두 이미 있다 — 추출 구성요소는 `TechnicalExtraction.technical_elements`,
질의 수는 검색 단계 결과. 다만 `_compare` 가 추출 결과를 받지 않으므로 그것만
넘겨 주면 된다.

**판정은 바꾸지 않는다.** 점수를 진단 로그와 `provider_metadata_safe` 에만 남긴다.
되돌릴 것이 없고, 임계값을 고를 실제 데이터가 쌓인다.

### 1-D. 라벨 수집 → 임계값 두 개 (§5, §6-4·5)

사람이 30~50 쌍에 상·중·하를 매긴다. **점수를 가리고** 매겨야 한다.
후보·근거·문서 조각을 보여 주고 등급만 입력받는 스크립트를 만든다.
분포를 보고 `t_med`(Risk 로 만들 것인가)와 `t_high`(먼저 볼 것인가)를 고른다.
전환할 때 임계값 버전을 `AnalysisVersions` 에 남긴다 (§4.2·4.4).

이 단계는 사람의 판단이 필요하므로 도구까지가 개발 범위다.

## 2. Gemini 기반 설명 + 권고

### 2-A. 설명이 앉을 자리 — **선행 조건**

core `Risk` 에 두 필드를 더한다.

```
explanation_safe    : str | None   왜 이것이 risk 인지
recommendation_safe : str | None   앞으로 무엇을 할지 (권고 수준)
```

`latest_analysis_job_id` 가 이미 있으므로 어느 실행이 만든 설명인지 되짚을 수 있고,
`AnalysisVersions.prompt_version` 이 어떤 프롬프트가 썼는지 남긴다.

건드릴 곳 — core 모델, Firestore 매퍼, in-memory 저장소, `_CandidateProjection`,
`accept_analysis_result`, API 응답 모델, 프론트 타입. 계약은 건드리지 않는다.

값은 사람이 읽을 문장이므로 보존 정책(`sanitize_summary` 계열)을 태워 길이와
민감값을 정리한 뒤 저장한다.

### 2-B. 특허 설명기

license 와 같은 모양으로 만든다 — `PatentExplainer` 프로토콜과
`GeminiPatentExplainer` 구현, 프롬프트 `patent_explain_v1`.

입력은 **검증을 통과한 근거만** 넣는다. 겹치는 구성, 인용된 청구항, 인용된 문서
조각. 검색 원문이나 미검증 후보는 넣지 않는다.

출력은 둘.

* `summary` — 왜 검토가 필요한지. 겹치는 구성이 무엇인지 근거를 짚어 설명
* `recommendation` — 앞으로 무엇을 할지

**법적 결론을 만들지 않는다.** 프롬프트에 명시한다. 침해·유효성·권리 범위를
판단하지 않고, 권고는 "특허팀 검토 요청", "해당 구성의 대안 설계 검토",
"출원 전 선행조사 확대" 처럼 **행동 수준**에 머문다. "침해입니다",
"침해가 아닙니다" 는 금지한다.

license 설명기와 같이, 모델이 없는 근거를 인용하면 설명 전체를 버린다.

### 2-C. license 설명 살리기

`GeminiLicenseExplainer` 는 이미 돌고 있고 결과만 버려진다. 2-A 의 자리가 생기면
그대로 저장한다. **추가 호출 비용이 없다** — 이미 부르고 있다.

`obligations` 는 권고에 가까우므로 `recommendation_safe` 로, `summary` 는
`explanation_safe` 로 옮긴다.

### 2-D. 화면에 임시로 끼운다

Risk 상세에 두 블록을 붙인다. 자리는 UI 대개편(로드맵 4 번)에서 다시 잡는다.
지금은 "기능이 살아 있고 값이 보인다" 까지가 목표다.

## 3. 순서

```
2-A  설명이 앉을 자리        ← 1-B 와 2-B 의 선행 조건
 │
 ├── 2-C  license 설명 살리기   (자리만 생기면 끝. 비용 0)
 ├── 2-B  특허 설명기 + 프롬프트
 ├── 1-B  인용 검증과 offset
 └── 1-A  측정 (코드 불필요, 언제든)
        │
        └── 1-C  파생 점수 기록
                │
                └── 1-D  라벨 도구 → 임계값 전환
```

2-A 를 먼저 하는 이유는 그것이 없으면 1-B 의 offset 도 2-B 의 설명도 저장할 곳이
없기 때문이다. 그리고 2-C 는 자리가 생기는 즉시 공짜로 얻는다.

1-A 는 코드가 필요 없으므로 다른 작업과 언제든 병행한다.

## 4. 이 계획이 지키는 경계

* **판정은 규칙 엔진, 모델은 설명.** 설명기는 등급도 Risk 존재도 바꾸지 않는다
* **지어낸 것은 전부 버린다.** 인용도 참조도 코드가 실재를 확인한다
* **법적 결론을 만들지 않는다.** 권고는 행동 수준까지
* **원문을 저장하지 않는다.** 하이라이트는 이미 저장한 근거 안에서만 가리킨다
* **계약은 동결.** 자리는 core 에 만든다
