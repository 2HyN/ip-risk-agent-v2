# 폴더 단위 마운트 — 설계와 검토

세 소스를 폴더 단위로 통합하고, UI 는 `/workspace` 아래에 각 폴더를 mount 한 트리로
보여 준다. Drive 는 `drive.file` 을 버리고 **서비스 계정 + 폴더 공유** 로 간다.

참고 — `origin/integration`(v1), `github.com/Sora3780/ip-risk-agent`.

## 결정 (2026-08-22)

| # | 결정 | 상태 |
|---|---|---|
| 1 | **서비스 계정 + 폴더 공유**. 공유받은 폴더만 읽는다 | 확정 |
| 2 | 여러 workspace 가 같은 폴더를 mount 하는 경우는 다루지 않는다 | **보류** |
| 3 | 조직 정책이 외부 공유를 막으면 그냥 실패한다 | **보류** |
| 4 | 지정된 폴더 안은 소유자를 구별하지 않고 전부 검사한다 | 확정 |
| 5 | 바로가기는 따라가지 않는다. 건너뛴 표시도 하지 않는다 | 확정 |
| 6 | 폴더 밖으로 나간 파일은 추적 불가로 보고 EXCLUDED 로 닫는다 | 확정 |

결정 3 의 원칙 — *조직이 막은 것을 서비스가 넘어서면 그것은 서비스가 아니라
백도어다.* 이 원칙 자체는 코드에 남길 값이 있다.

---

## 1. 서비스 계정이 이 설계에 주는 것

| | 접근 범위 | 봉쇄를 누가 하나 | 보관할 자격증명 |
|---|---|---|---|
| `drive.file` + Picker (지금) | 고른 항목 | Google | 사용자 refresh token |
| `drive.readonly` 사용자 OAuth | 계정 **전체** | **우리 코드** | 사용자 refresh token |
| **서비스 계정 + 폴더 공유** | **공유받은 것만** | **Google** | **없음** |

**봉쇄가 우리 밖에 남는다.** 범위 계산에 버그가 있어도 공유되지 않은 것을 요청하면
Google 이 404 로 거절한다. 사용자 OAuth 로 `drive.readonly` 를 받았다면 그 버그가
곧 범위 밖 파일을 실제로 읽는 경로가 됐을 것이다.

**보관할 토큰이 없다.** Cloud Run 에 이미 서비스 계정이 붙어 있어 키 파일이 필요
없다. workspace 를 전부 지운 뒤에도 Drive refresh token 19 개가 남아 있던 문제
(`1849f37` 로 고침)가 **구조적으로 생기지 않는다.** 지울 토큰 자체가 없다.

**변경 피드가 좁아진다.** 서비스 계정은 공유받은 것만 보므로 그 계정의 `changes`
피드도 그 범위다. 사용자 OAuth 였다면 계정 전체의 변경을 받아 우리가 걸러야 했고,
범위 밖 파일의 이름과 변경 사실이 우리 시스템을 지나갔을 것이다.

## 2. 범위 이탈과 재진입 — 이 설계의 핵심

> "폴더 밖으로 나간 파일이 고장과 다를 게 뭐지? 다른 소스에서는 source not found 를
> 어떻게 처리해? 나간 것을 excluded 처리할 수만 있다면 부활은 가능할 것 같은데?"

확인해 보니 **이 지적이 맞고 앞선 검토가 틀렸다.** 순서대로 적는다.

### 다른 소스는 "사라짐" 을 404 로 받지 않는다

세 소스 모두 **DELETE 변경 이벤트**로 받는다 — GitHub push 의 `removed`
(`webhook_processor.py:114`), Local 워처의 삭제, Drive 변경 피드의 `item.removed`
(`google_drive/adapter.py:373`). fetch 404 는 **이벤트와 가져오기 사이의 경합**에서만
나는 예외 경로다.

그러니 "폴더 밖으로 나감" 을 404 로 다루려던 앞선 구상 자체가 결이 맞지 않았다.

### 그리고 지금은 삭제도 Risk 를 닫지 않는다

DELETE 변경은 분석을 돌리지 않는다 — `process_change/service.py:163` 이 이벤트를
곧바로 `DONE` 으로 두고 artifact 는 `availability=DELETED` 가 된다. 그런데 **Risk 를
닫는 코드가 그 경로에 없다.** `exclude_artifact_risks` 를 부르는 곳은 수동 "추적
해제" 하나뿐이다(`public_facade/service.py:356`).

즉 **파일을 지워도 그 Risk 는 활성 목록에 그대로 남는다.** 폴더와 무관한 기존
결함이고, v1 이 `45c1d8c` 에서 "감시하지 않는 대상의 위험이 화면을 차지한다" 며 고친
것과 같은 자리다.

그래서 "고장과 다를 게 뭐냐" 의 실질적인 답은 이렇다 — **지금은 둘 다 Risk 를 닫지
않아 결과가 같다.** 다른 점은 하나뿐이다. FAILED 는 "분석 실패" 로 쌓이고 사람이
손댈 수 없는 채 남는다. 그 차이만으로 별도 분류를 만들 이유는 되지 않는다.

**정리** — 필요한 것은 "폴더 이탈" 전용 처리가 아니라, **artifact 가 추적 대상에서
벗어났을 때 Risk 를 닫는 경로 하나**다. 삭제·폴더 이탈·접근 상실이 모두 그리로
들어간다.

### 부활도 가능하다 — 지적이 맞다

앞선 검토는 "파일이 돌아와도 fingerprint 가 같아 분석이 돌지 않으니 `should_revive`
가 발화하지 않는다" 고 적었다. 그것은 **되살리기를 분석 결과에 매달았을 때의
이야기**이고, 이탈을 우리가 잡을 수 있다면 재진입도 우리가 잡을 수 있다.

* 판본이 그대로면 — 어제의 분석이 그 판에 대해 여전히 유효하다. **분석 없이 바로
  되살린다.** v1 이 `c73505b` 에서 mount 재연결에 대해 택한 방식과 같다.
* 판본이 달라졌으면 — fingerprint 가 달라지므로 **평소의 변경 경로**가 그대로 돈다.
  분석이 돌고 그 결과가 Risk 를 갱신한다.

그러므로 `docs/INTEGRATION_V1_CROSSCHECK.md` 1 번(감시를 재개해도 Risk 가 되살아나지
않는다)은 이 작업의 **선행 조건이 아니라 같은 작업이다.** 폴더 스코프가 두 가장자리를
모두 쥐면 그 코드가 crosscheck 1 번의 mount 재연결 경우까지 함께 닫는다.

### 서비스 계정이라 가장자리가 저절로 올 수 있다

서비스 계정의 접근권은 **폴더 공유에서 나온다.** 파일이 폴더 밖으로 나가면 그 계정은
접근을 잃고, Drive 변경 피드는 접근을 잃은 항목을 `removed` 로 준다. 다시 넣으면
접근이 돌아오고 피드에 다시 나타난다.

**사실이라면 이탈·재진입 양쪽이 이미 있는 DELETE / UPDATE 경로로 들어온다.** 폴더
내용을 주기적으로 대조하는 작업 자체가 필요 없어진다.

문서로 판단할 것이 아니라 실측할 것이다 — 5 절.

## 3. 세 소스 통합 — 되어 있는 것과 없는 것

### 되어 있는 것

**UI 트리는 데이터 모델을 바꾸지 않고 나온다.** `logical_path` 가 이미
`alias/상대경로` 다 — `_logical_path`(`process_change/service.py:431`)가 `path_hint`
를 우선해 `f"{alias}/{경로}"` 를 만든다. `/workspace/github_repo1/app/...` 는 이 값을
`/` 로 쪼개면 된다. GitHub 은 `path_hint` 에 저장소 기준 전체 경로를 넣으므로
**오늘도 트리가 나온다.**

### 없는 것

**Drive 에는 경로가 없다.** `google_drive/adapter.py:211,299` 가
`logical_path_hint=None` 이고 커넥터에 폴더·부모를 다루는 코드가 없다. 그래서 Drive
artifact 의 `logical_path` 는 `alias/파일이름` 으로 평평하다. 트리를 보여 주려면 부모
경로를 만들어 `path_hint` 에 넣어야 한다. **스코프 결정과 독립이므로 지금 시작할 수
있다.**

**Drive 가 받는 문서 종류가 좁다.** 지금은 mime 이 `text/plain` / `text/markdown` /
`application/json` / Google Doc 인 것만 통과한다(`google_drive/models.py:17`,
`adapter.py:186`). 결정 4 를 지키려면 다른 소스와 같은 기준으로 넓혀야 하고, 이는
**이미 계획에 있는 부분**이다. 폴더 마운트가 열리기 전에 들어가야 한다 — 폴더 안의
`.py`·`.csv`·`.yaml` 이 조용히 빠지면 약속과 동작이 어긋난다.

같이 볼 것 — `docs/INTEGRATION_V1_CROSSCHECK.md` 2 번. Drive 가 `.md` 에
`application/octet-stream` 을 붙이는 경우가 있어, mime 만 믿으면 확장자가 멀쩡한
파일도 빠진다. v1 이 운영에서 겪었다.

**파일이 움직였을 때의 정체성이 소스마다 다르다.** artifact 정체성은
`(source_workspace_id, source_artifact_id)` 인데,

* Drive 의 `source_artifact_id` 는 **file id** 라 폴더를 옮겨도 같은 artifact 다.
  2 절의 이탈·재진입이 자연스럽게 성립한다.
* GitHub 의 것은 **경로를 담고 있어** 파일을 옮기면 삭제 + 생성이 된다. 이력이 끊기고
  Risk 도 새로 생긴다.

당장 막는 것은 아니지만, 화면에서 같은 일로 보이는데 결과가 다르면 사용자가 설명을
요구하게 된다.

## 4. 가장 급한 것 — 비용

폴더 단위는 초기 스캔을 배로 키운다. 파일 하나가 문서·소스면 특허 경로로 가고,
Gemini 추출 1 회 + KIPRIS 검색 최대 5 회 + 상세 최대 6 회를 쓴다. **KIPRIS 무료
등급은 월 1,000 회다.** 결정 4 로 대상이 넓어지면 이 비용도 함께 커진다.

거를 수단 세 가지가 지금 **모두 비어 있다.**

| 수단 | 걸리는 지점 | 현재 |
|---|---|---|
| 소스의 `.ipriskignore` | 변경 이벤트가 생기지 않는다 | 점검 저장소에만 있음 |
| workspace `global_ignore_text` | 관문이 막아 provider 호출 없음 | 빈 문자열 |
| `include/exclude patterns` | 스코프 단계 | API 는 받는데 **프론트가 항상 빈 배열** |

**폴더 마운트를 열기 전에 이 중 하나는 채워져야 한다.** 그러지 않으면 폴더 하나를
붙이는 것으로 한 달치가 사라진다.

참고 저장소의 게이팅이 참고가 된다 — "내용이 실제로 바뀌었고, 10 분이 지났고, 쿼터가
남았을 때만 특허 검토를 돌린다". v3 는 추출 캐시와 출원번호 캐시가 있어 **재검사**
비용이 이미 0 에 가깝지만(S3 에서 실측), **처음 보는 파일**의 비용은 그대로다.

## 5. 먼저 할 실측 — 서비스 계정의 변경 피드

한 번의 실험이 2 절의 물음 셋을 모두 답한다. Drive 를 비워 두었으니 지금이 가장 좋은
상태다.

폴더 하나를 서비스 계정에 뷰어로 공유한 뒤,

1. 폴더에 **파일을 새로 넣는다** → SA 의 `changes` 에 잡히는가
   → 잡히면 "폴더 단위 지속 추적" 이 이미 있는 경로로 성립한다
2. 파일을 폴더 **밖으로 옮긴다** → `removed` 로 오는가
   → 오면 이탈 감지가 공짜다. 안 오면 폴더 내용을 주기적으로 대조해야 한다
3. 파일을 **되돌린다** → 다시 나타나는가
   → 나타나면 재진입도 같은 경로다

**이 결과가 설계의 크기를 정한다.** 셋 다 잡히면 남는 일은 "Risk 를 닫고 되살리는
경로" 하나뿐이고, 안 잡히면 폴더 대조 작업을 새로 만들어야 한다.

## 6. 권고 순서

1. **서비스 계정 변경 피드 실측** (5 절). 설계 규모가 여기서 정해진다
2. **비용 통제.** 폴더 마운트가 열리기 전에
3. **Drive 문서 종류를 다른 소스와 같게.** 결정 4 의 전제
4. **추적 대상에서 벗어난 artifact 의 Risk 를 닫는 경로.** 삭제·이탈·접근 상실이 모두
   들어가고 재진입 되살리기가 같은 코드에 붙는다. crosscheck 1 번도 여기서 닫힌다
5. **Drive 에 경로(`path_hint`) 넣기.** UI 트리의 전제. 독립적이라 언제든
6. **폴더 확장·상한.** v1 이 300 개 / 깊이 10 으로 두고 잘라낸 사실을 로그로
   남겼다(`ea70787`). 조용히 자르면 "전부 검사했다" 로 읽힌다

## 7. 미루기로 한 것

미룬 이유와 **다시 볼 조건**을 남긴다. 잊어서 안 한 것과 정하고 안 한 것은 다르다.

### 결정 2 — 여러 workspace 가 같은 폴더를 mount

서비스 계정 하나에서는 한 번 공유된 폴더가 **폴더 id 를 아는 누구에게나 mount
가능**해진다. mount 생성은 요청자의 workspace 권한만 보고 폴더 권한은 보지 않는다 —
볼 수단이 없다.

"폴더 하나는 workspace 하나에만" 이라는 거절로 값싸게 닫을 수 있으나, **중복 폴더를
확실하고 쉽게 다룰 방법이 정해진 뒤에** 함께 구현하기로 했다. 지금 메인 구현 범위에
넣을 여력이 없다는 판단이다.

**다시 볼 조건** — 한 workspace 를 넘어 외부 사용자를 받을 때. 그 전에는 workspace
구성원 사이의 소스 관리를 그 workspace 의 관리 책임으로 본다.

### 결정 3 — 조직 정책으로 공유가 막히는 경우

개발 과정에서 조직 계정을 시험할 일이 없다. 지금은 **그냥 실패하는 것으로 충분**하다고
판단했다. 실제로 어떻게 동작하고 어떻게 동작해야 하는지는 그런 계정을 다룰 때 정한다.

**다시 볼 조건** — 회사 Workspace 계정을 대상으로 시험할 때. 확인할 것은 두 가지다.
공유가 아예 거부되는지, 아니면 공유는 되는데 접근이 404 로 오는지. 안내 문구는 그
결과를 보고 쓰는 것이 맞다.

### 결정 5 — 바로가기 건너뛴 표시

바로가기의 mime(`application/vnd.google-apps.shortcut`)은 지금도 통과 목록에 없어
자연히 걸러진다. 건너뛴 사실을 화면에 알리는 것은 나중으로 미룬다.

**한 가지만 기억할 것** — 결정 4 로 문서 종류를 넓힐 때 바로가기가 **실수로 들어오지
않게** 해야 한다. 들어오면 그것이 범위 밖을 읽는 경로가 된다. 지금은 목록에 없어서
막히는 것이지 규칙으로 막고 있는 것이 아니다.

## 8. 참고로 남기는 것

**v1 을 그대로 옮기면 목표에 못 미친다.** v1 스스로 적어 두었다(`ea70787`) — "펼침은
연결 시점의 스냅샷이다. 이후 폴더에 새로 추가된 파일은 자동으로 추적되지 않는다."
v1 이 스코프를 넓힌 이유(`f50a15b`)도 **펼치기가 409 로 실패해서**였지 지속 추적
때문이 아니다. 지속 추적은 이 프로젝트가 새로 만드는 부분이다.

**사용자 OAuth 로 `drive.readonly` 를 받았다면** 필요했을 것들 — 게이트에 "이 파일이
마운트된 폴더 안에 있는가" 검사를 새로 넣어야 했고(지금 게이트는 ignore·mime·정합성만
본다), Drive 폴더가 파일시스템 트리가 아니라는 점(바로가기·다중 부모)을 우리 코드가
전부 감당해야 했다. 서비스 계정을 택해 이 부담이 사라졌다.
