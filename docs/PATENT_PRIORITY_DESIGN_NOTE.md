# 특허 검토 우선도 — 유사도 임계값 도입 검토

> 성격: **고도화 검토 노트.** 지금 결정할 것과 나중에 결정할 것을 갈라 두는 것이
> 목적이다.
>
> 갈린 결과 (2026-08-22): **§4 의 등급 의미는 구현되었다.** 점수(§3 의 A 안)와
> 임계값 두 개는 아직이다. 등급이 무엇을 뜻하는지는 코드가 이미 따르고 있고,
> 그 등급을 무엇으로 정할지가 남았다.

## 1. 지금 상태

우선도는 연속 점수가 아니라 **이산 규칙표**다 (`patent/grounding.py::suggested_priority`).

```
match_count == 0                              -> LOW
청구항 근거 있음  and  match_count >= 2        -> HIGH
청구항 근거 있음  or   match_count >= 2        -> MEDIUM
그 밖                                          -> LOW
근거가 잘렸고 HIGH 이면                        -> MEDIUM 으로 한 단계 내림
```

입력 신호는 셋뿐이다 — 대조로 일치한 구성요소 수, 근거가 청구항에서 왔는지,
근거가 잘렸는지. 셋 다 코드가 아는 값이다 (§4.3).
**유사도라고 부를 수 있는 수치는 파이프라인 어디에도 없다.**

검색 단계도 점수를 주지 않는다. KIPRIS 응답에 관련도 값이 없고,
`candidate_rank.py` 는 (질의 적중 수, 검색 결과 내 위치, 출원번호) 로만 정렬한다.

## 2. 먼저 처리해야 할 것 — 규칙의 전제가 바뀌었다

위 규칙의 주석은 이렇게 적고 있다.

> KIPRIS 가 실제로 주는 것은 대개 초록뿐이다. 청구항을 요구하면 실측에서 모든
> 후보가 LOW 로 깔려 우선순위가 정보를 주지 못한다. 그래서 초록 근거만으로도
> 겹치는 구성이 둘 이상이면 MEDIUM 으로 올린다.

**이 전제는 더 이상 사실이 아니다.** `patUtiModInfoSearchSevice` 경로에서 청구항이
함께 온다 (실측 18 건, 4 건). 즉 지금의 `match_count >= 2 -> MEDIUM` 은 청구항이
없던 시절의 우회책이고, 이제는 HIGH 가 정상적으로 나올 수 있다.

**임계값을 설계하기 전에 현재 규칙이 청구항과 함께 무엇을 내놓는지 먼저 관측해야
한다.** 분포를 모르는 상태에서 고른 임계값은 근거가 없다.

## 3. 유사도를 무엇으로 정의할 것인가

임계값을 쓰려면 먼저 점수가 있어야 한다. 세 갈래가 있고 성질이 크게 다르다.

| 안 | 내용 | 장점 | 대가 |
|---|---|---|---|
| **A. 파생 점수** | 지금 있는 신호(일치 구성요소 비율, 청구항/초록 가중, 질의 적중 수, 검색 위치)를 정규화해 0~1 로 합성 | provider 추가 없음. 결정적이고 설명 가능. 근거가 그대로 남는다 | 가중치를 사람이 정해야 한다. "유사도" 라기보다 **근거 강도**에 가깝다 |
| **B. 임베딩 유사도** | 문서 기술요소와 특허 청구항/초록을 임베딩해 코사인 유사도 | 연속적이고 임계값과 자연스럽게 맞는다 | Vertex 임베딩 호출 비용·지연. 값이 불투명해 "왜 상인가" 를 설명하기 어렵다. 교정 없이는 숫자에 의미가 없다 |
| **C. 모델 채점** | Gemini 에게 0~1 겹침 점수를 직접 요구 | 붙이기 가장 쉽다 | 교정되지 않고 호출마다 흔들린다. 무엇보다 **판정을 모델에 넘기는 것**이라 "판정은 규칙 엔진, 모델은 설명" 이라는 현재 경계와 충돌한다 |

**채택 (2026-08-22): A 를 기본, B 를 보조 신호.** C 는 우선도 결정에 쓰지 않는다.

B 를 "보조" 로 둔다는 것은 임베딩 유사도가 **판정을 뒤집지 못한다**는 뜻이다.
A 의 점수를 기록하고 B 를 함께 기록하되, 등급은 A 로 정한다. B 는 A 가 놓치는
표현 차이(같은 구성을 다른 용어로 쓴 경우)를 사람이 발견하도록 돕는 신호이고,
교정이 끝나기 전에는 임계값에 넣지 않는다.

A 를 택하면 점수는 이런 형태가 된다.

```
score = w1 * (일치 구성요소 / 추출 구성요소)
      + w2 * (청구항 근거 비율)
      + w3 * (적중 질의 수 / 전체 질의 수)
```

각 항이 이미 근거 원장에 남아 있으므로 **점수를 근거로 되짚을 수 있다.** 이것이
B 대비 가장 큰 실익이다.

## 4. 등급의 뜻 — '하' 는 낮은 위험이 아니다

> 2026-08-22 결정. 이 절이 임계값을 두 개 두는 **이유**다.

점수를 "확실히 risk" 100 에서 "전혀 risk 아님" 0 까지의 눈금으로 본다.
**'하' 는 그 눈금의 아래쪽 전부**이고 0 까지 포함한다. 즉 '하' 는 "위험이 조금
있다" 가 아니라 **"우리가 관리할 위험이 아니다"** 는 판정이다.

그래서 등급이 곧 Risk 의 존재를 정한다.

| 분석 결과 | 기존 Risk 없음 | 기존 Risk 있음 |
|---|---|---|
| 상 · 중 | Risk 를 만든다 (`NEW`) | 존재가 이어진다 (`EXISTING`) |
| 하 | **만들지 않는다** | **`RESOLVED` 로 닫힌다** |

이상적인 흐름은 이렇다. 상·중으로 잡힌 Risk 를 사용자가 지켜보다가, 문서가 바뀌고
재검사에서 '하' 로 내려가면 Risk 가 `RESOLVED` 가 되고, 사용자는 그것을 확인하고
받아들인다(`ACCEPTED_RISK`).

**임계값 두 개가 필요한 이유가 여기 있다.** 하나는 "Risk 로 만들 것인가"
(`t_med` — 중과 하의 경계)를 정하고, 다른 하나는 "먼저 볼 것인가"
(`t_high` — 상과 중의 경계)를 정한다. 성격이 다른 두 결정이라 값도 따로 잡아야 한다.

```
score >= t_high              -> 상   (Risk. 먼저 본다)
t_med <= score < t_high      -> 중   (Risk)
score <  t_med               -> 하   (Risk 아님)
```

`t_med` 는 **오탐과 누락의 경계**다. 낮추면 관리 목록이 관리할 필요 없는 것으로
차고, 높이면 진짜 위험을 놓친다. `t_high` 는 **검토 비용의 경계**다. §5 의 4 번이
말하듯 상의 총량이 감당 가능해야 한다.

### 지금 구현된 것

이 등급 의미는 이미 canonical 수용 경로에 들어가 있다
(`risk_reconcile/service.py::_is_risk_worthy`). 하 등급 후보는 투영에서 빠지고,
그러면 기존 Risk 는 `candidate_present=False` 경로를 타 `RESOLVED` 가 된다.
lifecycle 규칙을 따로 만들지 않고 기존 기계에 얹었다.

License 도 같은 규칙을 받는다. `NO_ACTION` 이 `LOW` 로 매핑되므로 의무가 없는
라이선스는 Risk 가 되지 않는다. 이것도 "전혀 risk 아님" 과 같은 뜻이다.

남은 것은 **점수와 임계값**이다. 지금은 §1 의 이산 규칙이 등급을 정한다.

## 4-b. 임계값 두 개를 쓸 때 반드시 지켜야 할 것

여기에 이 프로젝트에서 이미 값을 치른 교훈 셋을 붙인다.

### 4.1 점수를 못 구한 것과 점수가 낮은 것을 섞지 않는다

§4 에서 '하' 가 Risk 를 닫는 판정이 되었으므로 이 교훈은 전보다 훨씬 무겁다.
점수를 0 으로 두면 '하' 가 되고, '하' 는 이제 **기존 Risk 를 RESOLVED 로 닫는다.**
provider 조회가 실패했을 뿐인데 위험이 사라진 것으로 기록된다.

대조가 실패했거나 문서를 못 받았을 때 점수가 없다. 그것을 0 으로 두면 **LOW 로
읽힌다.** KIPRIS 오류 본문을 "결과 0 건" 으로 처리해 특허 분석이 `COMPLETE` 로
끝나던 것과 같은 종류의 사고다.

점수가 없으면 우선도를 매기지 말고 coverage 를 낮춘다. "모른다" 는 "낮다" 가 아니다.

### 4.2 임계값은 정책이다. 버전을 남긴다

라이선스 정책이 `POLICY_VERSION` 을 결과에 남기는 것과 같아야 한다. 임계값을 바꾸면
과거 판정의 의미가 조용히 달라진다. `AnalysisVersions` 에 임계값 버전을 남겨야
"작년의 상" 이 무엇이었는지 설명할 수 있다.

### 4.3 강등은 코드가 아는 사실로만 한다 (2026-08-22 확정)

"확신이 낮은 것을 위로 올리면 사람이 가짜 우선순위를 따라간다" 는 원칙은 유지한다.
바뀐 것은 **확신이 낮다는 것을 누가 판단하는가** 다.

예전에는 모델이 남긴 `uncertainty_flags` 가 비어 있지 않으면 HIGH 를 한 단계
내렸다. 실측은 이 규칙이 규칙이 아니라 상수임을 보여 주었다.

```
대조 80 건 중 표시가 하나 이상: 77 건
HIGH 자격(청구항 근거 + 겹침 2 이상): 13 건 → 13 건 모두 강등
표시가 0 개인 3 건은 모두 겹침 0 (어차피 LOW)
```

표시의 문구를 실제로 뽑아 보니 이유가 분명했다.

> 선행 특허 청구항에는 화자 분리에 사용되는 패턴 인식 기법의 구체적인 수학적
> 알고리즘이 제시되어 있지 않음

이것은 **특허의 서술 범위에 대한 논평**이지 우리 판단의 불확실성이 아니다.
청구항이 상위 개념으로 쓰이는 것은 정상이므로 이 관찰은 언제나 참이다.
"판단이 어려웠던 이유를 적으라" 고 물으면 모델은 언제나 무언가를 적는다.

그래서 강등 조건을 **코드가 검증할 수 있는 사실**로 좁혔다. 지금은 하나다.

| 조건 | 누가 아는가 | 효과 |
|---|---|---|
| 대조가 본 근거가 잘렸다 | 근거 원장 (`EvidenceLedger.truncated_ids`) | HIGH → MEDIUM |

청구항은 실측 중앙값 176 자로 대개 600 자 상한에 걸리지 않는다. 드물게 걸리고,
그래서 걸릴 때 뜻이 있다. 근거 상한을 올려 잘림을 없애는 선택도 있었지만,
"근거는 재검토를 위한 최소 인용이지 원문 보관이 아니다" 는 원칙을 깨게 되므로
잘렸다는 사실을 등급에 반영하는 쪽을 택했다.

모델의 관찰은 `review_caveats` 로 이름을 바꿔 남기되 **등급을 바꾸지 않는다.**
프롬프트도 v2 에서 "청구항이 구현 세부를 한정하지 않았다는 관찰은 적지 말고
`distinct_elements` 에 적으라" 고 명시했다. 실측에서 후보 3 건 중 2 건이 빈
`review_caveats` 를 냈고, 남은 하나는 문서 자체의 미해결 사항을 짚어 검토에
실제로 쓸모가 있었다.

판정은 규칙 엔진이 하고 모델은 설명한다 — 이 경계를 등급에도 적용한 것이다.

### 4.4 판정한 것이 무엇인지 남긴다

등급을 정하는 것은 대조 프롬프트인데 `AnalysisVersions.prompt_version` 에는 추출
프롬프트만 실리고 있었다. 규칙이나 프롬프트가 바뀌면 과거 판정의 뜻이 조용히
달라지므로 둘을 함께 남긴다 (`patent_extract_v2+patent_compare_v2`).

## 5. 임계값을 고르는 방법

임계값은 코드 문제가 아니라 **교정 문제**다. 필요한 것은 라벨이다.

1. 문서 ↔ 특허 후보 쌍을 30~50 개 모은다. 지금 corpus 로 충분히 만들 수 있다
2. 사람이 상/중/하를 매긴다. **점수를 보지 않고** 매겨야 한다
3. 후보 점수 분포를 그려 두 임계값을 고른다
4. 검토 비용 기준으로 조정한다 — HIGH 는 "반드시 사람이 본다" 는 뜻이므로 개수가
   감당 가능해야 한다. 정확도보다 **HIGH 의 총량**이 먼저 제약이다

라벨 없이 고른 임계값은 숫자만 있고 근거가 없다. 그럴 바에는 지금의 이산 규칙이
낫다 — 적어도 규칙은 읽고 반박할 수 있다.

## 6. 순서 제안

1. 청구항이 들어온 상태에서 **현재 규칙의 우선도 분포를 관측**한다
2. 분포를 보고 이산 규칙으로 충분한지 판단한다. 충분하면 여기서 멈춘다
3. 부족하면 A 안 파생 점수를 도입하되 **우선도 판정은 바꾸지 않고 점수만 기록**한다
4. 라벨을 모아 분포를 보고 임계값을 고른다
5. 그때 판정을 임계값 기반으로 전환하고 임계값 버전을 결과에 남긴다

3 번이 중요하다. 점수를 먼저 관측만 하면 되돌릴 것이 없고, 임계값을 고를 실제
데이터가 쌓인다.

## 부록 — §6.1 "우선도 분포 관측" 의 첫 실측 (2026-08-22)

특허 Risk 가 처음으로 생성되면서 §6 의 1 번 단계를 실제로 밟을 수 있게 됐다.

```
PATENT  33 건  →  HIGH 0 · MEDIUM 33 · LOW 0
LICENSE 24 건  →  HIGH 12 · MEDIUM 12
```

**현재 규칙은 특허에서 아무것도 가르지 않는다.** 33 건이 전부 MEDIUM 이다.
우선도가 하나의 값으로 뭉치면 검토 순서에 아무 정보를 주지 못하므로, 이것은
§2 에서 예상한 상황("청구항이 없던 시절의 우회책") 이 반대 방향으로 나타난
것이다.

청구항 근거가 붙었으므로 `has_claim_evidence` 는 참이다. 그러면 규칙상
HIGH 가 되려면 `match_count >= 2` 여야 하는데 전부 MEDIUM 이라는 것은
둘 중 하나를 뜻한다.

1. 대조에서 겹치는 구성요소가 대개 **1 개**만 나온다
2. 불확실 표시가 붙어 HIGH 에서 한 단계 내려온다

둘은 처방이 다르다. 1 번이면 대조 프롬프트가 구성요소를 너무 좁게 잡는 것이고,
2 번이면 임계값이 아니라 불확실 판정 기준을 봐야 한다.

### 갈린 결과 — 둘 다였고, 2 번이 결정적이었다

`patent_priority_diagnostic` 으로 대조 80 건을 관측했다.

```
priority     : LOW 38 · MEDIUM 42 · HIGH 0
match_count  : 0→37 · 1→30 · 2→10 · 3→3
불확실 표시   : 0개→3 · 1개→74 · 2개→3
```

| (겹침, 청구항, 표시) | 등급 | 건수 |
|---|---|---|
| (0, ✗, 0~2) | LOW | 37 |
| (1, ✓, 1~2) | MEDIUM | 29 |
| **(2, ✓, 1)** | **MEDIUM** | **10** |
| **(3, ✓, 1)** | **MEDIUM** | **3** |

`match_count == 1` 이 MEDIUM 42 건 중 29 건으로 지배적이지만 HIGH 를 막은 것은
아니다. **HIGH 자격을 갖춘 13 건이 13 건 모두 강등**됐고, 표시가 0 개인 3 건은
어차피 겹침이 0 이었다. 즉 HIGH 에 닿을 수 있는 후보는 예외 없이 표시를 달고 있었다.

처방은 §4.3 에 있다. 남은 `match_count == 1` 문제는 A 안 점수의 분모와 직결되므로
§6 의 3 번에서 다룬다.
