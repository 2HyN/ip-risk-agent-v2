## 지금 막혀 있는 것 — 읽고 시작하라

**corpus 적재와 배포는 0-G 뒤다.** 지금 적재하면 안 된다.

`DEVELOPMENT_SPEC.md` §5.5 가 관련성 게이트를 **corpus 확대의 선행 조건**으로 못박아
두었다. 이유는 그 절에 적혀 있다 — 오부착을 막고 있던 것은 게이트가 아니라 **corpus 가
비어 있다는 우연**이었고, 문서를 늘리면 틀린 식별자마다 그럴듯한 문서가 하나씩 생긴다.

실제로 그렇게 됐다.

| | 확대 전 | 확대 후 |
|---|---|---|
| corpus 문서 | 3 편 | **73 편** |
| 게이트를 통과하는 질의 | 686 | **26,890** |
| 그중 오부착 | 318 (46.4%) | **7,902 (29.4%)** |

**비율은 좋아졌는데 양이 25 배가 됐다.** 아직 손해가 없는 이유는 하나뿐이다 —
`prepare_rag_ingestion.py` 가 dry-run 이라 **전문이 Vertex RAG 에 올라가 있지 않다.**
올리는 순간 7,902 건의 틀린 근거가 실제로 쓰이기 시작한다.

**0-G 는 끝났다** (`088ee4a`). 같은 전수 측정에서 오부착이 **7,902 → 0** 이 됐다. 다만
**커밋됐을 뿐 배포되지 않았다** — 배포본은 `78a6490`/`79207f2` 라 아직 옛 게이트가 돈다.

### 적재 예행이 통과했다

RAG Engine 은 올린 문서를 **되받아 볼 수 없다.** 그래서 한 편만 올려 방법이 맞는지
먼저 확인했다 (시험용 corpus 를 따로 만들어 쓰고 지웠다. 운영
`6917529027641081856` 은 건드리지 않았다).

```
올림   agpl-3.0-obligations 1 편
감사   clean — 빠짐 0 · 중복 0 · 지문 불일치 0
검색   "AGPL-3.0-only 배포 시 의무사항" → 그 문서가 되돌아옴 → 게이트 통과
```

마지막 줄이 핵심이었다. Vertex 가 `sourceDisplayName` 을 `source_id` 로 돌려주므로
관련성 게이트가 커버리지를 맞출 수 있다. 여기서 이름이 어긋났다면 **목록은 멀쩡한 채로
근거가 전부 떨어져 나갔을** 것이고, 목록 API 로는 영영 안 보였을 고장이다.

### 남은 순서 [결정]

전체 727 편을 **같은 방식으로 한 번에 실제 corpus 에 올린다.**

1. **빌더에서 표 의존을 뺀다** → 73 → 727 편 (Fork 몫)
2. 올리고 `--verify --probe`
3. **0-G 가 든 리비전과 `RAG_CORPUS_ID`·`RAG_CORPUS_VERSION` 을 함께 배포한다**

3 이 하나로 묶여야 한다. 옛 게이트가 도는 동안 corpus 만 커지면 틀린 근거가 붙는 양이
그만큼 늘어난다 — 그것이 §1.3 이 경고한 "틀린 판정이 기록으로 굳는" 것이다.

## 측정 현재값

`DEVELOPMENT_SPEC.md` §10 의 표는 이 값들로 갱신되어야 한다 (아직 안 했다).

| 지표 | 명세에 적힌 값 | **지금** |
|---|---|---|
| corpus 커버리지 | 4/22 = 18.2% | **84/113 = 74.3%** (29 종이 덮이지 않음) |
| 오부착률 | 46.4% (686 중 318) | **29.4%** (분류 158 시점 측정. 226 으로 넓어져 재측정 필요) |
| SPDX 어휘 (`_CANONICAL`) | 42 | **727** |
| 정책 분류 (`_OUTCOME_BY_ID`) | 42 | **226** |

**커버리지가 100% 에서 74.3% 로 내려갔다. 후퇴가 아니라 분모가 커진 것이다.** Fork B 가
분류를 158 → 226 으로 넓히자 `needs_review` 대상이 84 → 113 이 되었고, 새로 분류된 29 종에는
아직 corpus 문서가 없다.

**이것은 A 와 B 가 서로에게 일을 만드는 고리다.** B 가 분류를 넓힐 때마다 A 가 덮어야 할
문서가 늘고, A 가 다 덮으면 B 가 또 넓힌다. 커버리지는 그 사이를 오르내린다. 두 흐름을
한 사람이 쥐어야 이 진동이 멈춘다 (아래 "일하는 방식" 참고).

### 멈추는 규칙 — 실측하고 나서 낸 권고 [사용자 결정 대기]

**표를 세면 226/727 이지만, 실제 경로로 재면 그림이 다르다.** `spdx.normalize` 가 폐기된
옛 식별자를 현행으로 바꿔 주기 때문이다.

```
GPL-3.0   -> GPL-3.0-only   -> POLICY_CONFLICT -> HIGH
AGPL-3.0  -> AGPL-3.0-only  -> POLICY_CONFLICT -> HIGH
GPL-2.0+  -> GPL-2.0-or-later -> POLICY_CONFLICT -> HIGH
```

표 밖 501 종을 전부 돌려 보면 **30 종이 정규화로 구제되고**(전부 copyleft 별칭)
**471 종만 진짜 `UNKNOWN`** 이다. 그 471 종의 정체는 폰트·문서·벤더 라이선스다 —
`Abstyles`, `Afmparse`, `Arphic-1999`, `Adobe-Utopia`, `Aspell-RU`, `AMD-newlib` 처럼
의존성 매니페스트에 거의 나타나지 않는 것들이다.

**그런데 23 종은 다르다.** 471 종 중 copyleft 계열이 그만큼 있다 — `CECILL-1.0/1.1/B`,
`NPL-1.0/1.1`, `QPL-1.0-INRIA-2004`, `copyleft-next-0.3.x`, `ESA-PL-*-copyleft-2.4`,
`LGPLLR`, `Linux-man-pages-copyleft*` 등. 이것들이 중요한 이유는 등급이 갈리기 때문이다.

| 판정 | 우선도 | 사용자가 읽는 문장 |
|---|---|---|
| `POLICY_CONFLICT` | **HIGH** | 결합 저작물의 소스 공개를 요구한다. 비공개 배포와 충돌한다 |
| `UNKNOWN` | **MEDIUM** | 라이선스를 식별하지 못했다. 자동 허용하지 않는다 |

**강한 copyleft 가 MEDIUM 으로 뜬다.** 보이기는 하므로 조용한 유실은 아니지만, 등급과
문장이 둘 다 틀리다. §7.3 이 말하는 "틀린 하향" 이다.

**권고 — 셋으로 나눈다.**

1. **지금 한다: copyleft 23 종.** 유한하고, 하나하나가 HIGH ↔ MEDIUM 을 가른다.
2. **수요가 부르면 한다: 나머지.** 실제 의존성 파일에 나타날 때 분류한다.
3. **하지 않는다: 폰트·문서·벤더 라이선스.** `UNKNOWN` = MEDIUM 이 정확한 표현이다 —
   정말로 모르고, 자동 허용하지도 않는다.

**471 종을 전부 분류하면** 지금까지 한 법적 판단이 두 배가 되고 corpus 문서 471 편이
따라오며, A↔B 고리는 끝나지 않는다. 얻는 것은 거의 나타나지 않는 라이선스에 대한 정밀도다.

**계측이 2 번을 가능하게 한다 [결정 필요]** — `UNKNOWN` 이 나올 때 그 SPDX 식별자를 로그에
남기면 실제 분포가 무엇을 분류할지 알려 준다. SPDX 식별자는 공개 문자열이고 0-I 가 이미
남기는 `dependency_format` 과 같은 부류(내용이 아니라 종류)라고 보지만, 사용자가 무엇에
의존하는지를 간접적으로 드러내므로 **말없이 넣지 않고 여기 올린다.**

**어휘와 정책의 대칭이 의도적으로 깨졌다.** 예전에는 둘이 정확히 같은 42 개였고 시험이
그것을 고정했다. 지금은 727 종을 **식별**하되 158 종만 **분류**한다. 나머지 569 종은
`UNKNOWN` 판정을 받지만 **식별자 문자열은 살아남는다** — 이것이 0-F(원문자열 보존)가
풀려던 문제의 상당 부분을 이미 푼다. 0-F 의 남은 몫은 727 종 밖의 것(사내 라이선스,
`LicenseRef-*`)이다.

**내용은 하나도 잃지 않았다.** 시험 930 건 전부 통과하고,
`scripts/validate_gcp_deployment.py` 를 Fork A 와 Fork D 가 각각 고쳤는데 양쪽 변경이 모두
살아 있다 (서로 다른 자리를 고쳐 운이 좋았다).

* `366ffff` 는 메시지가 "docs(status): report Fork B's result" 인데 **81 개 파일**이 들어

* `5e83336`(Fork D)은 Fork C 의 파일 둘을 함께 담아 갔다.
* `078c0f0`(메인)은 `docs/status` 를 통째로 스테이지했다. 그 안의 파일은 내가 만든
